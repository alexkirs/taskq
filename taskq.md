# taskq contract
taskq runs a queue of agent tasks on a GitHub or GitLab issue board. This file is the whole contract: states, log, roles, lease and fencing, compatibility and deployment. History of decisions lives in git and issues; operational state on the board (R1).
This file specifies **v4**, the Rust binary from `src/`.
## Principles (R1–R13)
### Change rule
A task that changes a rule names its R-number, edits this file in the same deliverable as the code and lists the amended R-numbers in its result. A changed rule keeps its number. A new rule gets the next one. A rule elsewhere that disagrees with this file is a defect. No history here: no dates, no decision logs; line bound: R8.
### R1. The board's own objects are the only state
No machine block in issues. State is what a person sees: labels, the issue text, `taskq:` comments (§ 2) and host heartbeat issues (§ 4). The comment log is the truth; labels are its projection. Local files are caches that a restart rebuilds: no local DB, receipt store, queue or lock. Exception: accepted [DashQ connection state](docs/design/enrollment.md) (identity/grant/revoke and coalesced projection, never task truth); AI request files, the tray's request history, the request log, local incident/profile records (§ 4) and the host admission file and lock and the emergency hold file (§ 3); the host operator's [resource grants and operation receipts](docs/design/shared-resource-controls.md#host-adapter) (`resources/`); they hold no task state. The `pid` of a fresh `status.json` is the one-service-per-root check (§ 4), not a lock.
### R2. One task, one attempt
A task has at most one live attempt: one worker or one reviewer process. Work bigger than one reviewable diff follows [shared task preparation](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#prepare-the-task), using tasks linked by `Depends on #N`. A live attempt is never moved to another host or session; a new attempt replaces it (§ 4).

### R3. Roles
- **Owner**: decides product questions, answers `ask`, accepts or rejects results through the PM.
- **PM** (manager): the agent session the owner talks to. Files tasks, relays questions and outcomes. Does no task work, never answers for the owner. The queue does not depend on a PM being online.
- **Service**: one per host (§ 5). The only process that spawns workers, reviewers and operators.
- **Worker** `T<N>`: a child of the service. Does one attempt, writes `result`, `ask` or `requeue`.
- **Reviewer** `R<N>`: a child of the service, spawned on demand for a result. Checks the exact candidate, then `close`, `requeue` with fixes, or `ask`. No resident supervisor session.
- **Operator**: the owner-facing agent for project research, edits, checks and TaskQ operations (§ 4), with normal runtime tools and project permissions (R9); authority per [shared approval boundaries](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#approval-boundaries), unresolved authority uses clarify/proposal. Task-state writes use TaskQ commands, never hand-edited logs. Its failure does not fail a worker task and does not prove absence of side effects.

Session names: `T<N> <title[:40]> (<host>)` and `R<N> <title[:40]> (<host>)`.

### R4. Comments move the queue
Each command that changes a task appends one `taskq:` comment, sets the projected labels and pokes the local service. Services also poll the board every `poll` seconds. No sender session, timer or PM chat is on the critical path.

### R5. Completion is written to the task
Result SHA, checks, questions and blockers go to the issue as `result`, `ask`, `requeue` comments; completion evidence follows [specq verification](https://github.com/taskqorg/specq/blob/main/engineering/verification.md).

### R6. Human report
`taskq status` renders the [read-model](docs/design/refactoring-backlog.md) snapshot of one board read (§ 5 `--json`; service status, `status.json` and tray count the same rows), in this order (empty parts omitted). Tray/browser project summaries and task rows (metadata/links first, full wrapped title second under M3) reuse [shared project blocks](docs/design/project-blocks.md), including separate Doing/Review, nonzero K counters and unknown Closed until authoritative totals exist:
1. `<project> · [board](<url>)`, preceded while a local `status.json` under 60 s old reports a board rate-limit pause (§ 4) by `Rate limit: board requests paused until <time> (<host>)`, else a low board budget by its § 4 line, also when this read fails.
2. `In work N · Waiting for answer N · Ready N`. In work: `doing` + `review`. Waiting: `ask`. Ready: `ready`.
3. `| Task | State | Runtime | Session |`, one row per open task except `ask`, `later`, `failed`, by priority then number; task and session cells are links; `waiting` rows say `blocked ([#M](url) open)`: each blocking dependency (§ 1) linked, then `open` or `unknown: <reason>`; `status --json` rows add `blocked` (`ref`, `url`, `reason`).
4. `Questions (answer N.M):` and `| Question | Brief reason | Options |` with `N.1 <option> · N.2 <option> ★` (★ =
   recommended), one row per `ask` and per `review` with options; an owner action (§ 2) reads `waiting for owner: <action>`.
5. `Later: [#N title](url), ...` on one line; then `Failed:` with a reason table.
6. `Hosts: <host> v<version> <age>[ focus off|unknown], ...` from heartbeats (§ 4).
7. `Next: 1 <action> ★ · 2 <action>` from the PM ([shared Next contract](https://github.com/taskqorg/specq/blob/main/design/workflow.md#ai-assisted-controls)).

Display titles at most 60 characters, reasons at most 160 and option text at most 120; show ellipsis with an issue link for the full text. Keep every row and option, counts and answer tokens; no total report cap. Cells pass one formatter: newline becomes space; `|`, `[`, `]`, `\` are escaped. Claude links use only the Remote Control URL registered by that native session; the local UUID is not a remote ID. Codex links: `codex://threads/<id>` when `TASKQ_CLIENT=codex`, else `<pages>/open.html#codex://threads/<id>`.

### R7. Style
Follow [specq Core](https://github.com/taskqorg/specq/blob/main/caveman/rules/core.md) and its applicable profile; project documents follow [Documentation](https://github.com/taskqorg/specq/blob/main/caveman/rules/documentation.md) in English.
Single and batch CLI outcomes use the same success/error renderer; a failed item keeps its task number.
Owner-text templates in sections 1, 2, 4, 5, 7 are the design target; release them with their implementation (R8), not as proof of shipped behavior.
Limits count logical lines and Unicode characters, including labels and numbering; exclude blank separators and the log header.
Link targets and exact commands/SHAs/paths are exempt from character limits, not line limits; link labels stay short.
Commands refuse over-limit new input before writing, naming the excess; historical/hand-written entries fold unchanged; compact displays use ellipsis and a link (stored text verbatim: [Core Write](https://github.com/taskqorg/specq/blob/main/caveman/rules/core.md#write), [source and sink](https://github.com/taskqorg/specq/blob/main/caveman/rules/changes.md#keep-the-source-and-sink-separate)).

### R8. The contract is the SoT and matches code
Apply [shared spec-first rules](https://github.com/taskqorg/specq/blob/main/engineering/spec-first.md) to this contract: TaskQ code and contract ship in the same release (§8); every §2 table row has a golden trace, and this file stays within 300 lines.

### R9. No silent changes to model, effort or permissions
Name any change to the owner first. `permission_mode`, `codex` and capacity (§ 9) in `taskq.json` are the owner's: agents propose capacity, apply it only on the owner's explicit instruction. Worker access comes only from operator-owned grants (§ 8 Access; [worker permissions](docs/design/worker-permissions.md) P1–P4; [permission authority](https://github.com/taskqorg/specq/blob/main/engineering/permission-authority.md)): project config, task text, labels and board answers may request or narrow access, never grant it. Legacy defaults (requests, not grants): Claude `--permission-mode dontAsk`; Codex `-s danger-full-access`. The operator (R3) uses the same configured CLI permissions, § 8 Access and host board environment as workers; no tool-free override, silent elevation or runtime fallback. Owner requests grant their stated scope; setup external effects still require §6 confirmation.

### R10. Multi-project only by explicit list
A PM manages several projects only from an owner-written list; folders are never discovered. One report per project. An
`N.M` answer that could match several projects needs the project named first.

### R11. Retire sessions only after their attempt ends
A worker or reviewer is stopped only when its task is closed or parked or its attempt is replaced, emergency recovery included (§ 4). Identity is the recorded native session ID, never a name match; a completed Claude background turn is stopped after native completion readback, and a CLI child after its log shows the turn ended (§ 4 step 1), each with its conversation retained for the next turn. Uncommitted work is never lost: only `cleanup --force` removes it, after saving it to `<root>/.taskq/trash/taskq-<N>.patch`.

### R12. Unverified means unknown
Follow [shared verification rules](https://github.com/taskqorg/specq/blob/main/engineering/verification.md). TaskQ readback and platform obligations are specified in §§4–8. Chain checks ([test classes](https://github.com/taskqorg/specq/blob/main/engineering/verification.md#test-classes)) are `cargo test --locked` and `taskq selftest`, both in CI. The [runtime qualification matrix](docs/runtime-qualification.md) is the bounded live acceptance, rerun only when its runtime path, permissions or client version changes; it is not a per-commit gate. Do not duplicate matrix evidence with command-string assertions. Design prototype tests under `docs/design/` are development instruments: not in CI, not a handoff requirement, and they write evidence only on request. Browser instruments (`tests/*.browser.cjs`, prototype tests) launch through `tests/browser.cjs`: Playwright's chromium headless shell by default; `PLAYWRIGHT_CHANNEL` picks an installed browser outside a worker only, and a worker (`TASKQ_TASK` set) ignores it with one log line, because the Google Chrome app aborts at startup under the macOS service and leaves a crash dialog. Tray screenshots run only when a check needs them and capture only the routes the diff changes (`tray --snapshot DIR --route R,..`); the full matrix (every route, both themes, 16/20 px; [native matrix](docs/design/ui-acceptance.md#native-matrix)) runs only for README shots and release qualification.

### R13. Spec first
Inherit [specq engineering rules](https://github.com/taskqorg/specq/tree/main/engineering) and its [shared-rule improvement process](https://github.com/taskqorg/specq/blob/main/engineering/spec-first.md#improve-shared-rules). General rules belong upstream; TaskQ scenarios and gaps stay in [use cases](docs/use-cases/README.md). Design collaboration follows the [shared workflow](https://github.com/taskqorg/specq/blob/main/design/workflow.md); the [implementation brief](docs/design/implementation-brief.md) maps the accepted product to system and application work. ## 1. Tasks
A task is an open issue by a trusted author (GitHub `OWNER|MEMBER|COLLABORATOR`, GitLab Reporter+) labelled `taskq` (`taskq add` sets it; on the board a person adds it). Any other issue never starts: a PM makes a task from it with `taskq add` and comments on it when the task closes. A closed issue is done, unless the board records that it closed without completing (GitHub `state_reason` other than `completed`, e.g. `not_planned`): such a dependency reads unknown, never done (R12; GitLab records no reason). The issue text is for people and may be
edited by hand: `## Goal`, `## Acceptance`, optional `## Scope`, one line `Depends on #N` per dependency; `Depends on <repo>#N` names an issue of another repository on the board's host, read with the board's token (`<repo>`: `name` under the board's owner, or `owner/name`). An unreadable dependency reads unknown. Acceptance items are `A1.`, `A2.`, never renumbered; each an observable result a reviewer checks without reading the code.
`add` writes these sections in that order, then dependencies: Goal 1-2 lines; Acceptance 1-8 items, one line each;
Scope optional, 1-4 bullet lines; dependencies one `Depends on #N` line each; with `--op-id`, a last line `op-id: <id>` identifies the create for read-only recovery below. Title at most 80 characters; each body line at most 240. Use short imperative sentences: Goal names the user outcome; each Acceptance names a visible check; Scope names a boundary. Keep headings on their own lines and one blank line between sections. More than eight checks: split before filing (R2).
**Create claim (R1, R12, R13).** `add --op-id` needs the owner's `create_claim_issue` (a positive issue number on this board by a trusted author; not a task, held or host issue) and a board that passed the § 3 read-after-write qualification. The first trusted, unedited `taskq: create-claim <id>` comment by comment id owns the op id forever (no expiry or transfer, a crash included); its second line `request-sha256: <hex>` binds actor, title, full body, labels and later text, and changed input is rejected. Only the invocation whose claim POST returns that winning comment, read back in full, may send one create POST.
Every other invocation reconciles read-only over open and closed issues with that op id: exactly one trusted issue with matching title and body returns its readback receipt; missing, conflicting, duplicate or unreadable evidence is unknown; a legacy issue without a claim is refused for owner reconciliation. An unknown claim or create POST never permits a create POST, even after a restart or an empty list. Never edit or delete claims or change the claim issue while operations exist; older clients must not submit these creates. Drafts stay with the consumer; hold/start application is separate and gets no recovery write here. `add` without an op id stays non-idempotent.
**Finding CLI (R1, R12, R13).** `taskq finding <title> --board URL --source installation/rule/episode --goal G --acceptance A.. [--evidence E..] [--start]` runs only as the owner-authenticated local CLI on the configured board (URL equals the snapshot's board URL; no board or config override). Observation and answer grants never authorize it; remote action grants remain a prerequisite. Each source part is an opaque 1-64 character ASCII id (`A-Z a-z 0-9 . _ -`, not dot-only), never a path or URL. Evidence is owner-reviewed text, at most four bullet lines of 240 characters, never collected automatically; consumers sanitize it and keep drafts on cancel, rejection or unknown outcome.
The op id `finding.<sha256>` of board identity and source gives each episode one permanent claim, binding actor, board, reviewed body, labels and the start choice; changed input is rejected. The create always uses `q-held`; a create retry is read-only. `--start` or a later `start` may initialize the held log and dispatch the separate idempotent `<op-id>.start` on the found issue; a failed or unknown start keeps the issue and never repeats create. `start` acceptance proves eligibility under focus, permissions and limits, not a worker launch. JSON `{create: receipt, start: receipt|null}`; text prefixes `Create:`/`Start:`. No new states or local draft store.
Held: `add --hold` labels the issue `q-held` instead of `taskq`, then writes `hold`; it is listed as `held` (whatever its log) and no version admits it. `taskq start N` writes `start`, then adds `taskq`.
Labels: `q-<state>` (projection; `waiting` maps to `q-blocked`); type `code|docs|research|asset`; `p0|p1|p2` (lower first, absent = 2; `p0` passes focus, § 4); `run-<runtime>` (none: any); `prefer-codex|prefer-claude` (soft, § 4 Filter); `host-<name>` (none: any host); `needs-<x>` (only a host whose `has` lists x, § 9);
`assignee-only` (start only when the board's user is an assignee); any other, e.g. `area-maps`. Reserved: `taskq-host`.
## 2. Log and states
A log entry is a comment by a trusted author whose first line is `taskq: <kind> [<arg>] [attempt <id>]`; the rest of the comment is its text. Entries are read in comment-id order. An edited comment (`updated_at` after `created_at`) or an unknown kind is ignored. A person can type an entry by hand; it counts like a command. The CLI form `taskq answer K` or `taskq answer N.K` (no colon, N = this task) also counts as `answer K`. In `ask` a comment whose whole body is K or option K's text (trimmed, any case, `K. ` optional) of the open card counts as `answer K` if one option matches; `fold` ignores other comments (an owner comment, § 4).

`core.rs` is one pure function `fold(n, entries, deps_open) -> Task {state, attempt, role, session, retries, card, result, inbox}`; `inbox` lists the accepted `answer`/`steer` ids of the current attempt. The attempt id is the id of the accepted `spawn` comment; it is the fencing token. An entry that names `attempt <id>` is accepted only when `<id>` is the current attempt. An entry not accepted in the current state is ignored and changes nothing.
Optional last lines `op-id: <id>`, then `revision: <R>`, of an entry are fields, not text; without the op id line a `revision:` line is text. The task's revision is the id of the entry that set its open card, else its attempt, else its last accepted entry (0: none). `fold` ignores an entry whose op id an earlier entry carried; a writer whose entry read back at another revision or ignored edits it (§ 5).

| State | Entry | Next | Notes |
|---|---|---|---|
| (none) | — | `ready`, `waiting` if `Depends on` names an open issue | start of every task |
| (none) | `hold` | `held` | only as the first accepted entry; N-1 ignores the kind |
| `held` | `start` | `ready`, `waiting` if `Depends on` names an open issue | then the writer adds `taskq` (§ 1) |
| `held`, `ready` | `gate` | same | owner gate `required` (§ 7); N-1 ignores the kind |
| `review`, `ask` | `approve <sha>` | same | gate `approved`; owner only (no `attempt`); `<sha>` is the current result |
| `ready` | `spawn worker <rt>:<session> <host>` | `doing` | attempt = this id, role worker |
| `doing` | `result <sha> attempt` | `review` | text: verdict (section 7); option lines make a card (section 2) |
| `doing` | `ask attempt` | `ask` | text: ask card below |
| `doing`, `review` | `requeue attempt` | `ready` | text: reason or fixes; `retries += 1`; 3rd: `ask` with the limit card |
| `doing`, `review` | `gone attempt` | `ready` / `review` | service: child exited or lease expired; emergency recovery (§ 4); `retries += 1`; 2nd: `ask` with the limit card |
| `doing` | `steer` | `doing` | text for the worker |
| `review` | `spawn reviewer <rt>:<session> <host>` | `review` | only without a live reviewer; attempt = this id |
| `review` | `ask attempt` | `ask` | reviewer's card; result kept |
| `review` | `close attempt` or `close` | closed | verdict text; written after publication (§ 7); ignored while a gate is not `approved` |
| `ask` | `answer [K]` | state before `ask`, else `ready` | `retries = 0`; delivered: text, else option K, else first line |
| any open | `requeue` | `ready` | by PM/owner: result, card and attempt cleared; `retries = 0` |
| any open | `later` / `failed` | `later` / `failed` | text: reason; attempt ended |
| `later`, `failed` | `requeue` / `close` | `ready` / closed | the only exits |

- `waiting` becomes `ready` when every `Depends on` issue is done (§ 1); an open or unknown one keeps it waiting.
- `gone` in `review` ends only the reviewer; the result stays and a new reviewer is spawned. Emergency interlock ([E1–E5](docs/design/emergency-recovery.md)): under the § 3 emergency hold no `spawn` is written on that host until `service release`; a child whose liveness reads unknown gets no `gone`; `service recover --apply` writes each `gone attempt` with `--op-id` and `--revision` (§ 4).
- `retries` is one counter: an attempt `requeue` that makes it 3, or a `gone` that makes it 2, moves to `ask` with the attempt ended; its `answer` then goes to `ready`. Limit card: a writer whose entry hits the limit appends, unless its text is a card, `Problem:` naming the limit, `1. requeue: …` ★, `2. later: …` and `To answer:` naming only `taskq answer N.K`; the reason's `K. ` lines become `K) ` (N-1 folds the same text). Every move to `ready` clears attempt, card and result.
- `answer K` whose option starts with `close` or `later` runs `close` (§ 7) or `later` instead, only through `taskq answer N.K`: a bare board comment `K` folds as a plain answer; an owner pick of `approve <sha7|sha> ...` approves a gated task only when that SHA matches its current result, including a bare board comment in `ask`. An attempt-bound answer cannot approve.
- Gate states: none, `required`, `approved`, `stale`. An approval binds to the result it names: the next `result` or a move to `ready` makes it `stale`, which blocks like `required` until an `approve` of the new result. The gate blocks only `close` in `review` (its publication and the closed issue that frees `Depends on` tasks); a fold from the board after any restart keeps it (R1). Closing a `later`/`failed` task stays the owner's own act.
- After an entry is accepted, the writer sets the `q-<state>` label; every service pass fixes labels that differ from the fold. A hand-moved label is overwritten: people change state with an entry.

### Ask card
`ask` writes, in order, at most nine nonblank lines, without headings or blank lines inside the card:
1. `Done: <what was checked or attempted>` -- one line, at most 160 characters; say `not started` when true.
2. `Problem: <decision needed and user effect>` -- one or two lines, at most 240 characters per line.
3. Optional `Evidence: [<label>](<url>)` -- one line, at most two screenshot/video/issue/PR links, labels at most 40 characters each.
4. Two to four options, `1. <action and trade-off>` etc.; one line each, at most 160 characters, exactly one ends in `★`. None: an owner action, its Problem the action; no attempt starts while it waits, its `answer` resumes the same session.
5. To answer: `taskq answer N.K` or comment `K` or the option text; an owner action: `taskq answer N --text <done>`. Last line; substitute this task's number for N.
Accepted shared UI target: [answer card](docs/design/answer-card.md) owns the reusable TaskQ/DashQ presentation; § 2 and § 5 remain behavioral authority. Tray exception (R6): mount cards only in `ask`; without parsed choices, show text and owner requeue (reason), later and confirmed Close controls. Close cancels without publication through `later` then `close`, each with CLI readback; partial/unknown delivery stays explicit. An answer op is resent only with its own id: once when a refresh reads the task past its revision, once per Check delivery after an unknown receipt. Other consumers remain read-only for unparsed cards. K is an option number; a bare K or option text counts only in `ask` (section 2).
`--text` supplies literal Done and Problem lines; `--link` supplies Evidence; `--option` and `--recommend` supply the options/star.

### Executable behavioral model
Apply the [shared behavioral-model method](https://github.com/taskqorg/specq/blob/main/engineering/verification.md#state-driven-systems).
TaskQ sources: the §2 transition table, `tests/golden/*.json` traces (`fold.json`: entries in, expected task out; `admit.json`: free slots in, admitted runtimes out), `fold`, then adapters.
`fold` is the behavioral truth; board and process qualification remain separate under R12. Attempt stages (§ 4 Profiling) are adapter observations outside `fold`: `claim` from the `spawn` post through its readback; `start` the runtime start/resume; `build` (worker) and `review` (reviewer) from child start to exit or stop, outcome from the attempt's accepted hand-in (`result`/`close` ok, also when stopped after it; replaced without one is `cancelled`; an issue that left the board read is read back once, no hand-in or no read is `unknown` with reason); `ask` from this service seeing its attempt enter `ask` until it leaves (in memory, lost on restart); `checks` the publication's CI verification and merge call; `close` the whole `close` command. Queue transitions (§ 4 Profiling) are adapter observations too: a service pass replays each task log with entries newer than its previous pass, entry by entry, and each accepted entry that changes the folded state is one transition (`waiting` is not logged and adds none; `held` is outside the queue, so `hold` and `start` add none; the first pass after a service start adds none).
## 3. Attempts, lease, capacity
- **Claim.** A service that admits a `ready` task posts `spawn worker`, re-reads the comments and starts the child only if `fold` accepted its own `spawn`; a loser posts nothing more. Same for `spawn reviewer`. `ponytail:` needs read-after-write order of comment lists, verified per board by a two-host test before use (R12); a guard label around `spawn` is the upgrade path.
- **Fencing.** The child gets `TASKQ_TASK=<N>` and `TASKQ_ATTEMPT=<id>`; its commands add `attempt <id>`; `fold` ignores a replaced attempt's late writes. With `TASKQ_ATTEMPT` set, `result`, `ask`, `requeue` or `gone` is refused before any write, naming both, when `TASKQ_TASK` is not `<N>` or the attempt is not live; a retry of a seen op id returns its first receipt.
- **Lease** = the attempt's host heartbeat (§ 4) is fresh and lists `#<N> <id>`. No timestamps in the task.
- **App lease.** A `codex-app` (§ 8) turn counts as the child while the Codex app runs in this host's logged-in session and the thread has no `task_complete` after the queued brief or text. A finished turn without `result`, `ask` or `requeue`, a closed app or a logout is a child exit (`gone`). Stopping only drops it from the heartbeat; the turn runs on and its late writes are fenced. Updates and re-execs wait for active app turns and never retire them (§ 8 step 3).
- **Expiry.** Any service that sees `doing` or `review` whose host heartbeat is older than `ttl` or does not list the attempt posts `gone attempt <id>`; an attempt younger than `ttl` (by its `spawn` or newest accepted `answer` or `steer`) is judged by heartbeat age only. That is the only recovery. The owning service resumes an attempt without a child when its `inbox` holds an undelivered entry, else posts `gone` with the attempt's last worker message.
- **Capacity** per project and host = the effective `limits.<runtime>` (§ 9) minus the service's live children of that runtime, reviewers and resumes included. Fixed (default): 0 or no limit admits none; Auto (§ 9): no limit means no count ceiling, 0 disables. No project cap: host limits add up. Each pass reloads capacity config; invalid config holds every launch and reports. Lowering a limit never stops a child (R11).
- **Load gate** (opt-in, § 9) holds every new child (claim, reviewer, resume) while CPU busy >= `cpu_max` % or available physical memory <= `memory_min` %; running children continue. OS readings: [capacity load model](docs/design/capacity.md#load-model). One sample per 30 s on a monotonic clock, independent of `poll`; the first CPU reading is a baseline; a missing, invalid or over 60 s old reading holds. Auto also holds below 2.5 GiB available and at macOS memory pressure level >= 4; an unread floor holds. Start, enable and threshold changes start held; three consecutive valid samples at CPU <= `cpu_max` − 10 and memory >= `memory_min` + 5 reopen (90 s); a failed, late or mid-band sample resets the count. At most one launch per 30 s, the next after a post-launch sample; checked before claim and before launch.
- A held resume keeps its inbox undelivered; a won claim held before launch stays leased in the heartbeat, uncounted, with no other claim, retry or `gone`. No battery or thermal gating, no forced retirement. **Host admission.** One host authority, `<install>/admission.json` under `<install>/admission.lock`, admits every Auto launch after the load gate. Each service rewrites its entry (version, reservations) every pass and 30 s; an entry over 120 s old drops. A reservation is `requested` (refused, with reason), `held` (granted; counted until its child exits) or `released` (child exited, start failed, claim lost, entry dropped). A grant needs every fresh service of `<install>/projects` at `status.json` `version` `4.2.0-dev` or newer (the minimum service version), held reservations under `admission.max`, the last host launch at least 30 s ago and a gate sample after it. An unreadable file refuses and is rebuilt from the writer's entry. Fixed services write their entry and are never refused. **Emergency hold.** `<install>/hold` (one reason line) refuses every launch of every service on the host before the load gate until `service release` removes it; pause and resume never touch it; an unreadable file holds; live children run on; a held resume keeps inbox and lease. Older services ignore it; `service hold` names them.
- **Cancellation** of an attempt = `requeue`, `later`, `failed` or `gone`; the owning service stops the child (R11).
## 4. Service
`taskq service run` is the host's single long-lived process; `taskq service install` makes the OS keep it running (§ 8).
One loop:

1. Reap exited children; a CLI child whose attempt log shows its turn ended (`turn.completed`, `turn.failed`, `result`) counts as exited and its lingering process tree is stopped (#1034). A child whose attempt is still current posts `gone attempt <id>` with the exit code and the last worker message of its log (one line, absolute paths root-relative or `<path>`, at most 240 characters with the label; § 7 rule 6), unless the attempt wrote `ask`, `result` or `requeue` after the child started: a clean exit; step 6 resumes it from its inbox.
2. Stop children whose attempt is no longer current (R11). Remove worktrees of closed tasks (§ 7).
3. Write the heartbeat issue `taskq host <name>` (label `taskq-host`) when older than `ttl / 3` or its body changes: lines `version <v>`, `service <id>`
   (12 hex of SHA-256 of `<install>/installation-id`), `machine <hostname>[ wsl]` (the `hostname` output, as agentq `host.name`; `wsl` under WSL; DashQ joins Hosts rows by it, [dashq hosts](https://github.com/taskqorg/dashq/blob/main/docs/design/hosts.md) H2), `#<N> <id>` per live child or launch held by the load gate, `focus off|unknown` when the focus admits nothing, plus `at <board time>` (a same-body edit keeps `updated_at`). Freshness uses the board's `updated_at` and the response `Date`, never local clocks.
4. Post `gone` for attempts of dead hosts (§ 3).
5. Fix projected labels; `waiting` with closed deps becomes `ready`.
6. Resume the session of a live attempt for a new `answer` or `steer` (text on stdin); spawn a reviewer for `review` without a live one; admit `ready` tasks matching this host by priority then number within capacity.
7. Every `update_every`, or at once when a local command wrote `<root>/.taskq/update`: the self-update check (§ 8); an installed service applies a newer version, others only report it. The outcome goes to the log.
8. Sleep until a poke or `poll` seconds.

- Filter: `host-*` absent or this host; workers use `run-*` when present, else a `prefer-*` runtime with a free slot, else the runtime with the most free slots (first listed on a tie), so any-runtime tasks alternate; `run-*` wins over `prefer-*`, and both `prefer-*` labels are ignored with one log line per pass; reviewers prefer the other runtime than the accepted worker (`claude` ↔ `codex`, `codex-app` → `claude`) with free capacity, falling back to the worker's runtime. Other filters remain: `assignee-only` passes; each `needs-*` in `has` (`needs-gate`: every host of a version with gates, § 7); `codex-app` keeps its §9 opt-in.
- Focus: `taskq service focus all|off|<label..> [--request TEXT]` writes `<root>/.taskq/focus`: `all`, one of the labels or `p0` passes; none or `off` (default) admits nothing, heartbeats and updates go on; capacity reason `focus` and the heartbeat say so. `service install` writes `off` when the file is missing, else keeps it. `--request` keeps the owner's words in `focus.request`; a focus without it removes the file. No arguments: print focus, `has`, labels of open tasks; an agent maps the owner's words to these, asks when unsure, says so when none fits.
- Pause: `service pause` (and the tray's) saves the focus to `focus.paused` and writes `off`; resume restores it. Without a saved focus resume fails and names the labels of open tasks: never `all` by default. Emergency ([E1–E5](docs/design/emergency-recovery.md)): under the § 3 hold the loop still reaps, stops replaced children and beats. A failed liveness read in step 1 keeps the child: `status.json` `kids` `live` `unknown` with its `reason` (else `running`), never `gone`; `hold` names the reason. `service recover` (only under a hold) lists each `doing`/`review` attempt of this host with its liveness from a `status.json` at most 60 s old (else all unknown); a child read running or absent gets the op `gone attempt <id>` with `--revision` (the task's) and `--op-id recover.<N>.<id>`; unknown gets none and blocks relaunch. `--apply` writes the ops through the § 5 dispatcher, one receipt each; step 2 stops fenced children; release admits by focus. Targets: tray control, graceful/force stop, per-project entries, selective resume (E1–E3).
- Poke: a local command touches `<root>/.taskq/poke`; the sleeping service checks its mtime every second. Each pass
  writes `<root>/.taskq/status.json` for `service status`, the tray and DashQ: coreq.md common keys (`update` included), service state, the § 5 snapshot (`tasks` with their § 2 `revision`; a failed pass keeps the last rows with `complete` false), `capacity` (effective limits, gate, admission and reservations), `requests`, `incident`, `agents` (§ 5, probed at most every 5 minutes) and § 8 `access`. The key list is the code: `service_run` in `src/main.rs` and `Service::capacity_json` in `src/service.rs`. Capacity is also published on each sample; missing or over 60 s old capacity reads unknown ([specq](https://github.com/taskqorg/specq/blob/main/engineering/verification.md#unknown-is-never-healthy)).
- Events: a pass appends to `<root>/.taskq/events` a line `<board time> #<N> close|failed|ask|blocked|gone <id>` per task it saw move to closed, `failed`, `ask` or `waiting` since its previous pass (a new task counts from its first state); the id is the attempt current at the move, else the task's last spawn; for `ask` and `blocked` else its last comment, else the issue number; a closed or `failed` task never spawned adds none. `gone`: per trusted `gone attempt <id>` log entry newer than the previous pass (the first pass adds none). One line per attempt and kind; lines older than 30 days drop. The first line `since <time>` is the first time covered (`events_since`); a restart keeps the file, moves while no service ran are missing. `ponytail:` no board replay. `ponytail:` files, no socket or pipe, on every OS.
- One service per root and host name: `service run` waits while a `status.json` under 60 s old names another live pid; a pass that finds this host's heartbeat under `ttl` naming another `service <id>` writes nothing and fails with `another service <id> runs as host <name>`. Restart: rebuild from the board; former children are not adopted (except the § 8 re-exec), their attempts are `gone`. `service restart` writes `<root>/.taskq/restart`: the next pass re-execs (§ 8 step 3).
- Tray (macOS, Windows; layout, routes and platform packaging: [menu specification](docs/design/menu.md) M1–M14): one per host. Any installed service starts `releases/<current>/taskq tray` when the heartbeat `<install>/tray` (the tray's pid) is older than 30 s; a tray that finds another fresh pid there exits, as does a tray on another version than `<install>/current`. It lists the projects of `<install>/projects` and reads each `<root>/.taskq/status.json` and `events`: no board, no token. Icon: the compact q with ▶ when a project admits, Ⅱ when none does, gray when all are paused; macOS may instead show Summary or a saved Custom icon ([square summary](docs/design/icon-summary.md), [custom icon](docs/design/custom-icon.md); Windows: compact only, menu M1), both drawn by one renderer (`src/icon.rs`) over a versioned configuration; an invalid saved Custom falls back to Summary. Writes name their target first: pause/resume per project and over all after a confirm naming each project and its effect; resume without a saved focus offers the project's labels and writes the pick; per project log, folder, restart, stop until the next logon, and uninstall after a confirm naming it. `Edit limits` writes only after a confirm naming project, host, old → new and `Running tasks continue`, and shows `Applied` only when `status.json` reads the values back. `Update now` shows when a `status.json` names an `update`: it writes that project's `<root>/.taskq/update` and reports success only when a `status.json` reads back that version. History (M6) is built from `events` only. Agents (M3) shows the § 5 `agents` probe, read-only. Resources opens btop in its own OS terminal window, never inside the menu; missing btop is installed first with the OS package manager, unelevated (M9). Notifications (M14): native OS notifications of new `events` lines, per kind and project as M14 sets, at most once per event. Tray settings, cursors and open-task titles persist in `<install>/tray.json`. `taskq tray --snapshot DIR [--route R,..]` writes the icon PNGs and popover snapshots of the current state in both themes, then exits; an unknown route is refused (routes: M8); the capture window stays off the visible screen where the OS allows and takes no focus.
- AI requests ([menu specification](docs/design/menu.md) M7, M10; [AI workspace](docs/design/ai-workspace.md)): the tray writes `<root>/.taskq/requests/<id>.json` (`text`; `after`: the request it clarifies) into the first registered project with a fresh `status.json` and pokes it. Its service runs one operator (R3) turn at a time per project on the first CLI runtime with a nonzero limit; replies keep the recorded runtime/session. An unavailable continuation fails explicitly, without replaying side effects; the brief on stdin embeds pinned specq (§8), the active project contract, every registered project's path, `status.json` and focus, the request and this answer contract: one JSON `{kind: result|clarify|proposal|refuse, text, ops}`. The service writes `<id>.answer.json` (`state` running, result, clarify, proposal, refuse, failed, applying, applied or `apply failed`; `rev` +1 per write). A `proposal` holds only allowlisted ops on registered projects, else it is `failed`: `focus` (labels, request), `pause`, `resume`, `add` (title, goal, acceptance; a repeated item takes its first copy's op id), `answer` (task, option or text), `later`, `requeue` (task, text); no value starts with `-`. Confirm writes `<id>.confirm` with the `rev` shown; only a `proposal` at that `rev` is applied, once: each op runs its `taskq` command in its project with `--json`, `--op-id <id>.<rev>.<k>` and the task's `revision` from `status.json` at proposal time; the answer keeps each receipt; `applied` only when the focus file or the command's board re-read shows every op, else `apply failed` per op naming its receipt reason. After a crash, recovery turns `running` into `failed` with partial effects unknown, never automatic replay; the newest 20 requests stay. Draft and command history (M7) live in `<install>/tray-requests.json`. An operator failure reports possible partial effects; reconcile before retry. Tools run in the project root, output stays in requests, and no fixed-duration timeout kills authorized work. Service update/restart waits for running operator turns; existing CLI children retain §8 handover. Add project (M10): the OS folder picker (cancel changes nothing). A taskq project (`taskq.json`, `selftest` passes) gets `service install` after a confirm naming the folder, installed once `<install>/projects` lists it; an old one (`selftest` fails) shows its first error line and a § 9 link and writes nothing; a new folder (empty or a Git root) or one with files and no Git offers `Set up with AI…`: a request with `onboard` = the folder (absolute, existing), whose operator gets the service's § 6 inspection (M10; failed reads stay unknown) and may propose only one `setup` op (board, host, `owner/name`, create, visibility default private, publish), never over an existing `taskq.json`. The proposal lists every effect in order (git init, repository creation as the named account, origin remote, `taskq.json`, labels, `service install`) for the confirm; apply refuses when the effects changed since; `applied` only when `selftest` passes there and `<install>/projects` lists it. Owner comment: a comment by a trusted author on a task in `ask`, after its card, that is no log entry and names no option (§ 2), becomes once per comment id (listed in `requests/comments`; past its bound only ids no longer eligible go) a request with `task`, `comment` and the issue link; the tray shows the link. Its proposal holds one `answer` (option or text), `later` or `requeue` op on that task, else it is `failed`; a close only through an option that starts with `close` (§ 2). The owner confirms it in the tray like any proposal. Request log: `<root>/.taskq/requests.log`, one JSON line `{at, source, task, text}` per request, `at` in unix seconds: the service adds each tray request (`tray`) and owner comment (`comment`) when it first answers it, the CLI each accepted `ask` card, `answer` and `requeue` (`answer`, `requeue`); PM proposals are the `- YYYY-MM-DD <text>` lines of the [use cases](docs/use-cases/README.md#proposals) Proposals section (`pm`), read at retro time. Bound: the newest 500 lines (`data::REQUEST_LOG`); pruner `retro::append` on every append, under `requests.log.lock`. Lines are kept verbatim: a missing log reads as empty; an existing empty, unreadable or corrupt log reads unknown with its reason, and the file stays.
- Incident reports ([design](docs/design/incidents.md): catalog, payload, route and dedup): `incident_reports` (§ 9) is true by default; `false` or env `TASKQ_INCIDENT_REPORTS=off` (tests set it) disables. Setup (§ 6) and the update that ships it disclose destination, public visibility, posting account, payload keys, fallback and opt-out before any send; an existing project without the key stays local. Only a catalog fault reports; consumer, tool, login, config, board-outage, permission and security failures never auto-post. The payload is the design's enumerated allowlist, at most 4 KiB: no project, repository, task, host, user, path or free text; panic text stays in `.taskq/cli-errors.log`. Route: an issue in the release repository (§ 8) through an existing github.com login, label `incident`, never `taskq`; at most one write per report, no reopen, no retry store; otherwise the sanitized report stays in `<root>/.taskq/incidents/<fingerprint>.json`. A report never changes a task, the queue or an exit code and never reports itself. `status.json` `incident` and `service status` show the newest outcome, cached across processes in `.taskq/incident.json`.
- Data ([specq data](https://github.com/taskqorg/specq/blob/main/engineering/data.md#files)): bounds in `src/data.rs`, pruned hourly by the service: `<install>/taskq.log` and `<project>.log` past 4 MiB and `.taskq/cli-errors.log` past 256 KiB keep their newest half; attempt logs the newest 50 plus live attempts; `incidents/` the newest 50; `requests/comments` past 1000 lines the newest half plus comments still eligible; `events`, `requests/` and `requests.log` as above. - Log and board budget (#1009): each service log line is `<UTC time> <text>` (ISO 8601, local clock); a multi-line message (HTTP error body, panic) folds into it. Every process counts its board HTTP requests per operation and, on a rate-limit reply, pauses its board calls until the reset, at most 1 h: calls fail at once naming the reset, the service logs one paused and one resumed line and resumes without a restart (operation names and header rules: [counting format](docs/budget-1032.md#counting-format)). `status.json` `requests` holds the counts, the last `remaining`/`limit` and `paused_until`; the log gets `requests 1h: ..` hourly; `service status`/`list` print `Board requests: <n>/h; ..` (else unknown with reason) and the pause. #988 profiling times operations; this counts requests. CLI processes and workers count and pause alone; coreq update and incident requests are not counted. Sources (#1084): a CLI process with board requests at exit, and the service hourly, append one `taskq-requests {at_ms, source, ops}` line to `<install>/taskq.log` (profile lock and bound). Board access budget (#1011): one board user's 5000 requests/h serve every host, project, service, CLI, worker, PM and DashQ. A service pass costs one open-issue list (github.com: GraphQL, labels only); it re-reads comments only of issues whose `updated_at` moved, writes the heartbeat only on change or past `ttl / 3`, reuses that issue for leases, verifies each label once per process and reads dependencies only for a would-be `ready` task (§ 1). Agent CI waits: § 7 rule 7. Budget alarm: at `remaining` <= 20 % of `limit` the service logs `board budget low` once per reset, and `service status`/`list` and R6 line 1 show `Board budget low: <remaining>/<limit> <resource> until <reset> (<host>); top here: <op> <n>`.

Owner-facing service/tray text follows R7: counts use R6 names/order; task rows are `#N <title>` (title at most 60 characters). Use `Focus: <labels|off>`, `Paused`, `Service: <running|stopped|unknown>`, `Update: <version|up to date|unknown>`; unknown/stale values per [unknown is never healthy](https://github.com/taskqorg/specq/blob/main/engineering/verification.md#unknown-is-never-healthy). Menu action labels at most 32 characters; summary/reason lines at most 160; navigation per the menu design and [D8](https://github.com/taskqorg/specq/blob/main/design/operator-ui.md#principles); CLI lists wrap one project/label per line when needed.
### Profiling (#988)
Follow [shared profiling](https://github.com/taskqorg/specq/blob/main/engineering/profiling.md). Time six operations: `service.pass` (board reconciliation, no sleep), `dispatch` (claim and readback up to runtime handoff), `spawn` (runtime start or resume, its failures included, not child lifetime), `forge.call` (one HTTP request), `update` (check, download, verification), `tray.render` (icon rasterization and native apply, not webview paint). Their budgets stay unknown until owner-approved baselines; profiling never changes admission or task state. Per the [shared agent work](https://github.com/taskqorg/specq/blob/main/engineering/profiling.md#agent-work), the attempt stages `claim`, `start`, `build`, `checks`, `review`, `ask` and `close` (#1147) are always measured too, budgets **unknown**, as `taskq-stage` lines in the same log, lock and bound (the host is the log's own): task and attempt numbers, runtime (`claude`/`codex`/`codex-app`/`other`), duration, outcome (`ok`/`ask`/`retried`/`failed`/`cancelled`/`unknown`), error class (`exit`: a child ended without hand-in; `left-board`/`unreadable`: no hand-in evidence), and for `build`/`review` the context tokens (model input read across the stage's calls, cache included) and call count the runtime logged into the attempt log after launch: Claude usage per assistant message id; Codex `turn.completed` input (calls not reported); a call without usage makes the stage's tokens unknown; `codex-app`, unreadable logs and children adopted across a re-exec (duration too) read unknown with reason; service stages run no model.
Board operations (#1173), always on, budgets **unknown**: each call of the board adapter is one `taskq-board` line with its kind (`list` open issues, `inbox` a task's comment log, `read` one issue, `claim` a `spawn` post, `comment` another post or edit, `label` a label change or label catalog setup, `close` an issue close, `write` an issue create or edit, `publish` the § 7 publication), duration, outcome (`ok`/`failed`), error class and the lowest rate-limit `remaining` after it (none reported: unknown); cached clock, user and label-schema reads are not operations. Queue transitions (model: § Executable behavioral model): one `taskq-transition` line per transition with task, entry id, from and to state, time in the previous state (board seconds between the entries; the first entry's start is unknown), runtime and host of the attempt on either side; the service of that host records it, each service records a move without an attempt (consumers dedupe by task and entry).
All these records hold fixed codes and numbers only (`TASKQ_PROFILE_TRACE=1` adds span ids) in `<install>/taskq.log` under its § 4 Data bound; appends and the pruner coordinate through the nonblocking `taskq-profile.lock`; collection stops as unknown at the bound; an instrumentation failure never fails the operation. Its chain check (R12) races appends against a prune that wins the lock: every retained record is a counted successful append.
`taskq profile` reads the retained log without board access, ranks the six by p95, failure rate and variance, then board operations by p95 with failures and the lowest `remaining`, and queue transitions with time in the previous state, and lists this host's board requests of the past hour by source (§ 4 Sources); corrupt or missing records read unknown, counts cover retained records only; collection completeness, earlier or pruned history and adapter retry or cancellation counts stay unknown; an hour with records starting inside it says partial; agent `gh`, PM chat tools and DashQ are not counted. Last it ranks attempt stages per runtime by p95, failure and retry rate, with count, p50/p95/max, outcomes, model calls and context tokens (sum, k of n known, else unknown with reason); DashQ reads this local report, never the board, for stage data, which holds no task text, secrets or host paths.

- Errors/refusals: `Error: <problem>` then `Next: <action>`; at most 2 lines, at most 160 characters each. A compact error links its complete diagnostic in `.taskq/cli-errors.log`; if saving fails, preserve the diagnostic as raw output (R12).
- Other command acknowledgements: one line naming action and project/version; at most 160 characters. Batch operations: one outcome per item.
- `requeue`, `later`, `failed`: `Reason: <blocker>` then optional `Next: <fix>`; at most 2 lines, at most 240 characters each.
- `answer --text` and `steer`: at most 4 lines, at most 240 characters each; one decision/instruction per line, no invented context.
- `service focus/list/status`: named project, focus, counts, freshness and unknown reason; one field/item per line, at most 160 characters.
- `update`, `cleanup`, setup and `selftest`: one outcome per version/path/check ([Core Write](https://github.com/taskqorg/specq/blob/main/caveman/rules/core.md#write)).
- Help keeps full command syntax; `inbox`, raw service logs/status JSON and original issue/log text are exempt from display caps ([verbatim diagnostics](https://github.com/taskqorg/specq/blob/main/caveman/rules/changes.md#keep-the-source-and-sink-separate)).
- Unused positional arguments are refused before any action: `unused positional arguments: <arguments>`; repeat value flags for multiple items.
- Commands add `attempt $TASKQ_ATTEMPT` when it is set. A command refused by `fold` prints the current state. `TASKQ_ROOT` must contain the current directory when that directory lies in a taskq project (a folder with `taskq.json` here or above), else every command is refused `TASKQ_ROOT <root> is not the project of the current directory <dir>`: a reused session's stale environment never writes into another project.
- `--op-id ID`, `--revision R` (answer, requeue, later, failed, steer, result, ask, close, start, approve; `add`: op id, § 1) write the § 2 fields: a seen op id returns the first receipt, writes nothing; another revision is refused `stale` naming the current one, board unchanged. An entry that a concurrent write beat on readback (other revision, raced op id, ignored) is edited by its writer: `stale`.
- Receipt: `--json` prints one object `{task, op_id, outcome, state, revision, reason, next}`; outcome `accepted` (readback state), `rejected`, `stale` or `unknown` (written, no readback: `Next:` reads `inbox N`, retries the same op id); else the lines above.
- `wait` reads issues updated since the local cursor `<root>/.taskq/pm-cursor` (a cache, R1) and folds those that changed.
- Untrusted text (issue bodies by others, worker output) follows [shared agent security](https://github.com/taskqorg/specq/blob/main/engineering/security.md#agents).

## 7. Worker, reviewer, publication
Worker brief: task text, attempt, branch, delivery commands, this file's path (this release's URL when the root has none), the folder rule (§ 8), the CI-wait rule (rule 7). The task is the owner's grant for this section's commit and publication steps ([shared approval boundaries](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#approval-boundaries)); nothing outside them is approved. Rules:
1. Read this file and the whole issue first, then [prepare the task](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#prepare-the-task): a decision conflict (R13), an untestable or ambiguous Acceptance item or a split (R2) is an `ask` with options before any code.
2. Workspace: `git worktree add -b taskq-<N> .worktrees/taskq-<N> origin/main` (existing branch: continue it). `workspace: external`: the path the project's `AGENTS.md` gives.
3. Owner-only question: `ask` with options, then stop. Cannot be done: `requeue --text`, then stop.
4. Before `result`: commit on `taskq-<N>` with `Task: <issue url>` in the message, rebase on `origin/main`, run the project checks, name each command and outcome in `--checks`. `result` refuses, naming the files, when the diff from `origin/main` changes a `uiSources` file whose blob `docs/shots/manifest.json` at the SHA does not record (fix: `docs/shots/update.sh`); a readable SHA without the manifest: no check; any other Git or manifest failure reads unknown and refuses. Never weaken a check to pass: a changed or deleted existing test or golden trace needs a changed rule in the same diff and is named in `--text`. For fixes, `--checks` records the [shared before/after evidence](https://github.com/taskqorg/specq/blob/main/engineering/verification.md#run-policy-by-stage) or its limitation.
5. Delivery `direct`: push `taskq-<N>`. `auto-merge`, `review-pr`: push and open one PR/MR into `main`. Then `result --sha <sha>`; do not wait for CI, `close` checks it. Research: `--sha` = current `origin/main`, the answer in `--text`.
6. Everything written through taskq is public: no secrets, tokens or local paths.
7. CI wait, worker or reviewer: at most one poll a minute (`gh pr checks <PR> --watch --interval 60`); never `gh run watch`, which polls every 3 s, or `gh run view` without `--json`.

### Result and close verdicts
`result` body: `Changed: <user effect>` (1-2 lines), `Checks: <command -- outcome>` (one line per check, 1-8 lines),
then `Open: <remaining item|none>` (1-2 lines); at most 12 lines, at most 240 characters per line. Keep exact commands and platform qualifications (R12).
`--text` supplies literal Changed and Open lines, then a decision card's Done/Problem lines in the § 2 Ask card format, with `--option`, `--recommend`, `--link` (none: no card fields); `--checks` supplies unprefixed command/outcome lines, each rendered with `Checks:`. SHA stays in the log header; one PR/evidence link may share Changed and carry the [shared risk description](https://github.com/taskqorg/specq/blob/main/caveman/rules/changes.md#merge-request-description-markdown) for either publication route.
`close --text` supplies all three labelled fields in the same order and limits; Checks names each `A<k> ok|gap|unknown` plus exact-SHA CI outcome, not a vague PASS.
Reviewer checks every Acceptance and contract against the candidate and CI on that SHA, waiting per rule 7; `Checks:` follows [shared review](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#review), within the same verdict limits. Requeue only for Acceptance/contract gaps; advisory findings go in `Open:`. Then `close --text <verdict>`, `requeue --text <exact fixes>` or `ask` with options. PM relays the verdict verbatim, links intact.

`close` publication goes through the board API only:
- `direct`: branch `taskq-<N>` equals the result SHA, `main` is its ancestor, CI green on that SHA; move `main` to it
  without force, read back, close. GitLab has no fast-forward ref API: `direct` there merges a fast-forward MR.
- `pr`: exactly one open PR/MR of `taskq-<N>` at the result SHA, current `main` its ancestor (else `requeue`: rebase), CI green on its head; `main` refuses a stale head at merge time (GitHub: a ruleset requiring branches up to date that the token can never bypass, or readable protection requiring it with admins enforced; GitLab: fast-forward or semi-linear merge method), else refuse; mark a draft GitHub PR ready; squash-merge with the title and
  all `Task:` lines; read the merge back; close. Incident ancestry checks in this same close use the returned merge SHA for squash publication, the result SHA for direct publication; later human moves are never read.
- No commit (research, or SHA already on `main`): verify ancestry, close.
- Pending or missing CI: refuse, state unchanged. Failed CI or conflict: `requeue` with the message.
- On the attempt host: remove a clean `.worktrees/taskq-<N>` and its local branch; dirty ones stay.
- Merged, not closed (a partial publication, or a PR/MR into a release branch, which never closes its issue on merge): with no open PR/MR of `taskq-<N>` into `main`, `close` finds the merged one of `taskq-<N>` into any base whose head is the result SHA and closes with that one receipt (`merged #P [into <base>] as SHA`): no second merge, no requeue. From a reviewer's `ask` (result kept) an owner `close` option runs it (§ 2); `doing` or a worker's `ask` has no result to verify: `later`, then `close`.

**Delivery presets** ([agent behavior](docs/design/agent-behavior.md) B1–B5; commit, push, PR and merge, apart from § 8 Access) are § 9 `delivery` `{preset, revision}`, the owner's (R9; the revision +1 per owner edit): `auto-merge` (the `pr` route), `direct`, `review-pr` (the `pr` route after the owner gate below). `local` and `push-branch` are refused until B3 pending-handoff states exist. Without `delivery`, `publish` names the preset at revision 0 (`pr` is `auto-merge`); nothing converts it to `review-pr`, a migration is an owner-reviewed edit. `close` reads the policy then. Its publication receipt is the last verdict line `delivery <preset> r<revision>: <main fast-forwarded to SHA|merged #P as SHA|SHA already on main>`. `review-pr` needs every host at `4.2.0-dev` or newer: 4.1.11 ignores `approve` and publishes it as `auto-merge`.

### Recipes and owner gates
A recipe ([plans and decisions](docs/design/plans-and-decisions.md) P5) is a reusable task list in § 9 `recipes`; its identity is the name and its `version`. `taskq recipe NAME --run ID` adds each task held through the configured create claim (§ 1) in order with op id `recipe.<name>.<version>.<ID>.<k>`, so a rerun returns the first receipts; `deps` become `Depends on #N`, `{goal}` is replaced by `--goal`. A task with `gate: true` also gets label `needs-gate` and a `gate` entry. Nothing starts until every task reads back; then only `--start` or `taskq start N` starts them: the queue runs them like any task, no separate scheduler.
A gated task's or `review-pr` project's reviewer that finds the result otherwise done asks with options, Done naming task fit and CI on that SHA, the first `approve <sha7> and close ★`; an owner pick (§ 2) or `taskq approve N` binds the gate to that result, the reviewer then closes. A new result needs a new approval; a stale or missing one makes `close` refuse before publication. Tasks that `Depends on` the gated one wait for its close.

## 8. Runtimes and deployment
**Access (R9).** `<install>/worker-policy.json` is operator-owned: `revision` (+1 per write) and `grants`, each `runtime`, preset `mode`, scope (`project` root, else host default; a project grant replaces the default there) and provenance (`by` OS account, `at`). Presets: `restricted` writes runtime homes, user caches, OS temp and `<root>/.taskq`; `workspace` also `<root>`; `full` turns the runtime sandbox off on start and resume (Claude `--permission-mode bypassPermissions`; Codex `-s danger-full-access` without other sandbox options, model and effort kept). Each start and resume resolves requested (`taskq.json` flags) and effective access; `service permissions` and `status.json` `access` show both. No grant: legacy flags run unchanged, never recorded as a grant. Every mode but Full keeps `<install>` (policy, token, releases), `PATH` directories, the runtimes' package directories and `.codex/*.toml` out of worker writes. Enforcement: macOS a taskq Seatbelt profile; Linux Codex Restricted/Workspace the `taskq-sandbox` launcher ([setup and boundary](docs/design/linux-sandbox.md)) and an explicit project grant; Windows Codex Workspace an explicit project grant and the pinned native candidate ([qualification matrix](docs/runtime-qualification.md)); per-platform boundaries in [shipped enforcement](docs/design/worker-permissions.md#shipped-enforcement). Windows Restricted, read-only narrowing and network-denied requests refuse until qualified; no Full retry or working-installation migration. Unknown enforcement refuses before claim or resume, with the reason in `capacity` `reasons`: unreadable policy, missing launcher prerequisites, no Linux grant, or other OS/runtime without enforcement. Full on the same host and user is uncontained: its worker can edit the policy. Other modes close direct writes only: user autostart, shell or runtime settings and repository Git config or hooks a worker plants and that later run outside a sandbox (the service's own `git` included) stay a same-user path. `service permissions` writes outside a worker only (refused under `TASKQ_ATTEMPT`); a board answer never grants. Changes apply to new starts and resumes. Rollback floor `4.2.0-dev`: with any grant or an unreadable store the service and a grant write set an older `previous` to the running version; a release that fails health then stays down, nothing admitted, for the operator. A manual downgrade below the floor is the operator's and runs legacy flags ([procedure](docs/design/worker-permissions.md#rollback-floor)).

1. Hosts need no git, gh or toolchain. Each release runner runs `selftest` on its staged artifact before publishing. Windows releases use MSVC's static WebView2 loader; GNU `service install` copies the loaded `WebView2Loader.dll` beside both release and launcher before activation. Checksums and provenance follow [release rules](https://github.com/taskqorg/specq/blob/main/engineering/release-contract.md#rules) and [security](https://github.com/taskqorg/specq/blob/main/engineering/security.md#dependencies-and-releases): each binary and `SHA256SUMS` carry a GitHub build provenance attestation (`gh attestation verify <file> --repo taskqorg/taskq`); installers and update keep the checksum check.
2. `taskq update` and service step 7 run the coreq update. A new `current` then gets one allowlist sweep of the rest of `<install>` and a `~/.local/bin/taskq` v3 python shim. Kept: `releases/` of `current`, `previous`, the running version and each `projects` root's `status.json` version (its service and live children), `current`, `previous`, `projects`, `token`, `installation-id`, `connection/` ([DashQ connection](docs/design/enrollment.md)), `worker-policy.json`, `windows-native/`, the launcher, `WebView2Loader.dll`, `taskq-tray.exe`, `*.log`, `tray*`, `capacity/`, `resources/`, `TaskQ-*.xml`, `*.tmp`. A file in use stays until a later update.
3. At step 7, an installed service whose running version is older than `current` logs `current is <v>; restarting` and re-execs through the launcher without downloading or running selftest. The service re-execs; live CLI children pass to the new image through `<root>/.taskq/kids`. An active Claude, codex-app or operator turn defers re-exec until it ends; the restart request remains pending. Windows: exit 75 once no child is live; the coreq launcher restarts it. A pending restart skips update checks, logs `restart to <current> waits for #<N>, ..` once per changed set and lists it in `status.json` `restart_waits` (null when none) and `service status` `Restart: waits for ..`.
4. The service marks its version `healthy` after `rollback_after`. Children keep running from their own release folder: no drain, no manual resume, no blocked user command.
5. `service install` installs its binary (coreq `install_self`) as a new file, never over an existing release binary in place: macOS kills every later start of a rewritten binary (`OS_REASON_CODESIGNING`), and three such starts roll the release back. It then writes and loads the unit; while the project's fresh `status.json` lists live children (or is unreadable) it writes `<root>/.taskq/restart` instead of reloading, so they pass over as in step 3. Windows `stop`/`uninstall` and a reloading `install` also end the service process tree; stopping a child ends its process tree (`taskkill /T`). On Windows run setup outside an MSIX app (e.g. Claude Desktop): its AppData writes are private, the task sees neither binary nor `gh` login. The unit's coreq launcher counts unhealthy starts per project, so one project's crash loop rolls back `current` and starts of other projects do not count. macOS signing (#1089): with the login-keychain identity `TaskQ Local Signing`, `service install`, an update and the tray sign as `org.taskq.taskq` so one TCC grant matches every later release; without it, or on a failed signature, they stay ad-hoc and the log says so ([procedure](docs/design/worker-permissions.md#macos-signing-identity)).
**Compatibility N/N-1.** v4 releases differ only by additive log kinds that N-1 can ignore without a different fold. A change that N-1 cannot ignore needs a cutover like § 9. N-1 reads op id and revision lines as text (its cards and deliveries show them). N-1 ignores `gate` and `approve`, so it would close a gated task: `needs-gate` keeps its services from spawning workers or reviewers for one, and an N-1 operator's `close` stays the owner's own act. N-1 parses only `Depends on #N`, so it would start a task waiting on `Depends on <repo>#N` (§ 1): until every host of the board runs a version with it, that line goes only into a held task (`add --hold`), started after (CHANGELOG **Board**). Hosts update independently in any order. A version whose `selftest` fails is not published.

## 9. Config and cutover
`taskq.json` beside the project root:
- `board` `github|gitlab`; `repo` `owner/name`; `host` the board's web host (default `github.com`, `gitlab.com`).
- One module per board under `src/board/` (`github.rs`, `gitlab.rs`): its API, token lookup, login probe, CLI, env and default host. The `Board` trait and `src/board/mod.rs` (shared HTTP, registry by name) are the only contract; core, service and operator never branch on the board kind, and editing one board never touches another's module.
- `label_schema` `canonical|legacy` (absent: legacy if the board has `priority-1|2` or `q-waiting` objects, else canonical). Both names work in priority and focus/status filters; `p0` has no legacy name; logs keep `waiting`. Canonical writes on existing boards need all-host compatible release/idle approval; legacy objects and closed issues stay, only open issues are reassigned.
- `publish` `direct|pr`, `delivery` (§ 7); `workspace` `external` keeps host-owned worktrees.
- `hosts` `{hostname: name}` (env `TASKQ_HOST` overrides); `has` `{name: [x..]}`; `limits` `{"claude": n, "codex": n, "codex-app": n}`.
- `add --prefer codex|claude` writes one soft `prefer-<rt>` label ([specq runtime preference](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#runtime-preference)); two values or another runtime are refused; workers take it only while that runtime has a free slot here (§ 4 Filter). Opt-in `codex-app` (macOS, Windows): only on hosts whose `has` lists it, only for `run-codex-app` tasks (`add --runtime codex-app`); reviewer chain checks keep app-worker cases on macOS and Windows and none elsewhere. A screen task adds `needs-screen` (`has` `screen`). macOS evidence tasks: [runtime qualification](docs/runtime-qualification.md#macos-evidence-tasks). Answering a real ask stays the owner's act.
- `capacity_hosts` `{name: {"limits": {..}, "load_gate": {..}}}`: partial `limits` override the top-level ones for that host; a host `load_gate` replaces the top-level `load_gate` object; omitted gate fields are `enabled` false, `cpu_max` 85, `memory_min` 15. Valid: limits 0..u32::MAX, `cpu_max` 10..100, `memory_min` 1..95, integer percent. `admission` `{"mode": "auto"|"fixed", "max": n}` (a host's replaces the top-level one; absent: fixed; setup (§ 4 Add project) writes auto): auto turns the gate on with the [D03](docs/design/admission-calibration.md) defaults `cpu_max` 90, `memory_min` 10 and CPU as the 60 s mean, a 100 % latest interval vetoing, memory floor max(`memory_min` %, 2.5 GiB) and macOS pressure level >= 4 holding; given gate fields override them; `enabled` false is invalid. Absent keys keep today's behavior; nothing migrates or enables itself; old binaries ignore these keys, so use them only on hosts with a compatible version.
- `recipes` `{name: {"version": V, "tasks": [{"title", "goal", "acceptance": [..], "scope", "deps": [earlier 1-based index..], "gate", "type", "runtime", "priority", "host"}]}}` (§ 7).
- `permission_mode`, `codex` (R9); `incident_reports` `true|false` (§ 4); `pages` link wrapper base; `assignee` (login or `me`) report filter.
- `ttl`, `poll`, `update_every`, `rollback_after`: seconds, defaults 300, 60, 900, 600.
- GitHub token: one owner-installed credential per host in `<install>/token` (0600 on Unix; owner-only access on Windows), shared by service and workers; an existing OAuth token is accepted, a fine-grained PAT preferred. No env or CLI-login fallback; TaskQ, workers and setup never run `gh auth login`; a missing, empty or unreadable token is an owner item with the same error in service and worker. Never in config. GitLab keeps coreq token lookup and `Authorization: Bearer`.

A cutover is one step per project, not per host: two board formats do not mix. No migration code: `CHANGELOG.md` says per release what changed on the board and what an open issue needs. An agent reads the entries from the board's version to the new one, prints a plan per open issue and collects its questions (issues the new format cannot hold) for the owner, one by one or all at once. After the owner's OK, with every old service stopped and no old children, it applies the plan with `taskq` commands and issue edits. Closed issues are never touched. New services start: Mac, then Windows. Repair is the same agent procedure for one project; it warns when `status` shows another host's fresh heartbeat.
