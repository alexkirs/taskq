# План рефакторинга taskq: ревью handoff и порядок работ

Дата: 2026-10-12. База: `origin/main` 6a90b11 и ветка `deploy-artifact-pipeline` ebf0d8f
(`docs/deployment-handoff.md`). Это план и замечания. Код и доска не менялись.

## 1. Диагноз в пяти пунктах

1. **Код и спек раздуты в 25 раз за 7 дней.** `taskq.py` в первом коммите (2026-10-06) имел
   296 строк. Сейчас 7589 строк. `taskq.md` вырос до 2869 строк, внутри около 30 блоков
   «owner decision» и истории «Changed: old → new». Всего 514 коммитов и 208 PR за неделю.
   Логика при этом примитивная: задача, состояние, исполнитель, событие.
2. **Деплой сложен из-за модели, а не из-за кода.** Релиз — это Git-checkout. Поэтому на
   каждом хосте нужны `git`, `gh`, обход CRLF, проверки ancestry и blob-хешей. Сверху
   ручной qualification JSON, ручная публикация `qualified_hosts`, ручные чекпоинты
   (`claim --checkpoint`, `migrate --controllers-stopped`) и ручной resume. WIP-ветка
   добавляет ZIP, но внутри снова собирает Git-репозиторий из bundle и ходит в сеть
   (`taskq_release.py:165-174`). Это тот же clone, только длиннее.
3. **Нет горячей замены.** Сервис в паузе не видит смену pointer (`host_service.py:460-471`).
   Активный сервис видит её только после прохода, потом выходит и ждёт, что его
   перезапустит LaunchAgent или Scheduled Task, созданные руками вне репозитория. Дочерний
   проход смешивает старый `host_service.py` с новым `taskq.py`. Автообновление на границе
   launcher ставит релиз синхронно и **отказывает** в исходной команде пользователя.
4. **Три леджера мощности и вечные holds.** Слоты лежат в JSON задачи, в anchor issue доски
   и в host SQLite. Один запуск воркера (`owned_model_turn`) — это 7 записей в 3 хранилища
   без отката. Сейчас висят гранты закрытых задач 706–715. Правило «не снимать без
   доказанного fencing» плюс отсутствие fencing дают вечную блокировку.
5. **«Board-only» пока декларация.** Локально живут пять SQLite (capacity, registry,
   dispatch-owner, pm-receipts, arm-runtime) и PID/log-эвристики живости. Epoch-gate
   сервиса решает, может ли tick вообще что-то запускать.

## 2. Что делать иначе (замечания к системе)

### 2.1 Релиз — это файл с хешем, а не Git

- Артефакт = готовый к запуску файл + `sha256` + подпись. Без bundle, без `git init`, без
  `fetch origin` на хосте.
- Проверка на хосте = sha256 и подпись ed25519 по ключу, вшитому в предыдущую версию.
  Ancestry, blob-хеши и CI-статус проверяет **один раз** CI при сборке, не каждый хост.
- Из runtime хоста уходят `git` и `gh`. Удаляются `verify_release`, `qualified_checks`,
  `qualified_publication`, `release_repository`, fixture-машинерия, обход CRLF.

### 2.2 Без кластерной атомарности: каждый хост тянет обновление сам

- Фазы campaign «preflight all → stage all → activate only all ready» удалить. Без
  транспорта между хостами (TCP22 закрыт) они нереализуемы. Протокол с совместимостью
  N/N-1 делает их ненужными.
- Правило совместимости: версия N читает данные доски N-1 и пишет N. Версия N-1 читает N
  или безопасно отказывает в записи, но не ломает задачу. Тогда хосты обновляются
  независимо и в любом порядке.
- Реестр хостов не нужен. Хост существует, если его сервис пишет на доску heartbeat с
  версией. Это и есть fleet status «кто на какой версии».

### 2.3 Горячая замена по принципу супервизора

```
releases/<version>/taskq[.exe]   неизменяемо
current                          pointer, атомарный rename
```

Цикл сервиса между проходами (и в паузе тоже):

1. Прочитать `latest.json` релиза (URL + sha256 + подпись).
2. Новая версия: скачать в `releases/<v>.tmp`, проверить хеш и подпись, переименовать.
3. Smoke: `releases/<v>/taskq selftest` (импорт, конфиг, чтение доски, без эффектов).
4. Сменить pointer и сделать re-exec себя (Unix `execve`; Windows: запустить новый,
   выйти, OS-юнит страхует).
5. Новая версия падает в первые K минут: вернуть pointer назад автоматически.

Воркеры — отдельные процессы. Они доживают на своей неизменяемой папке. Дренаж, пауза и
ручной resume не нужны. Ручной путь `taskq update` остаётся одной командой, делающей те
же шаги 1–4.

### 2.4 Сервис — единственный, кто спавнит и считает мощность на хосте

- Воркер и ревьюер = дочерние процессы сервиса. Живость = `wait()` родителя, а не
  PID/birth, логи и `libproc`/`/proc`/kernel32. Удаляется весь блок process identity
  (около 300 строк, по три реализации).
- Мощность хоста = конфиг-лимит минус живые дети. Без SQLite: после рестарта сервис
  пересчитывает её по живым процессам. Проектного лимита нет (D8).
  Три леджера сводятся к одному.
- Fencing вместо вечных holds. Каждая попытка получает `attempt` (generation). Запись на
  доску принимается только при совпадении `attempt`, иначе это устаревший писатель и
  запись отклоняется. Захват задачи — это lease с TTL и heartbeat от сервиса. Lease
  истёк: задача свободна, старый писатель отфенсен по generation. Это закрывает
  «unknown writers» по построению.

### 2.5 Брокер сообщений = сервис + доска, без внешнего MQ

- Долговременное хранилище — события в issue (уже есть). Redis/NATS не нужны.
- Адресация `task#attempt`, а не строки `role:runtime:session` (workstream 3).
- Сервис хоста — единственный маршрутизатор. Он доставляет события своим детям (resume
  сессии) и локальным подписчикам через poke-файл (`taskq wait`, PM-адаптер). Между хостами
  связь идёт через доску.
- Авторитет очереди не зависит от PM-чата. Нет PM — событие лежит pending на доске.
  `wait --pm` (опрос раз в 25 с) и внешний sender уходят из критического пути.
- Ревьюер запускается по требованию как обычный ребёнок сервиса, а не висит как `S<N>`.

### 2.6 Никакого shell между нами и процессами

- Брифы передаются через argv и файл, не через PowerShell-обёртки hex/base64. Это убирает
  все падения PR719 на Windows (ShellBriefs timeout, BOM) вместе с их причиной.
- `no_window()` (32 места) и `powershell()` (8 мест) удаляются.

### 2.7 Язык: Rust для нового ядра (D6)

Python сам источник фрикции деплоя. Rust её убирает:

| | Python сейчас | Rust |
|---|---|---|
| Рантайм на хосте | нужен Python ≥3.9; на Windows берётся чужой из `.cache/codex-runtimes`, Store Python ломается | не нужен, один бинарник |
| Сборка | нет, релиз = исходники + Git | один workflow на тег: 3 нативных раннера, один `checksums.txt` |
| Обновление себя | launcher + pointer + alias в `$PROFILE` | замена файла + re-exec; Windows позволяет переименовать запущенный exe |
| Процессы и IPC | ctypes под 3 ОС, ~105 строк SID/DACL | `std::process`, файлы `<root>/.taskq/poke` и `status.json` |
| Внешние зависимости | git, gh, sqlite3, PowerShell | ноль на хосте |
| Модель состояний | строки и словари | `enum` + `match`: компилятор требует обработать каждое состояние |

Правила, чтобы Rust остался компактным и быстрым в сборке:

- **Без async.** Сервис делает десятки запросов в минуту. Хватает потоков и блокирующего
  HTTP. Никакого `tokio`.
- **Минимум crates:** `serde` + `serde_json`, `ring` (sha256, ed25519). HTTP через
  системный `curl` (macOS, Windows 10+, Linux): `ureq`+rustls дал 47 crates. Сокета нет:
  poke-файл на всех ОС. `libc` (уже в дереве `ring`) только для `waitpid` после re-exec. Без
  `self-replace` (лаунчер). CLI вручную. Цель: ≤40 crates в `Cargo.lock` (сейчас 31).
- **Один crate, модули внутри.** Workspace не нужен.
- **Сборка на нативных раннерах** (`ubuntu`, `macos`, `windows`) в одном workflow, а не
  кросс-компиляция. Кэш `Swatinem/rust-cache`. Тесты и smoke идут на тех же раннерах.
- `opt-level="z"`, `lto=true`, `strip=true`: бинарник 3–5 MB.

Оговорка: бинарников будет три (по ОС), но исходник один, тег один и workflow один.
Сравнивать поведение Win/Mac/Linux больше не нужно.

Условие: переписывать **упрощённую** модель, а не 7.6k строк. Сначала спек ≤300 строк
(фаза 2), потом ядро по нему. Цель: ядро ≤2.5k строк Rust.

### 2.8 Разделение кода

```
src/main.rs       CLI: add, answer, close, status, inbox, ack, wait, update, service
src/core.rs       модель: состояния, события, переходы, fencing; чистые функции, без I/O
src/board.rs      адаптер GitHub/GitLab issues (лог `taskq:`-комментариев, D8)
src/service.rs    супервизор: lease, спавн, мощность, маршрутизация, self-update
src/runtime.rs    claude, codex (hermes удалить или вынести)
src/platform.rs   3 шаблона OS-юнита (plist, schtasks XML, systemd user unit)
```

OS-специфичный код живёт только в `platform.rs`. Это около 100 строк шаблонов и
`taskq service install`. Файл разбивать на папку, только когда он перерастёт ~800 строк.

- Историю решений оставить в git и issues. Операционное состояние (холды, epoch, хосты)
  убрать в handoff. Инцидент-лог `docs/supervisor.md` §9 (~400 строк) убрать в архив.
- Статус 2026-10-12: сделано. 297 строк; handoff в `docs/handoff.md`; документы v3 в `docs/legacy/`.
  Тест в `src/core.rs` держит лимит 300 строк, запрет дат и покрытие таблицы § 2 golden-трассами.

### Фаза 1. Минимальный рабочий деплой на текущем Python (M) — отменена

Статус 2026-10-12: Rust v4 (фазы 3–4) уже даёт release, update, лаунчер и `service install`.
Мост на `.pyz` выбросили бы при cutover, поэтому он не строится. v3 заморожен (только

Цель: выпускать версии без ручных шагов, пока идёт переписывание. Это мост, а не финал.

1. CI на теге: одна сборка `taskq-<ver>.pyz` (zipapp) + `sha256` + ed25519-подпись,
   публикация в GitHub Release. Три ОС гоняют один и тот же `.pyz` в `selftest`.
2. `taskq update`: скачать, проверить хеш и подпись, положить в `releases/<ver>/`,
   сменить pointer. Без Git, без qualification JSON, без `gh`.
3. Сервис: проверять pointer между проходами **и в паузе**, делать re-exec. Детский
   проход запускать целиком из выбранного релиза (`host_service.py:362` сейчас берёт
   старый файл).
4. Убрать автообновление, которое блокирует команду пользователя (`taskq.py:7574-7578`).
5. `taskq service install`: сгенерировать LaunchAgent, Scheduled Task, systemd user unit.
   Ручные юниты на Mac и Windows заменить сгенерированными.
6. Одноразовая миграция Mac capacity (недостающие измерения task/supervisor) скриптом
   при остановленном сервисе. Каркас миграций не строить.

Готово, когда: тег превращается в обновлённые Mac и Windows без ручных команд; новая
версия на одном хосте не ломает задачи на хосте со старой.

## 6. Риски

- **Переписывание затянется.** Мост фазы 1 позволяет работать на Python сколько нужно.
  Rust-ядро начинать только после спека ≤300 строк.
- **Скорость итераций агентов на Rust.** Без async и с малым числом crates `cargo check`
  идёт секунды. Модель держать в `core.rs` чистыми функциями: её проще всего тестировать.
- **Снятие holds без fencing.** Снимать только гранты задач, закрытых на доске, и только
  при остановленных сервисах обоих хостов. Новые holds уже защищены `attempt`.
- **Совместимость N/N-1 нарушена.** Новая версия, не прошедшая `selftest` против
  записанных фикстур доски v3, не публикуется.
