# taskq contract
taskq runs a queue of agent tasks on a GitHub or GitLab issue board. This file is the contract: states, log, roles, lease and fencing, compatibility, deployment; a linked `Contract detail` section of a docs page holds moved detail with the same authority. Decision history lives in git and issues; operational state on the board (R1).
This file specifies **v4**, the Rust binary from `src/`.
## Principles (R1–R13)
### Change rule
A task that changes a rule names its R-number, edits this file in the same deliverable as the code and lists the amended R-numbers in its result. A changed rule keeps its number; a new rule takes the next. A disagreeing rule elsewhere is a defect. No history here: no dates, no decision logs; size bound: R8.
### R1. The board's own objects are the only state
No machine block in issues. State is what a person sees: labels, the issue text, `taskq:` comments (§ 2) and host heartbeat issues (§ 4). The comment log is the truth; labels project it. Local files are caches a restart rebuilds: no local DB, receipt store, queue or lock. Exceptions hold no task state: [DashQ connection state](docs/design/enrollment.md), the § 3 admission and hold files, the § 4 request, incident and profile files, the host operator's [resource grants](docs/design/shared-resource-controls.md#host-adapter) (`resources/`). A fresh `status.json` `pid` is the one-service-per-root check (§ 4), not a lock.
### R2. One task, one attempt
A task has at most one live attempt: one worker or one reviewer process. Work bigger than one reviewable diff follows [shared task preparation](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#prepare-the-task) with tasks linked by `Depends on #N`. A live attempt never moves to another host or session; a new attempt replaces it (§ 4).

### R3. Roles
- **Owner**: decides product questions, answers `ask`, accepts or rejects results through the PM.
- **PM** (manager): the agent session the owner talks to. Files tasks, relays questions and outcomes; does no task work, never answers for the owner. The queue never needs a PM online.
- **Service**: one per host (§ 5); the only process that spawns workers, reviewers and operators.
- **Worker** `T<N>`: a service child; does one attempt, writes `result`, `ask` or `requeue`.
- **Reviewer** `R<N>`: a service child spawned on demand for a result; checks the exact candidate, then `close`, `requeue` with fixes, or `ask`. No resident supervisor session.
- **Operator**: the owner-facing agent for project research, edits, checks and TaskQ operations (§ 4), with the workers' runtime tools and project permissions (R9); authority per [shared approval boundaries](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#approval-boundaries). Task-state writes use TaskQ commands. Its failure fails no worker task and proves no absence of side effects.

Session names: `T<N> <title[:40]> (<host>)` and `R<N> <title[:40]> (<host>)`.

### R4. Comments move the queue
Each task-changing command appends one `taskq:` comment, sets the projected labels and pokes the local service; services also poll the board every `poll` seconds. No sender session, timer or PM chat is on the critical path.

### R5. Completion is written to the task
Result SHA, checks, questions and blockers go to the issue as `result`, `ask`, `requeue` comments; completion evidence follows [specq verification](https://github.com/taskqorg/specq/blob/main/engineering/verification.md).

### R6. Human report
`taskq status` renders the [read-model](docs/design/refactoring-backlog.md) snapshot of one board read (§ 5 `--json`; service status, `status.json` and tray count the same rows), in this order, empty parts omitted; tray and browser rows reuse [shared project blocks](docs/design/project-blocks.md).
1. `<project> · [board](<url>)`, preceded by `Rate limit: board requests paused until <time> (<host>)` while a `status.json` under 60 s old reports a pause, else by the § 4 low-budget line, also when this read fails.
2. `In work N · Waiting for answer N · Ready N`: `doing` + `review`, `ask`, `ready`.
3. `| Task | State | Runtime | Session |`, one row per open task except `ask`, `later`, `failed`, by priority then number; task and session cells link; `waiting` rows read `blocked ([#M](url) open)` per blocking dependency (§ 1), `open` or `unknown: <reason>`; `--json` rows add `blocked` (`ref`, `url`, `reason`).
4. `Questions (answer N.M):` and `| Question | Brief reason | Options |` with `N.1 <option> · N.2 <option> ★`, one row per `ask` and per `review` with options; an owner action (§ 2) reads `waiting for owner: <action>`.
5. `Later: [#N title](url), ...` on one line; then `Failed:` with a reason table.
6. `Hosts: <host> v<version> <age>[ focus off|unknown], ...` from heartbeats (§ 4).
7. `Next: 1 <action> ★ · 2 <action>` from the PM ([shared Next contract](https://github.com/taskqorg/specq/blob/main/design/workflow.md#ai-assisted-controls)).

Titles ≤ 60 characters, reasons ≤ 160, options ≤ 120, then ellipsis and an issue link; every row, option, count and answer token stays. Cells: newline becomes space; `|`, `[`, `]`, `\` are escaped. Claude links use only the Remote Control URL the session registered. Codex links: `codex://threads/<id>` when `TASKQ_CLIENT=codex`, else `<pages>/open.html#codex://threads/<id>`.

### R7. Style
Follow [specq Core](https://github.com/taskqorg/specq/blob/main/caveman/rules/core.md) and its profile; project documents follow [Documentation](https://github.com/taskqorg/specq/blob/main/caveman/rules/documentation.md) in English. CLI outcomes share one success/error renderer; a failed batch item keeps its task number. Limits count logical lines and Unicode characters, labels and numbering included, blank separators and the log header excluded; link targets and exact commands, SHAs and paths are exempt from character limits. Commands refuse over-limit input before writing, naming the excess; stored text stays verbatim ([source and sink](https://github.com/taskqorg/specq/blob/main/caveman/rules/changes.md#keep-the-source-and-sink-separate)).

### R8. The contract is the SoT and matches code
Apply [shared spec-first rules](https://github.com/taskqorg/specq/blob/main/engineering/spec-first.md): code and contract ship in the same release (§ 8); every § 2 table row has a golden trace; the § 8 size bound holds.

### R9. No silent changes to model, effort or permissions
Name any change to the owner first. `permission_mode`, `codex` and capacity (§ 9) in `taskq.json` are the owner's: agents propose capacity and apply it only on the owner's explicit instruction. Worker access comes only from operator-owned grants (§ 8 Access; [worker permissions](docs/design/worker-permissions.md); [permission authority](https://github.com/taskqorg/specq/blob/main/engineering/permission-authority.md)); config, task text, labels and board answers may request or narrow access, never grant it. Legacy defaults (requests): Claude `--permission-mode dontAsk`; Codex `-s danger-full-access`. The operator uses the workers' CLI permissions, § 8 Access and the host board environment: no override, silent elevation or fallback. Setup external effects need § 6 confirmation.

### R10. Multi-project only by explicit list
A PM manages several projects only from an owner-written list; folders are never discovered. One report per project. An `N.M` answer that could match several projects needs the project named first.

### R11. Retire sessions only after their attempt ends
A worker or reviewer stops only when its task is closed or parked or its attempt is replaced (§ 4). Identity is the recorded native session ID, never a name match; a Claude background turn stops after native completion readback, a CLI child after its log shows the turn ended (§ 4 step 1), each keeping its conversation. Uncommitted work is never lost: only `cleanup --force` removes it, after saving `<root>/.taskq/trash/taskq-<N>.patch`.

### R12. Unverified means unknown
Follow [shared verification rules](https://github.com/taskqorg/specq/blob/main/engineering/verification.md). Chain checks are `cargo test --locked` and `taskq selftest`, both in CI. The [runtime qualification matrix](docs/runtime-qualification.md) is the bounded live acceptance, rerun only when its runtime path, permissions or client version changes. Prototype tests under `docs/design/` are instruments, not gates. Browser launch and screenshot scope: [UI acceptance](docs/design/ui-acceptance.md#contract-detail).

### R13. Spec first
Inherit [specq engineering rules](https://github.com/taskqorg/specq/tree/main/engineering) and its [shared-rule improvement process](https://github.com/taskqorg/specq/blob/main/engineering/spec-first.md#improve-shared-rules). TaskQ decisions live here; conflicting tasks `ask` with options. `AGENTS.md` and `CLAUDE.md` point here. TaskQ scenarios and gaps stay in [use cases](docs/use-cases/README.md). Design follows the [shared workflow](https://github.com/taskqorg/specq/blob/main/design/workflow.md); the [implementation brief](docs/design/implementation-brief.md) maps the accepted product to work. Security reports: [SECURITY.md](SECURITY.md).

## 1. Tasks
A task is an open issue by a trusted author (GitHub `OWNER|MEMBER|COLLABORATOR`, GitLab Reporter+) labelled `taskq` (`taskq add` sets it). Other issues never start: a PM makes a task from one with `taskq add`. A closed issue is done unless the board records it closed without completing (GitHub `state_reason` not `completed`): such a dependency reads unknown (R12). The issue text may be hand-edited: `## Goal`, `## Acceptance`, optional `## Scope`, one line `Depends on #N` per dependency; `Depends on <repo>#N` names an issue of another repository on the board's host (`name` under the board's owner, or `owner/name`), read with the board's token. An unreadable dependency reads unknown. Acceptance items are `A1.`, `A2.`, never renumbered, each an observable check.
`add` writes, in order: Goal 1-2 lines; Acceptance 1-8 items, one line each; optional Scope, 1-4 bullet lines; `Depends on` lines; with `--op-id`, a last line `op-id: <id>`. Title ≤ 80 characters, body lines ≤ 240. More than eight checks: split (R2).
**Create claim (R1, R12, R13).** `add --op-id` needs the owner's `create_claim_issue` and a board that passed the § 3 read-after-write test. The first trusted, unedited `taskq: create-claim <id>` comment owns the op id forever and binds the request by `request-sha256`; changed input is rejected. Only the invocation whose claim POST reads back as that winner may send one create POST; every other one reconciles read-only, and unknown evidence never permits a create. `add` without an op id is not idempotent. Detail: [finding tasks](docs/design/finding-tasks.md#contract-detail).
**Finding CLI (R1, R12, R13).** `taskq finding` (§ 5) runs only as the owner's local CLI on the configured board; grants never authorize it. `--source` parts are opaque ASCII ids; evidence is owner-reviewed text, ≤ 4 lines of 240 characters. Op id `finding.<sha256>` of board and source gives each episode one permanent claim; the create always uses `q-held` and retries read-only; `--start` or a later `start` dispatches the separate `<op-id>.start`. JSON `{create: receipt, start: receipt|null}`. Detail: [finding tasks](docs/design/finding-tasks.md#contract-detail).
Held: `add --hold` labels the issue `q-held` instead of `taskq`, then writes `hold`; it is listed as `held` and no version admits it. `taskq start N` writes `start`, then adds `taskq`.
Labels: `q-<state>` (projection; `waiting` maps to `q-blocked`); type `code|docs|research|asset`; `p0|p1|p2` (lower first, absent = 2; `p0` passes focus, § 4); `run-<runtime>` (none: any); `prefer-codex|prefer-claude` (soft, § 4 Filter); `host-<name>` (none: any); `needs-<x>` (only a host whose `has` lists x, § 9); `assignee-only` (start only when the board's user is an assignee); any other, e.g. `area-maps`. Reserved: `taskq-host`.
## 2. Log and states
A log entry is a trusted author's comment whose first line is `taskq: <kind> [<arg>] [attempt <id>]`; the rest is its text. Entries are read in comment-id order. An edited comment (`updated_at` after `created_at`) or an unknown kind is ignored. A hand-typed entry counts like a command. `taskq answer K` or `taskq answer N.K` (no colon) also counts as `answer K`. In `ask` a comment whose whole body is K or option K's text (trimmed, any case, `K. ` optional) counts as `answer K` if one option matches; `fold` ignores other comments.

`core.rs` is one pure function `fold(n, entries, deps_open) -> Task {state, attempt, role, session, retries, card, result, inbox}`; `inbox` lists the accepted `answer`/`steer` ids of the current attempt. The attempt id is the id of the accepted `spawn` comment: the fencing token. An entry naming `attempt <id>` is accepted only when `<id>` is the current attempt. An entry not accepted in the current state changes nothing.
An entry's optional last lines `op-id: <id>`, then `revision: <R>`, are fields, not text. The task's revision is the id of the entry that set its open card, else its attempt, else its last accepted entry (0: none). `fold` ignores an entry whose op id an earlier entry carried; a writer whose entry read back at another revision or ignored edits it (§ 5).

| State | Entry | Next | Notes |
|---|---|---|---|
| (none) | — | `ready`, `waiting` if `Depends on` names an open issue | start of every task |
| (none) | `hold` | `held` | only as the first accepted entry; N-1 ignores the kind |
| `held` | `start` | `ready`, `waiting` if `Depends on` names an open issue | then the writer adds `taskq` (§ 1) |
| `held`, `ready` | `gate` | same | owner gate `required` (§ 7); N-1 ignores the kind |
| `review`, `ask` | `approve <sha>` | same | gate `approved`; owner only (no `attempt`); `<sha>` is the current result |
| `ready` | `spawn worker <rt>:<session> <host>` | `doing` | attempt = this id, role worker |
| `doing` | `result <sha> attempt` | `review` | text: verdict (section 7); option lines make a card (section 2) |
| `doing` | `ask attempt` | `ask` | text: ask card below |
| `doing`, `review` | `requeue attempt` | `ready` | text: reason or fixes; `retries += 1`; 3rd: `ask` with the limit card |
| `doing`, `review` | `gone attempt` | `ready` / `review` | service: child exited or lease expired; emergency recovery (§ 4); `retries += 1`; 2nd: `ask` with the limit card |
| `doing` | `steer` | `doing` | text for the worker |
| `review` | `spawn reviewer <rt>:<session> <host>` | `review` | only without a live reviewer; attempt = this id |
| `review` | `ask attempt` | `ask` | reviewer's card; result kept |
| `review` | `close attempt` or `close` | closed | verdict text; written after publication (§ 7); ignored while a gate is not `approved` |
| `ask` | `answer [K]` | state before `ask`, else `ready` | `retries = 0`; delivered: text, else option K, else first line |
| any open | `requeue` | `ready` | by PM/owner: result, card and attempt cleared; `retries = 0` |
| any open | `later` / `failed` | `later` / `failed` | text: reason; attempt ended |
| `later`, `failed` | `requeue` / `close` | `ready` / closed | the only exits |

- `waiting` becomes `ready` when every `Depends on` issue is done (§ 1); an open or unknown one keeps it waiting.
- `gone` in `review` ends only the reviewer; the result stays and a new reviewer spawns. Under the § 3 emergency hold that host writes no `spawn`; a child whose liveness reads unknown gets no `gone`; `service recover --apply` writes each `gone` with `--op-id` and `--revision` (§ 4).
- `retries` is one counter: an attempt `requeue` that makes it 3, or a `gone` that makes it 2, moves to `ask` with the attempt ended; its `answer` then goes to `ready`. Limit card: unless its text is a card, the writer appends `Problem:` naming the limit, `1. requeue: …` ★, `2. later: …` and `To answer:` naming only `taskq answer N.K`; the reason's `K. ` lines become `K) `. Every move to `ready` clears attempt, card and result.
- `answer K` whose option starts with `close` or `later` runs `close` (§ 7) or `later` instead, only through `taskq answer N.K`; a bare board `K` folds as a plain answer. An owner pick of `approve <sha7|sha> ...` approves a gated task only when that SHA matches its current result, a bare board comment in `ask` included; an attempt-bound answer cannot approve.
- Gate states: none, `required`, `approved`, `stale`. An approval binds to the result it names: the next `result` or a move to `ready` makes it `stale`, blocking until a new `approve`. The gate blocks only `close` in `review`; a fold after any restart keeps it (R1). Closing a `later`/`failed` task stays the owner's act.
- After an accepted entry the writer sets the `q-<state>` label; every service pass fixes labels that differ from the fold. People change state with an entry, not a label.

### Ask card
`ask` writes, in order, ≤ 9 nonblank lines, no headings or blank lines:
1. `Done: <what was checked or attempted>` -- one line, ≤ 160 characters; `not started` when true.
2. `Problem: <decision needed and user effect>` -- one or two lines, ≤ 240 characters each.
3. Optional `Evidence: [<label>](<url>)` -- one line, ≤ 2 links, labels ≤ 40 characters.
4. Two to four options, `1. <action and trade-off>` etc.; one line each, ≤ 160 characters, exactly one ends in `★`. None: an owner action, its Problem the action; no attempt starts while it waits; its `answer` resumes the same session.
5. To answer: `taskq answer N.K` or comment `K` or the option text; an owner action: `taskq answer N --text <done>`. Last line; N is this task's number.
`--text` supplies Done and Problem; `--link` Evidence; `--option` and `--recommend` the options and star. Presentation and tray card rules: [answer card](docs/design/answer-card.md#contract-detail).

### Executable behavioral model
Apply the [shared behavioral-model method](https://github.com/taskqorg/specq/blob/main/engineering/verification.md#state-driven-systems). TaskQ sources: the § 2 table, `tests/golden/*.json` traces (`fold.json`: entries in, task out; `admit.json`: free slots in, admitted runtimes out), `fold`, then adapters. `fold` is the behavioral truth; board and process qualification stay separate (R12).
Attempt stages and queue transitions (§ 4 Profiling) are adapter observations outside `fold`. Stages: `claim` the `spawn` post and readback; `start` runtime start/resume; `build`/`review` child start to exit or stop, outcome from the accepted hand-in (`result`/`close` ok; replaced without one `cancelled`; none or unreadable `unknown` with reason); `ask` while this service sees its attempt in `ask` (lost on restart); `checks` CI verification and merge; `close` the whole command. A transition is each accepted entry that changes the folded state, replayed per pass (`waiting`, `hold`, `start` and the first pass after a start add none).
## 3. Attempts, lease, capacity
- **Claim.** A service admitting a `ready` task posts `spawn worker`, re-reads the comments and starts the child only if `fold` accepted its own `spawn`; a loser posts nothing more. Same for `spawn reviewer`. `ponytail:` needs read-after-write order of comment lists, verified per board by a two-host test (R12); a guard label around `spawn` is the upgrade path.
- **Fencing.** The child gets `TASKQ_TASK=<N>` and `TASKQ_ATTEMPT=<id>`; its commands add `attempt <id>`; `fold` ignores a replaced attempt's late writes. With `TASKQ_ATTEMPT` set, `result`, `ask`, `requeue` or `gone` is refused before any write when `TASKQ_TASK` is not `<N>` or the attempt is not live; a seen op id returns its first receipt.
- **Lease** = the attempt's host heartbeat (§ 4) is fresh and lists `#<N> <id>`. No timestamps in the task.
- **App lease.** A `codex-app` turn is the child while the Codex app runs in this host's session and the thread has no `task_complete` after the queued brief or text. A finished turn without hand-in, a closed app or a logout is a child exit (`gone`). Stopping only drops it from the heartbeat; late writes are fenced. Updates wait for active app turns (§ 8 step 3).
- **Expiry.** Any service seeing `doing` or `review` whose host heartbeat is older than `ttl` or lacks the attempt posts `gone attempt <id>`; an attempt younger than `ttl` (by `spawn` or newest `answer`/`steer`) is judged by heartbeat age only. That is the only recovery. The owning service resumes an attempt without a child when its `inbox` holds an undelivered entry, else posts `gone` with the last worker message.
- **Capacity** per project and host = the effective `limits.<runtime>` (§ 9) minus the service's live children of that runtime, reviewers and resumes included. Fixed (default): 0 or no limit admits none; Auto: no limit means no count ceiling, 0 disables. Host limits add up across projects. Each pass reloads capacity config; invalid config holds every launch. Lowering a limit never stops a child (R11).
- **Load gate** (opt-in, § 9) holds every new child (claim, reviewer, resume) while CPU busy >= `cpu_max` % or available memory <= `memory_min` %; running children continue. A missing or stale sample holds; reopening needs three valid samples below the band; ≤ 1 launch per 30 s; a held resume keeps its inbox; a held won claim stays leased. No battery or thermal gating, no forced retirement. Sampling and hysteresis: [capacity](docs/design/capacity.md#contract-detail).
- **Host admission.** One host authority, `<install>/admission.json` under `<install>/admission.lock`, admits every Auto launch after the load gate. Each service rewrites its entry every pass and 30 s; an entry over 120 s old drops. Reservations: `requested` (refused, with reason), `held` (counted until its child exits), `released`. A grant needs every fresh service of `<install>/projects` at version `4.2.0-dev` or newer, held reservations under `admission.max`, the last host launch ≥ 30 s ago and a gate sample after it. An unreadable file refuses and is rebuilt. Fixed services are never refused.
- **Emergency hold.** `<install>/hold` (one reason line) refuses every launch on the host before the load gate until `service release` removes it; pause and resume never touch it; an unreadable file holds; live children run on. Older services ignore it; `service hold` names them.
- **Cancellation** of an attempt = `requeue`, `later`, `failed` or `gone`; the owning service stops the child (R11).
## 4. Service
`taskq service run` is the host's single long-lived process; `taskq service install` makes the OS keep it running (§ 8). One loop:

1. Reap exited children; a CLI child whose attempt log shows its turn ended (`turn.completed`, `turn.failed`, `result`) counts as exited and its process tree is stopped. A child whose attempt is current posts `gone attempt <id>` with the exit code and its last worker message (one line, paths root-relative or `<path>`, ≤ 240 characters), unless the attempt wrote `ask`, `result` or `requeue` after the child started: then step 6 resumes it from its inbox.
2. Stop children whose attempt is no longer current (R11). Remove worktrees of closed tasks (§ 7).
3. Write the heartbeat issue `taskq host <name>` (label `taskq-host`) when older than `ttl / 3` or changed: `version <v>`, `service <id>` (12 hex of SHA-256 of `<install>/installation-id`), `machine <hostname>[ wsl]` (DashQ joins hosts by it, [dashq hosts](https://github.com/taskqorg/dashq/blob/main/docs/design/hosts.md) H2), `#<N> <id>` per live child or gate-held launch, `focus off|unknown` when focus admits nothing, `at <board time>`. Freshness uses the board's `updated_at` and response `Date`, never local clocks.
4. Post `gone` for attempts of dead hosts (§ 3).
5. Fix projected labels; `waiting` with closed deps becomes `ready`.
6. Resume the session of a live attempt for a new `answer` or `steer` (text on stdin); spawn a reviewer for `review` without one; admit `ready` tasks matching this host by priority then number within capacity.
7. Every `update_every`, or when a local command wrote `<root>/.taskq/update`: the self-update check (§ 8); an installed service applies a newer version, others report it.
8. Sleep until a poke or `poll` seconds.

- Filter: `host-*` absent or this host; workers use `run-*`, else a `prefer-*` runtime with a free slot, else the runtime with the most free slots (first listed on a tie); both `prefer-*` labels are ignored with a log line; reviewers prefer the runtime other than the worker's (`claude` ↔ `codex`, `codex-app` → `claude`) with free capacity. `assignee-only` passes; each `needs-*` must be in `has` (`needs-gate`: every host of a version with gates, § 7); `codex-app` keeps its § 9 opt-in.
- Focus: `taskq service focus all|off|<label..> [--request TEXT]` writes `<root>/.taskq/focus`: `all`, one of the labels or `p0` passes; `off` (default) admits nothing while heartbeats and updates go on, said by capacity reason `focus` and the heartbeat. `service install` writes `off` only when the file is missing. `--request` keeps the owner's words in `focus.request`. No arguments: print focus, `has` and open-task labels; an agent maps the owner's words to these and asks when unsure.
- Pause: `service pause` saves the focus to `focus.paused` and writes `off`; resume restores it, else fails naming open-task labels: never `all` by default.
- Emergency ([E1–E5](docs/design/emergency-recovery.md#contract-detail)): under the § 3 hold the loop still reaps, stops replaced children and beats. A failed liveness read keeps the child (`status.json` `kids` `live` `unknown` with `reason`), never `gone`. `service recover` (only under a hold) proposes `gone attempt <id>` with `--revision` and `--op-id recover.<N>.<id>` for each child read running or absent; unknown blocks relaunch. `--apply` writes them through the § 5 dispatcher.
- Poke: a local command touches `<root>/.taskq/poke`; the sleeping service checks it every second. Each pass writes `<root>/.taskq/status.json` for `service status`, the tray and DashQ: coreq common keys, service state, the § 5 snapshot (a failed pass keeps the last rows with `complete` false), `capacity`, `requests`, `incident`, `agents` (§ 5, probed ≤ every 5 minutes) and § 8 `access`; the key list is `service_run` in `src/main.rs` and `Service::capacity_json` in `src/service.rs`. Capacity is also published per sample; over 60 s old reads unknown.
- Events: a pass appends to `<root>/.taskq/events` `<board time> #<N> close|failed|ask|blocked|gone <id>` per task it saw move to closed, `failed`, `ask` or `waiting` since its previous pass; the id is the attempt current at the move, else the last spawn, for `ask`/`blocked` else the last comment, else the issue number; a never-spawned closed or `failed` task adds none. `gone`: per trusted `gone attempt` entry newer than the previous pass. One line per attempt and kind; 30-day bound; first line `since <time>` (`events_since`); moves while no service ran are missing. `ponytail:` files, no board replay, no socket.
- One service per root and host name: `service run` waits while a `status.json` under 60 s old names another live pid; a pass finding this host's heartbeat under `ttl` naming another `service <id>` writes nothing and fails `another service <id> runs as host <name>`. Restart rebuilds from the board; former children are not adopted (except the § 8 re-exec), their attempts are `gone`. `service restart` writes `<root>/.taskq/restart`: the next pass re-execs.
- Tray (macOS, Windows; [menu](docs/design/menu.md#contract-detail) M1–M14): one per host, started by any installed service when `<install>/tray` (its pid) is older than 30 s. It reads `<install>/projects` and each `<root>/.taskq/status.json` and `events`: no board, no token. Icons come from `src/icon.rs`. Writes name their target and effect first; `Applied`, `Edit limits` and `Update now` succeed only when `status.json` reads the value back. `taskq tray --snapshot DIR [--route R,..]` writes icon and popover snapshots in both themes, then exits.
- AI requests ([AI workspace](docs/design/ai-workspace.md#contract-detail), menu M7, M10): the tray writes `<root>/.taskq/requests/<id>.json`; the service runs one operator (R3) turn at a time per project and writes `<id>.answer.json` with a `state` and `rev`. The answer contract is JSON `{kind: result|clarify|proposal|refuse, text, ops}`; a proposal holds only allowlisted ops (`focus`, `pause`, `resume`, `add`, `answer`, `later`, `requeue`) on registered projects. Only a confirmed proposal at its shown `rev` applies, once, each op with `--op-id <id>.<rev>.<k>` and the task's revision; `applied` only after readback; a crash never replays. Add project (M10) installs a passing project after a confirm; a new folder gets a `setup` proposal listing every external effect (§ 6). An owner comment on an `ask` task that is no entry becomes a request whose proposal holds one `answer`, `later` or `requeue` op. Request log: `<root>/.taskq/requests.log`, newest 500 lines (`data::REQUEST_LOG`).
- Incident reports ([incidents](docs/design/incidents.md#contract-detail)): `incident_reports` (§ 9) defaults to true; `false` or `TASKQ_INCIDENT_REPORTS=off` disables. Setup and the shipping update disclose destination, visibility, account, payload, fallback and opt-out first. Only a catalog fault reports, with an allowlisted payload ≤ 4 KiB holding no project, task, host, user, path or free text, as one `incident` issue in the release repository; else it stays in `<root>/.taskq/incidents/`. A report never changes a task, the queue or an exit code; `status.json` `incident` shows the newest outcome.
- Data ([specq data](https://github.com/taskqorg/specq/blob/main/engineering/data.md#files)): bounds in `src/data.rs`, pruned hourly: `<install>/taskq.log` and `<project>.log` past 4 MiB and `.taskq/cli-errors.log` past 256 KiB keep their newest half; attempt logs the newest 50 plus live ones; `incidents/` the newest 50; `requests/comments` past 1000 lines the newest half plus eligible ones; `events`, `requests/` and `requests.log` as above. A corrupt `status.json`, `tray.json`, `kids` or `focus` reads unknown with its reason, admits or adopts nothing and deletes no release; a tray save first copies a corrupt `tray.json` to `tray.json.corrupt`.
- Log and board budget ([counting format](docs/budget-1032.md#contract-detail)): service log lines are `<UTC time> <text>`. Every process counts its board HTTP requests per operation and, on a rate-limit reply, pauses board calls until the reset (≤ 1 h), failing them at once. `status.json` `requests` and `service status`/`list` show counts, `remaining`/`limit` and the pause. CLI processes and the service hourly append `taskq-requests {at_ms, source, ops}` to `<install>/taskq.log`. One board user's 5000 requests/h serve every host, CLI, worker, PM and DashQ: a pass costs one open-issue list and re-reads comments only of issues whose `updated_at` moved. At `remaining` <= 20 % of `limit` the service logs `board budget low` once per reset, and `service status`/`list` and R6 line 1 show `Board budget low: <remaining>/<limit> <resource> until <reset> (<host>); top here: <op> <n>`.

Owner-facing service/tray text follows R7: counts use R6 names and order; task rows are `#N <title>`. Use `Focus: <labels|off>`, `Paused`, `Service: <running|stopped|unknown>`, `Update: <version|up to date|unknown>`. Menu labels ≤ 32 characters; lines ≤ 160; navigation per [D8](https://github.com/taskqorg/specq/blob/main/design/operator-ui.md#principles).
### Profiling (#988)
Follow [shared profiling](https://github.com/taskqorg/specq/blob/main/engineering/profiling.md); budgets stay unknown until owner-approved baselines; profiling never changes admission or task state. Records hold fixed codes and numbers only (`TASKQ_PROFILE_TRACE=1` adds span ids) in `<install>/taskq.log` under its § 4 Data bound, appended under the nonblocking `taskq-profile.lock`; an instrumentation failure never fails the operation.
- Six timed operations: `service.pass`, `dispatch` (claim to runtime handoff), `spawn` (runtime start or resume), `forge.call` (one HTTP request), `update`, `tray.render` (icon and native apply).
- `taskq-stage` per attempt stage (§ 2 model): task, attempt, runtime, duration, outcome (`ok`/`ask`/`retried`/`failed`/`cancelled`/`unknown`), error class and, for `build`/`review`, context tokens and model calls from the attempt log (else unknown with reason).
- `taskq-board` per board adapter call: kind (`list`, `inbox`, `read`, `claim`, `comment`, `label`, `close`, `write`, `publish`), duration, outcome, error class, lowest `remaining`.
- `taskq-transition` per queue transition: task, entry id, from and to state, time in the previous state, runtime and host on either side; consumers dedupe by task and entry.
`taskq profile` reads the retained log without the board and ranks operations, board calls, transitions and attempt stages by p95 and failure rate, and lists this host's board requests of the past hour; missing data reads unknown or partial. DashQ reads this local report, never the board, for stage data.

## 7. Worker, reviewer, publication
Worker brief: task text, attempt, branch, delivery commands, this file's path (else this release's URL), the folder rule (§ 8), rule 7. The task grants this section's commit and publication steps only ([approval boundaries](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#approval-boundaries)). Rules:
1. Read this file and the whole issue first, then [prepare the task](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#prepare-the-task): a decision conflict (R13), an unclear Acceptance item or a split (R2) is an `ask` before code.
2. Workspace: `git worktree add -b taskq-<N> .worktrees/taskq-<N> origin/main` (existing branch: continue it). `workspace: external`: the path the project's `AGENTS.md` gives.
3. Owner-only question: `ask` with options, then stop. Cannot be done: `requeue --text`, then stop.
4. Before `result`: commit on `taskq-<N>` with `Task: <issue url>`, rebase on `origin/main`, run the project checks, name each in `--checks`. `result` refuses a diff changing a `uiSources` file whose blob `docs/shots/manifest.json` does not record (fix: `docs/shots/update.sh`); an unreadable check reads unknown and refuses. Never weaken a check: a changed existing test or golden trace needs a changed rule in the same diff, named in `--text`. Fixes record [before/after evidence](https://github.com/taskqorg/specq/blob/main/engineering/verification.md#run-policy-by-stage) or its limit.
5. Delivery `direct`: push `taskq-<N>`. `auto-merge`, `review-pr`: push and open one PR/MR into `main`. Then `result --sha <sha>`; do not wait for CI. Research: `--sha` = current `origin/main`, the answer in `--text`.
6. Everything written through taskq is public: no secrets, tokens or local paths.
7. CI wait, worker or reviewer: ≤ one poll a minute (`gh pr checks <PR> --watch --interval 60`); never `gh run watch` or `gh run view` without `--json`.

### Result and close verdicts
`result` body: `Changed: <user effect>` (1-2 lines), `Checks: <command -- outcome>` (1-8 lines), `Open: <remaining item|none>` (1-2 lines); ≤ 12 lines of ≤ 240 characters, exact commands kept (R12). `--text` supplies Changed and Open, then an optional card's Done/Problem (§ 2 format) with `--option`, `--recommend`, `--link`; `--checks` lines get the `Checks:` prefix. One PR link may carry the [risk description](https://github.com/taskqorg/specq/blob/main/caveman/rules/changes.md#merge-request-description-markdown).
`close --text` has the same three fields; Checks names each `A<k> ok|gap|unknown` and the exact-SHA CI outcome.
The reviewer checks every Acceptance and contract against the candidate and its CI, per [shared review](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#review) and rule 7. Requeue only for Acceptance/contract gaps; advisory findings go in `Open:`. Then `close --text`, `requeue --text <exact fixes>` or `ask`. The PM relays the verdict verbatim.

`close` publication goes through the board API only:
- `direct`: branch `taskq-<N>` equals the result SHA, `main` its ancestor, CI green on it; move `main` without force, read back, close. GitLab: a fast-forward MR.
- `pr`: exactly one open PR/MR of `taskq-<N>` at the result SHA, `main` its ancestor (else `requeue`: rebase), CI green; `main` must refuse a stale head (GitHub: an unbypassable up-to-date ruleset, or protection with admins enforced; GitLab: fast-forward or semi-linear), else refuse; mark a draft ready; squash-merge with the title and all `Task:` lines; read the merge back; close. Incident ancestry uses the merge SHA, or the result SHA for direct.
- No commit (research, or SHA already on `main`): verify ancestry, close.
- Pending or missing CI: refuse, state unchanged. Failed CI or conflict: `requeue` with the message.
- On the attempt host: remove a clean `.worktrees/taskq-<N>` and its branch; dirty ones stay.
- Merged, not closed (partial publication, or a merge into a release branch): with no open PR/MR into `main`, `close` finds the merged one of `taskq-<N>` whose head is the result SHA and closes with `merged #P [into <base>] as SHA`. From a reviewer's `ask` an owner `close` option runs it (§ 2); `doing` or a worker's `ask`: `later`, then `close`.

**Delivery presets** ([agent behavior](docs/design/agent-behavior.md) B1–B5) are § 9 `delivery` `{preset, revision}`, the owner's (R9): `auto-merge` (the `pr` route), `direct`, `review-pr` (`pr` after the owner gate). `local` and `push-branch` are refused until B3 states exist. Without `delivery`, `publish` names the preset at revision 0 (`pr` is `auto-merge`). `close` reads the policy then and ends its verdict with `delivery <preset> r<revision>: <main fast-forwarded to SHA|merged #P as SHA|SHA already on main>`. `review-pr` needs every host at `4.2.0-dev` or newer.

### Recipes and owner gates
A recipe ([plans and decisions](docs/design/plans-and-decisions.md) P5) is a task list in § 9 `recipes` with a `version`. `taskq recipe NAME --run ID` adds each task held through the § 1 create claim with op id `recipe.<name>.<version>.<ID>.<k>`, so a rerun returns the first receipts; `deps` become `Depends on #N`; `{goal}` becomes `--goal`. A `gate: true` task also gets `needs-gate` and a `gate` entry. Nothing starts until every task reads back; then `--start` or `taskq start N`.
A reviewer of a gated task or `review-pr` project that finds the result done asks with `approve <sha7> and close ★` first; an owner pick or `taskq approve N` binds the gate to that result; the reviewer then closes. A new result needs a new approval; `close` refuses before publication otherwise.

## 8. Runtimes and deployment
**Access (R9).** `<install>/worker-policy.json` is operator-owned: `revision` and `grants` (`runtime`, preset `mode`, project or host scope, `by`, `at`). Presets: `restricted` writes runtime homes, caches, OS temp and `<root>/.taskq`; `workspace` also `<root>`; `full` turns the sandbox off (Claude `--permission-mode bypassPermissions`; Codex `-s danger-full-access`). Starts and resumes resolve requested and effective access, shown by `service permissions` and `status.json` `access`; no grant runs legacy flags. Non-Full modes keep `<install>`, `PATH` and runtime package directories and `.codex/*.toml` out of worker writes. Unknown enforcement refuses before claim or resume. `service permissions` writes outside a worker only; a board answer never grants. Rollback floor `4.2.0-dev`. Enforcement per platform, limits and procedures: [worker permissions](docs/design/worker-permissions.md#contract-detail).

|---|---|---|
| Codex | `codex exec --json <codex opts> -C <root> -`, brief on stdin; session from the first `thread.started` line | `codex exec --json resume <id> -` |
| Claude | `claude --bg --remote-control <name> --permission-mode <mode>`, brief on stdin; native ID from `agents --json` | After stop readback: `claude --bg --resume <id>`, fresh brief on stdin; same ID required |

The child's environment drops `CLAUDE_CODE_SESSION_ID` and `CODEX_THREAD_ID`, adds `TASKQ_TASK`, `TASKQ_ATTEMPT`, `TASKQ_ROLE` and, on GitHub, the host board token as `GH_TOKEN`/`GITHUB_TOKEN`. Briefs go through stdin, never a shell. App turns use the app's own environment and need an owner-provisioned `gh` token; a missing token is a worker `ask`. Claude background-turn completion comes from native `agents --json --all` and the transcript, never launcher exit; resume keeps the native ID. Platform detail: [runtime qualification](docs/runtime-qualification.md#contract-detail). Logs: `<root>/.taskq/<T|R><N>-<attempt>.log`.
**Rule delivery (R13).** Each worker, reviewer and operator start and resume embeds `engineering/{agent-workflow,use-cases,verification}.md` and `caveman/rules/changes.md` from specq revision `46f5f62389f84ce3cc4d2a526a42a5d4bacbf8be` before the task text, fetched from immutable HTTPS URLs without credentials (10 s, 64 KiB per file); a failed fetch refuses the launch. The same payload reaches every runtime; a new approved specq revision changes the pin; rules refresh on the next resume or attempt; logs name the revision.
**Folders.** Service, tray and spawned runtimes touch only `<root>`, `<install>`, `~/.claude`, `~/.codex` and the OS temp dir; never Documents, Desktop, Downloads, iCloud, removable or network volumes or other app containers. The brief names an existing contract and forbids searching `/` or `~`; the tray reaches other folders only through the owner's folder picker.
**Shared core.** Release, update, launcher and rollback, service units, the `status.json` common keys and the GitLab board token follow [coreq.md](https://github.com/taskqorg/coreq/blob/v0.11.0/coreq.md) (crate `coreq`, pinned by tag) as `Tool::new("taskq", "TaskQ", "taskqorg/taskq", VERSION)`: install `~/.local/share/taskq` (Windows `%LOCALAPPDATA%\taskq`), files `taskq-<ver>-<os>-<arch>`, units `com.taskq.<project>`, `TaskQ-<project>`, `taskq-<project>.service`. taskq's own parts:
1. Hosts need no git, gh or toolchain. Each release runner runs `selftest` on its artifact before publishing. Windows releases use MSVC's static WebView2 loader. Each binary and `SHA256SUMS` carry a build provenance attestation (`gh attestation verify <file> --repo taskqorg/taskq`) per [release rules](https://github.com/taskqorg/specq/blob/main/engineering/release-contract.md#rules).
2. `taskq update` and service step 7 run the coreq update. A new `current` then gets one allowlist sweep of `<install>` and a `~/.local/bin/taskq` v3 python shim. Kept: `releases/` of `current`, `previous`, the running version and each `projects` root's `status.json` version, `current`, `previous`, `projects`, `token`, `installation-id`, `connection/`, `worker-policy.json`, `windows-native/`, the launcher, `WebView2Loader.dll`, `taskq-tray.exe`, `*.log`, `tray*`, `capacity/`, `resources/`, `TaskQ-*.xml`, `*.tmp`. A file in use stays until a later update.
3. At step 7 an installed service older than `current` logs `current is <v>; restarting` and re-execs through the launcher; live CLI children pass to the new image through `<root>/.taskq/kids`. An active Claude, codex-app or operator turn defers re-exec; the restart stays pending, logged once per changed set as `restart to <current> waits for #<N>, ..` and shown in `status.json` `restart_waits` and `service status`. Windows: exit 75 once no child is live.
4. The service marks its version `healthy` after `rollback_after`. Children keep running from their own release folder.
5. `service install` installs its binary as a new file, never over an existing release binary (macOS kills rewritten binaries). While the project's `status.json` lists live children it writes `<root>/.taskq/restart` instead of reloading. Windows stops end the process tree (`taskkill /T`); run Windows setup outside an MSIX app. The coreq launcher counts unhealthy starts per project. macOS signing with `TaskQ Local Signing`, else ad-hoc: [worker permissions](docs/design/worker-permissions.md#contract-detail).
**Compatibility N/N-1.** v4 releases differ only by additive log kinds N-1 can ignore without a different fold; anything else needs a § 9 cutover. N-1 reads op id and revision lines as text. N-1 ignores `gate` and `approve`, so `needs-gate` keeps its services off gated tasks. N-1 parses only `Depends on #N`, so `Depends on <repo>#N` goes only into a held task until every host has it. Hosts update independently. A version whose `selftest` fails is not published.
**Contract size (R8).** `taskq.md` stays within 300 lines and 60 KiB, enforced by the § 2 golden-trace test in `src/core.rs`.

## 9. Config and cutover
`taskq.json` beside the project root:
- `board` `github|gitlab`; `repo` `owner/name`; `host` the board's web host (default `github.com`, `gitlab.com`).
- One module per board under `src/board/` (`github.rs`, `gitlab.rs`); the `Board` trait and `src/board/mod.rs` are the only contract; core, service and operator never branch on the board kind.
- `label_schema` `canonical|legacy` (absent: legacy if the board has `priority-1|2` or `q-waiting` objects, else canonical). Both names work in filters; `p0` has no legacy name. Canonical writes on existing boards need all-host compatible release approval; only open issues are relabelled.
- `publish` `direct|pr`, `delivery` (§ 7); `workspace` `external` keeps host-owned worktrees.
- `hosts` `{hostname: name}` (env `TASKQ_HOST` overrides); `has` `{name: [x..]}`; `limits` `{"claude": n, "codex": n, "codex-app": n}`.
- `add --prefer codex|claude` writes one soft `prefer-<rt>` label ([runtime preference](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#runtime-preference)). Opt-in `codex-app` (macOS, Windows): only on hosts whose `has` lists it, only for `run-codex-app` tasks. A screen task adds `needs-screen` (`has` `screen`). macOS evidence tasks: [runtime qualification](docs/runtime-qualification.md#macos-evidence-tasks).
- `capacity_hosts` `{name: {"limits": {..}, "load_gate": {..}}}`: partial `limits` override the top-level ones for that host; a host `load_gate` replaces the top-level object; defaults `enabled` false, `cpu_max` 85, `memory_min` 15; valid limits 0..u32::MAX, `cpu_max` 10..100, `memory_min` 1..95. `admission` `{"mode": "auto"|"fixed", "max": n}` (host value replaces top-level; absent: fixed; setup writes auto): auto enables the gate with [D03](docs/design/admission-calibration.md) defaults `cpu_max` 90, `memory_min` 10 and the 2.5 GiB floor; `enabled` false is invalid. Absent keys keep today's behavior; old binaries ignore them.
- `recipes` `{name: {"version": V, "tasks": [{"title", "goal", "acceptance": [..], "scope", "deps": [earlier 1-based index..], "gate", "type", "runtime", "priority", "host"}]}}` (§ 7).
- `permission_mode`, `codex` (R9); `incident_reports` `true|false` (§ 4); `pages` link wrapper base; `assignee` (login or `me`) report filter.
- `ttl`, `poll`, `update_every`, `rollback_after`: seconds, defaults 300, 60, 900, 600.
- GitHub token: one owner-installed credential per host in `<install>/token` (owner-only), shared by service and workers; a fine-grained PAT preferred. No env or CLI-login fallback; nothing runs `gh auth login`; a missing token is an owner item. Never in config. GitLab keeps coreq token lookup.

A cutover is one step per project: two board formats never mix. No migration code: `CHANGELOG.md` says per release what changed on the board and what an open issue needs. An agent reads the entries from the board's version to the new one, prints a plan per open issue and collects its questions for the owner. After the owner's OK, with every old service stopped and no old children, it applies the plan with `taskq` commands and issue edits. Closed issues are never touched. New services start: Mac, then Windows. Repair is the same procedure for one project; it warns when another host's heartbeat is fresh.
