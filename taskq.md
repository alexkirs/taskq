# taskq contract
taskq queues agents on GitHub/GitLab. Contract includes linked `Contract detail` sections; state: board (R1).
**v4**: Rust in `src/`.
## Principles (R1–R13)
### Change rule
A task that changes a rule names its R-number, edits this file in the same deliverable as the code and lists the amended R-numbers in its result. A changed rule keeps its number. A new rule gets the next one. A rule elsewhere that disagrees with this file is a defect. No history here: no dates, no decision logs; line bound: R8.
### R1. The board's own objects are the only state
The trusted comment log is truth; labels project it. People see labels, issue text, `taskq:` comments (section 2), and heartbeats (section 4); no issue machine block. Restart rebuilds caches; no local task DB or queue. Exceptions without task truth: minimal native recovery identity (§3); [DashQ connection state](docs/design/enrollment.md); AI request files/history/log; incidents/profiles; host policy/migration backup; emergency hold; operator [resource grants/receipts](docs/design/shared-resource-controls.md#host-adapter). Fresh `status.json` checks the per-root pid; `<install>/service` checks the host pid (section 4).
### R2. One task, one attempt
A task has at most one live attempt: one worker or one reviewer process. Work bigger than one reviewable diff follows [shared task preparation][sq-prepare], using tasks linked by `Depends on #N`. A live attempt is never moved to another host or session; a new attempt replaces it (§ 4).

### R3. Roles
- **Owner**: decides product questions, answers `ask`, accepts or rejects results through the PM.
- **PM** (manager): the agent session the owner talks to. Files tasks, relays questions and outcomes. Does no task work, never answers for the owner. The queue does not depend on a PM being online.
- **Service**: one host process for all registered projects (§ 5). The only process that spawns workers, reviewers and operators.
- **Worker** `T<N>`: a child of the service. Does one attempt, writes `result`, `ask`, `requeue` or `later`.
- **Reviewer** `R<N>`: a child of the service, spawned on demand for a result. Checks the exact candidate, then `close`, `requeue` with fixes, or `ask`. No resident supervisor session.
- **Operator**: the owner-facing agent for project research, edits, checks and TaskQ operations (§ 4), with normal runtime tools and project permissions (R9); authority per [shared approval boundaries][sq-approval], unresolved authority uses clarify/proposal. Task-state writes use TaskQ commands, never hand-edited logs. Its failure does not fail a worker task and does not prove absence of side effects.

Session names: `T<N> <title[:40]> (<host>)` and `R<N> <title[:40]> (<host>)`.

### R4. Comments move the queue
Each command that changes a task appends one `taskq:` comment, sets the projected labels and pokes the local service. Services also poll the board every `poll` seconds. No sender session, timer or PM chat is on the critical path.

### R5. Completion is written to the task
Result SHA, checks, questions and blockers go to the issue as `result`, `ask`, `requeue` or `later`; evidence follows [specq verification][sq-verify].

### R6. Human report
`taskq status` renders the [read-model](docs/design/refactoring-backlog.md) snapshot of one board read (§ 5 `--json`; service status, `status.json` and tray count the same rows), in this order (empty parts omitted). Tray/browser project summaries and task rows (metadata/links first, full wrapped title second under M3) reuse [shared project blocks](docs/design/project-blocks.md), including separate Doing/Review, nonzero K counters and unknown Closed until authoritative totals exist:
1. `<project> · [board](<url>)`, preceded while a local `status.json` under 60 s old reports a board rate-limit pause (§ 4) by `Rate limit: board requests paused until <time> (<host>)`, else a low board budget by its § 4 line, also when this read fails.
2. `In work N · Waiting for answer N · Ready N`. In work: `doing` + `review`. Waiting: `ask`. Ready: `ready`.
3. `| Task | State | Runtime | Session |`, one row per open task except `ask`, `later`, `failed`, by priority then number; task and session cells are links; `waiting` rows say `blocked ([#M](url) open)`: each blocking dependency (§ 1) linked, then `open` or `unknown: <reason>`; `status --json` rows add `blocked` (`ref`, `url`, `reason`).
4. `Questions (answer N.M):` and `| Question | Brief reason | Options |` with `N.1 <option> · N.2 <option> ★` (★ =
   recommended), one row per `ask` and per `review` with options; an owner action (§ 2) reads `waiting for owner: <action>`.
5. `Later: [#N title](url), ...` on one line; then `Failed:` with a reason table.
6. `Hosts: <host> v<version> <age>[ focus off|unknown], ...` from heartbeats (§ 4).
7. `Next: 1 <action> ★ · 2 <action>` from the PM ([shared Next contract](https://github.com/taskqorg/specq/blob/main/design/workflow.md#ai-assisted-controls)).

Display titles at most 60 characters, reasons at most 160 and option text at most 120; show ellipsis with an issue link for the full text. Keep every row and option, counts and answer tokens; no total report cap. Cells pass one formatter: newline becomes space; `|`, `[`, `]`, `\` are escaped. Claude links use only the Remote Control URL registered by that native session; the local UUID is not a remote ID. Codex links: `codex://threads/<id>` when `TASKQ_CLIENT=codex`, else `<pages>/open.html#codex://threads/<id>`.

### R7. Style
Follow [specq Core](https://github.com/taskqorg/specq/blob/main/caveman/rules/core.md) and its applicable profile; project documents follow [Documentation](https://github.com/taskqorg/specq/blob/main/caveman/rules/documentation.md) in English.
Single and batch CLI outcomes use the same success/error renderer; a failed item keeps its task number.
Owner-text templates in sections 1, 2, 4, 5, 7 are the design target; release them with their implementation (R8), not as proof of shipped behavior.
Limits count logical lines and Unicode characters, including labels and numbering; exclude blank separators and the log header.
Link targets and exact commands/SHAs/paths are exempt from character limits, not line limits; link labels stay short.
Commands refuse over-limit new input before writing, naming the excess; historical/hand-written entries fold unchanged; compact displays use ellipsis and a link (stored text verbatim: [Core Write][sq-write], [source and sink][sq-sink]).

### R8. The contract is the SoT and matches code
Apply [shared spec-first rules](https://github.com/taskqorg/specq/blob/main/engineering/spec-first.md) to this contract: TaskQ code and contract ship in the same release (§8); every §2 table row has a golden trace, and this file stays within the § 8 contract size bound. Host acceptance: [H-A1–H-A5](docs/design/host-service.md#command-surface-acceptance); targets need qualification.

### R9. No silent changes to model, effort or permissions
Name model, effort or permission changes to the owner first. Host.json owns capacity, `permission_mode` and `codex` (section 9); agents propose capacity and apply it only on explicit owner instruction. Access comes only from operator-owned grants ([P1-P4](docs/design/worker-permissions.md), [authority][sq-perm], section 8 Access); project config, tasks, labels and answers may request or narrow, never grant it. Requests: Claude `--permission-mode dontAsk`; Codex `-s danger-full-access`. Operators use the same CLI permissions and host board environment as workers: no silent elevation, runtime fallback or tool-free override. Owner requests grant their stated scope; setup external effects still need section 6 confirmation.

### R10. Multi-project only by explicit list
Host service/PM use owner-approved `<install>/projects` only; no discovery. One report/project.
`N.M` answer that could match several projects needs the project named first.

### R11. Retire sessions only after their attempt ends
A worker or reviewer is stopped only when its task is closed or parked or its attempt is replaced, emergency recovery included (§ 4). Identity is the recorded native session ID, never a name match; a completed Claude background turn is stopped after native completion readback, and a CLI child after its log shows the turn ended (§ 4 step 1), each with its conversation retained for the next turn. Uncommitted work is never lost: only `cleanup --force` removes it, after saving it to `<root>/.taskq/trash/taskq-<N>.patch`.

### R12. Unverified means unknown
Follow [shared verification][sq-verify]. Merge gate: `python3 scripts/check.py`; [selection and budgets](docs/testing.md). Release needs exact-source CI and staged offline selftest. [Live acceptance](docs/runtime-qualification.md) reruns for changed runtime paths, permissions or clients. Prototypes are instruments; [UI acceptance](docs/design/ui-acceptance.md#contract-detail) owns browser/screenshot scope.

### R13. Spec first
Inherit [specq engineering rules](https://github.com/taskqorg/specq/tree/main/engineering) and its [shared-rule improvement process](https://github.com/taskqorg/specq/blob/main/engineering/spec-first.md#improve-shared-rules). TaskQ decisions live here and win over conflicting shared rules (§ 8); conflicting tasks use `ask` with options. `AGENTS.md` and `CLAUDE.md` point here. General rules belong upstream; TaskQ scenarios and gaps stay in [use cases](docs/use-cases/README.md). Design collaboration follows the [shared workflow](https://github.com/taskqorg/specq/blob/main/design/workflow.md); the [implementation brief](docs/design/implementation-brief.md) maps the accepted product to system and application work. Security reports: [SECURITY.md](SECURITY.md) (private GitHub vulnerability reporting, 7 calendar days), per the [shared security baseline](https://github.com/taskqorg/specq/blob/main/engineering/security.md).

## 1. Tasks
A task is an open issue by a trusted author (GitHub `OWNER|MEMBER|COLLABORATOR`, GitLab Reporter+) labelled `taskq` (`taskq add` sets it; on the board a person adds it). Any other issue never starts: a PM makes a task from it with `taskq add` and comments on it when the task closes. A closed issue is done, unless the board records that it closed without completing (GitHub `state_reason` other than `completed`, e.g. `not_planned`): such a dependency reads unknown, never done (R12; GitLab records no reason). The issue text is for people and may be
edited by hand: `## Goal`, `## Acceptance`, optional `## Scope`, one line `Depends on #N` per dependency; `Depends on <repo>#N` names an issue of another repository on the board's host, read with the board's token (`<repo>`: `name` under the board's owner, or `owner/name`). An unreadable dependency reads unknown. Acceptance items are `A1.`, `A2.`, never renumbered; each an observable result a reviewer checks without reading the code.
`add` writes these sections in that order, then dependencies: Goal 1-2 lines; Acceptance 1-8 items, one line each;
Scope optional, 1-4 bullet lines; dependencies one `Depends on #N` line each; with `--op-id`, a last line `op-id: <id>` identifies the create for read-only recovery below. Title at most 80 characters; each body line at most 240. Use short imperative sentences: Goal names the user outcome; each Acceptance names a visible check; Scope names a boundary. Keep headings on their own lines and one blank line between sections. More than eight checks: split before filing (R2).
**Create claim (R1, R12, R13).** `add --op-id` needs the owner's `create_claim_issue` and a board that passed the § 3 read-after-write test. The first trusted, unedited `taskq: create-claim <id>` comment owns the op id forever and binds the request by `request-sha256`; changed input is rejected. Only the invocation whose claim POST reads back as that winner may send one create POST; every other one reconciles read-only, and unknown evidence never permits a create. `add` without an op id is not idempotent. Detail: [finding tasks](docs/design/finding-tasks.md#contract-detail).
**Finding CLI (R1, R12, R13).** `taskq finding` (§ 5) runs only as the owner-authenticated local CLI on the configured board, with no board or config override. Observation and answer grants never authorize it; remote action grants remain a prerequisite. Source parts are opaque ASCII ids, never paths or URLs; evidence is owner-reviewed text, never collected automatically. Op id `finding.<sha256>` of board and source gives each episode one permanent claim; the create always uses `q-held` and retries read-only; `--start` or a later `start` dispatches the separate `<op-id>.start`, and a failed start never repeats the create. Detail: [finding tasks](docs/design/finding-tasks.md#contract-detail).
Held: `add --hold` labels the issue `q-held` instead of `taskq`, then writes `hold`; it is listed as `held` (whatever its log) and no version admits it. `taskq start N` writes `start`, then adds `taskq`.
Labels: `q-<state>` (projection; `waiting` maps to `q-blocked`); type `code|docs|research|asset`; `p0|p1|p2` (lower first, absent = 2; `p0` passes focus, § 4); `run-<runtime>` (none: any); `prefer-codex|prefer-claude` (soft, § 4 Filter); `host-<name>` (none: any host); `needs-<x>` (only a host whose `has` lists x, § 9);
`assignee-only` (start only when the board's user is an assignee); any other, e.g. `area-maps`. Reserved: `taskq-host`.
## 2. Log and states
A log entry is a comment by a trusted author whose first line is `taskq: <kind> [<arg>] [attempt <id>]`; the rest of the comment is its text. Entries are read in comment-id order. An edited comment (`updated_at` after `created_at`) or an unknown kind is ignored. A person can type an entry by hand; it counts like a command. The CLI form `taskq answer K` or `taskq answer N.K` (no colon, N = this task) also counts as `answer K`. In `ask` a comment whose whole body is K or option K's text (trimmed, any case, `K. ` optional) of the open card counts as `answer K` if one option matches; `fold` ignores other comments (an owner comment, § 4).

`core.rs` is one pure function `fold(n, entries, deps_open) -> Task {state, attempt, role, session, retries, card, result, inbox}`; `inbox` lists the accepted `answer`/`steer` ids of the current attempt. The attempt id is the id of the accepted `spawn` comment; it is the fencing token. An entry that names `attempt <id>` is accepted only when `<id>` is the current attempt. An entry not accepted in the current state is ignored and changes nothing.
Optional last lines `op-id: <id>`, then `revision: <R>`, of an entry are fields, not text; without the op id line a `revision:` line is text. The task's revision is the id of the entry that set its open card, else its attempt, else its last accepted entry (0: none). `fold` ignores an entry whose op id an earlier entry carried; a writer whose entry read back at another revision or ignored edits it (§ 5).

| State | Entry | Next | Notes |
|---|---|---|---|
| (none) | — | `ready`, `waiting` if `Depends on` names an open issue | start of every task |
| (none) | `hold` | `held` | only as the first accepted entry; N-1 ignores the kind |
| `held` | `start` | `ready`, `waiting` if `Depends on` names an open issue | then the writer adds `taskq` (§ 1) |
| `held`, `ready` | `gate` | same | owner gate `required` (§ 7); N-1 ignores the kind |
| `review`, `ask` | `approve <sha>` | same | gate `approved`; owner only (no `attempt`); `<sha>` is the current result |
| `ready` | `spawn worker <rt>:<session> <host>` | `doing` | attempt = this id, role worker |
| `doing` | `result <sha> attempt` | `review` | text: verdict (section 7); option lines make a card (section 2) |
| `doing` | `ask attempt` | `ask` | text: ask card below |
| `doing`, `review` | `requeue attempt` | `ready` | text: reason or fixes; `retries += 1`; 3rd: `ask` with the limit card |
| `doing`, `review` | `gone attempt` | `ready` / `review` | service: observed exit or explicit recovery (§ 4); `retries += 1`; 2nd: `ask` with the limit card |
| `doing` | `steer` | `doing` | text for the worker |
| `review` | `spawn reviewer <rt>:<session> <host>` | `review` | only without a live reviewer; attempt = this id |
| `review` | `ask attempt` | `ask` | reviewer's card; result kept |
| `review` | `close attempt` or `close` | closed | verdict text; written after publication (§ 7); ignored while a gate is not `approved` |
| `ask` | `answer [K]` | state before `ask`, else `ready` | `retries = 0`; delivered: text, else option K, else first line |
| any open | `requeue` | `ready` | by PM/owner: result, card and attempt cleared; `retries = 0` |
| any open | `later` / `failed` | `later` / `failed` | text: reason; attempt ended |
| `later`, `failed` | `requeue` / `close` | `ready` / closed | the only exits |

- `waiting` becomes `ready` when every `Depends on` issue is done (§ 1); an open or unknown one keeps it waiting.
- `gone` in `review` ends only the reviewer; the result stays and a new reviewer is spawned. Emergency interlock ([E1–E5](docs/design/emergency-recovery.md)): under the § 3 emergency hold no `spawn` is written on that host until `service release`; a child whose liveness reads unknown gets no `gone`; `service recover --apply` writes each `gone attempt` with `--op-id` and `--revision` (§ 4).
- `retries` is one counter: an attempt `requeue` that makes it 3, or a `gone` that makes it 2, moves to `ask` with the attempt ended; its `answer` then goes to `ready`. Limit card: a writer whose entry hits the limit appends, unless its text is a card, `Problem:` naming the limit, `1. requeue: …` ★, `2. later: …` and `To answer:` naming only `taskq answer N.K`; the reason's `K. ` lines become `K) ` (N-1 folds the same text). Every move to `ready` clears attempt, card and result.
- `answer K` whose option starts with `close` or `later` runs `close` (§ 7) or `later` instead, only through `taskq answer N.K`: a bare board comment `K` folds as a plain answer; an owner pick of `approve <sha7|sha> ...` approves a gated task only when that SHA matches its current result, including a bare board comment in `ask`. An attempt-bound answer cannot approve.
- Gate states: none, `required`, `approved`, `stale`. An approval binds to the result it names: the next `result` or a move to `ready` makes it `stale`, which blocks like `required` until an `approve` of the new result. The gate blocks only `close` in `review` (its publication and the closed issue that frees `Depends on` tasks); a fold from the board after any restart keeps it (R1). Closing a `later`/`failed` task stays the owner's own act.
- After an entry is accepted, the writer sets the `q-<state>` label; every service pass fixes labels that differ from the fold. A hand-moved label is overwritten: people change state with an entry.

### Ask card
`ask` writes, in order, at most nine nonblank lines, without headings or blank lines inside the card:
1. `Done: <what was checked or attempted>` -- one line, at most 160 characters; say `not started` when true.
2. `Problem: <decision needed and user effect>` -- one or two lines, at most 240 characters per line.
3. Optional `Evidence: [<label>](<url>)` -- one line, at most two screenshot/video/issue/PR links, labels at most 40 characters each.
4. Two to four options, `1. <action and trade-off>` etc.; one line each, at most 160 characters, exactly one ends in `★`. None: an owner action, its Problem the action; no attempt starts while it waits, its `answer` resumes the same session.
5. To answer: `taskq answer N.K` or comment `K` or the option text; an owner action: `taskq answer N --text <done>`. Last line; substitute this task's number for N.
Presentation and tray card rules: [answer card](docs/design/answer-card.md#contract-detail).
`--text` supplies literal Done and Problem lines; `--link` supplies Evidence; `--option` and `--recommend` supply the options/star.

## 3. Attempts, lease, capacity
- **Claim.** A service that admits a `ready` task posts `spawn worker`, re-reads the comments and starts the child only if `fold` accepted its own `spawn`; a loser posts nothing more. Same for `spawn reviewer`. `ponytail:` needs read-after-write order of comment lists, verified per board by a two-host test before use (R12); a guard label around `spawn` is the upgrade path.
- **Fencing.** The child gets `TASKQ_TASK=<N>` and `TASKQ_ATTEMPT=<id>`; its commands add `attempt <id>`; `fold` ignores a replaced attempt's late writes. With `TASKQ_ATTEMPT` set, `result`, `ask`, `requeue` or `gone` is refused before any write, naming both, when `TASKQ_TASK` is not `<N>` or the attempt is not live; a retry of a seen op id returns its first receipt.
- **Lease** = the attempt's host heartbeat (§ 4) is fresh and lists `#<N> <id>`. No timestamps in the task.
- **App lease.** [Detail](docs/runtime-qualification.md#contract-detail).
- **Recovery.** Missing heartbeat or restart means unknown, never exit. Replacement, reviewer and continuation require prior execution release. Delivery requires exact-input acceptance, not intent or exit; confirmed no-start permits retry. Reuse board/native identity; persist only missing recovery data. [Execution ownership](docs/runtime-qualification.md#execution-ownership) defines status, proof and qualification; task state never proves release.
- **Capacity** is host-wide: `<install>/host.json` runtime limits minus occupied slots in all registered projects, reviewers/resumes included. Key: project identity + attempt. Pending grant and running child occupy one slot, counted once for runtime limits, admission.max and project caps; pending-to-running adds none. Optional project `limits` only lowers its share: remaining = min(host remaining, project remaining). Missing runtime limit: no ceiling; 0 disables. Lowering never stops children (R11). Validate host.json/pass; invalid/unreadable policy holds new launches as unknown, keeping children and leases.
- **Load gate** (host policy, § 9) holds every new child (claim, reviewer, resume) while CPU busy >= `cpu_max` % or available physical memory <= `memory_min` %; running children continue. A missing, invalid or stale reading holds; reopening needs three consecutive valid samples below the band; at most one launch per 30 s. A held resume keeps its inbox; a held won claim stays leased. No battery or thermal gating, no forced retirement. Serialize slot grants and transitions; release only after verified failed launch/exit. Choose ready projects round-robin; resumes/reviewers keep precedence. Count legacy work during drain; migration admits nothing new.
- **Host admission.** In-process grants follow the host load gate, admission.max, runtime limits and 30 s spacing. No Fixed mode. Hold new admission host-wide until all legacy services drain and exit; existing attempts keep leases and may resume to finish. Unknown legacy liveness holds admission.
- **Emergency hold.** `<install>/hold` refuses every launch on the host before the load gate until `service release` removes it; an unreadable file holds; live children run on; older services ignore it. Detail: [capacity](docs/design/capacity.md#contract-detail).
- **Cancellation** = `requeue`, `later`, `failed` or `gone`; the owner stops the child (R11). These task transitions never release execution; unknown termination stays fenced.
## 4. Service
`taskq service run`: one host process for `<install>/projects`, one loop thread per root; `service install` registers a project and persists the process (§ 8). A project panic restarts only its thread, reattaching running children; three panics in 10 minutes quarantine it (reap, heartbeat, `status.json` only) until `service restart`.
One loop:

1. Reap exact native executions per the [adapter matrix](docs/runtime-qualification.md#adapter-recovery-matrix). Missing or unsupported observations stay unknown. A turn terminal requests owned-tree stop where needed; confirm the execution boundary before release. For an observed exit of a current attempt without `ask`/`result`/`requeue` since start, post `gone` with exit code and bounded last worker line (§7 rule 6). A hand-in preserves its task outcome; step 6 handles new inbox input.
2. Stop children whose attempt is no longer current (R11). Remove worktrees of closed tasks (§ 7).
3. Write the heartbeat issue `taskq host <name>` (label `taskq-host`) every 60 s or on state change (rate-limit failures read stale, never exit): lines `version <v>`, `service <id>`
   (12 hex of SHA-256 of `<install>/installation-id`), `machine <hostname>[ wsl]` (the `hostname` output, as agentq `host.name`; `wsl` under WSL; DashQ joins Hosts rows by it, [dashq hosts](https://github.com/taskqorg/dashq/blob/main/docs/design/hosts.md) H2), `#<N> <id>` per live child or launch held by the load gate, `session #<N> <id> <url>` per live Claude child with a Remote Control URL, `focus off|unknown` when the focus admits nothing, plus `at <board time>` (a same-body edit keeps `updated_at`). Freshness uses the board's `updated_at` and the response `Date`, never local clocks.
4. Reconcile unresolved executions; unreachable owners remain unknown (§ 3).
5. Fix projected labels; `waiting` with closed deps becomes `ready`. Research/proposal decisions use `ask` (§ 7.5), not closed results.
6. Resume the session of a live attempt for a new `answer` or `steer` (text on stdin); spawn a reviewer for `review` without a live one; admit `ready` tasks matching this host by priority then number within capacity.
7. Host update check (§ 8): every host.json `update_every` (60 s) or any `<root>/.taskq/update`; installed service applies newer versions, others report. Log the outcome in every project log.
8. Sleep until a poke or `poll` seconds.

- Filter: `host-*` absent or this host; workers use `run-*` when present, else a `prefer-*` runtime with a free slot, else the runtime with the most free slots (first listed on a tie), so any-runtime tasks alternate; `run-*` wins over `prefer-*`, and both `prefer-*` labels are ignored with one log line per pass; reviewers prefer the other runtime than the accepted worker (`claude` ↔ `codex`, `codex-app` → `claude`) with free capacity, falling back to the worker's runtime. Other filters remain: `assignee-only` passes; each `needs-*` in `has` (`needs-gate`: every host of a version with gates, § 7); `codex-app` keeps its §9 opt-in.
- Focus: `taskq service focus all|off|<label..> [--request TEXT]` writes `<root>/.taskq/focus`: `all`, one of the labels or `p0` passes; none or `off` (default) admits nothing, heartbeats and updates go on; capacity reason `focus` and the heartbeat say so. `service install` writes `off` when the file is missing, else keeps it. `--request` keeps the owner's words in `focus.request`; a focus without it removes the file. No arguments: print focus, `has`, labels of open tasks; an agent maps the owner's words to these, asks when unsure, says so when none fits.

Emergency (E1–E5): under the § 3 hold the loop still reaps, stops replaced children and beats; unknown liveness never becomes `gone`; `service recover` proposes and `--apply` writes fenced `gone` ops. Detail: [emergency recovery](docs/design/emergency-recovery.md#contract-detail).
- Poke: [shared command receipts](docs/design/profiling.md#service-wakeups); signals use `<root>/.taskq/poke` or `<install>/poke`. Each pass
  writes `<root>/.taskq/status.json` for `service status`, tray and DashQ: coreq.md common keys, service state, § 5 snapshot (`tasks` with § 2 `revision`; failed passes keep rows with `complete` false), `capacity` (limits, gate, admission, reservations), `requests`, `incident`, `agents` (§ 5, probed at most every 5 minutes) and § 8 `access`. Failed publication is logged, blocks release-health marking and preserves supervision ([contract](docs/design/profiling.md#service-wakeups)).
- Events: a pass appends to `<root>/.taskq/events` one line `<board time> #<N> close|failed|ask|blocked|gone <id>` per observed move to closed, `failed`, `ask` or `waiting` and per new `gone` entry; 30-day bound; moves while no service ran are missing. Detail: [menu](docs/design/menu.md#contract-detail).
- One service per host: `service run` waits while `<install>/service` (the service's pid) is under 60 s old and names another live pid; a project thread waits while its `status.json` under 60 s old names another live pid; a pass that finds this host's heartbeat under `ttl` naming another `service <id>` writes nothing and fails with `another service <id> runs as host <name>`. - AI requests ([AI workspace](docs/design/ai-workspace.md#contract-detail), menu M7, M10): the tray writes `<root>/.taskq/requests/<id>.json`; the service runs one operator (R3) turn at a time per project. Owner comments on `ask` tasks and Add project (M10) become requests too; setup effects follow § 6. Request log: `<root>/.taskq/requests.log`.

Setup and the shipping update disclose destination and opt-out before any send. Only a catalog fault reports, with an allowlisted payload; a report never changes a task, the queue or an exit code.
- Data: [bounds](docs/design/host-service.md#contract-detail), `src/data.rs`: telemetry SQLite/WAL (30 days / 64 MiB total, shared capture; legacy import locked); text logs hourly.

- Log and board budget: [contract detail](docs/budget-1032.md#contract-detail) owns counting, pause and alarm formats. The board user's 5000 requests/h serve all hosts and clients; at <=20 % remaining log once per reset and show the alarm in service status/list and R6.

- `requeue`, `later`, `failed`: `Reason: <blocker>` then optional `Next: <fix>`; at most 2 lines, at most 240 characters each.
- `answer --text` and `steer`: at most 4 lines, at most 240 characters each; one decision/instruction per line, no invented context.
- `service focus/list/status`: named project, focus, counts, freshness and unknown reason; one field/item per line, at most 160 characters.
- `update`, `cleanup`, setup and `selftest`: one outcome per version/path/check ([Core Write][sq-write]).
- Help keeps full command syntax; `inbox`, raw service logs/status JSON and original issue/log text are exempt from display caps ([verbatim diagnostics][sq-sink]).
- Unused positional arguments are refused before any action: `unused positional arguments: <arguments>`; repeat value flags for multiple items.
- Commands add `attempt $TASKQ_ATTEMPT` when it is set. A command refused by `fold` prints the current state. `TASKQ_ROOT` must contain the current directory when that directory lies in a taskq project (a folder with `taskq.json` here or above), else every command is refused `TASKQ_ROOT <root> is not the project of the current directory <dir>`: a reused session's stale environment never writes into another project.

An entry that a concurrent write beat on readback (other revision, raced op id, ignored) is edited by its writer: `stale`.
- Receipt: `--json` prints one object `{task, op_id, outcome, state, revision, reason, next}`; outcome `accepted` (readback state), `rejected`, `stale` or `unknown` (written, no readback: `Next:` reads `inbox N`, retries the same op id); else the lines above.

## 7. Worker, reviewer, publication
Worker brief: task text, attempt, branch, delivery commands, this file's path (this release's URL when the root has none), the folder rule (§ 8), the CI-wait rule (rule 7). The task grants these commit/publication steps ([shared approval boundaries][sq-approval]); nothing outside them is approved. Rules:
1. Read this file and the whole issue first, then [prepare the task][sq-prepare]: a decision conflict (R13), an untestable or ambiguous Acceptance item or a split (R2) is an `ask` with options before any code.
2. Workspace: `git worktree add -b taskq-<N> .worktrees/taskq-<N> origin/main` (existing branch: continue it). `workspace: external`: the path the project's `AGENTS.md` gives.
3. Owner: `ask`. External blocker: `later` with failed check + one unblock condition; resume only after proof. Code fix: `requeue`. Then stop.
4. Before `result`: commit to `taskq-<N>` with `Task: <issue url>`; rebase on `origin/main`; run checks; list outcomes in `--checks`. `result` names and refuses changed `uiSources` files whose SHA blobs `docs/shots/manifest.json` omits (fix: `docs/shots/update.sh`); Readable SHA, no manifest: skip; other Git/manifest errors: unknown, refuse. Test changes follow [specq testing](https://github.com/taskqorg/specq/blob/main/engineering/testing.md): name the defect and retained risk protection in `--text`; change a rule only when accepted behavior or protection changes. Fix `--checks`: [before/after evidence](https://github.com/taskqorg/specq/blob/main/engineering/verification.md#run-policy-by-stage) or its limitation. Sandbox-blocked host tests print `sandbox-blocked`; Checks: that marker, never PASS. Do not requeue; gate: green exact-result-SHA CI (R12).
5. Delivery `direct`: push `taskq-<N>`. `auto-merge`, `review-pr`: push and open one PR/MR into `main`. Then `result --sha <sha>`; do not wait for CI, `close` checks it. Research/proposal tasks (type `research`, docs proposals) end with `ask`: options and one recommendation. No `result`/`close` before the owner answers. Then deliver the approved outcome or file approved dependents; closure still needs review. No commit: `--sha` = current `origin/main`.
6. Everything written through taskq is public: no secrets, tokens or local paths.
7. CI wait, worker or reviewer: at most one poll a minute (`gh pr checks <PR> --watch --interval 60`); never `gh run watch`, which polls every 3 s, or `gh run view` without `--json`.

### Result and close verdicts
`result` body: `Changed: <user effect>` (1-2 lines), `Checks: <command -- outcome>` (one line per check, 1-8 lines),
then `Open: <remaining item|none>` (1-2 lines); at most 12 lines, at most 240 characters per line. Keep exact commands and platform qualifications (R12).
`--text` supplies literal Changed and Open lines, then a decision card's Done/Problem lines in the § 2 Ask card format, with `--option`, `--recommend`, `--link` (none: no card fields); `--checks` supplies unprefixed command/outcome lines, each rendered with `Checks:`. SHA stays in the log header; one PR/evidence link may share Changed and carry the [shared risk description](https://github.com/taskqorg/specq/blob/main/caveman/rules/changes.md#merge-request-description-markdown) for either publication route.
`close --text` supplies all three labelled fields in the same order and limits; Checks names each `A<k> ok|gap|unknown` plus exact-SHA CI outcome, not a vague PASS.
Reviewer checks every Acceptance and contract against the candidate and CI on that SHA, waiting per rule 7; `Checks:` follows [shared review](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#review), within the same verdict limits. A research or proposal task without an `ask` and owner answer before `result`/`close` is a task-fit gap. Requeue only for Acceptance/contract gaps; advisory findings go in `Open:`. Then `close --text <verdict>`, `requeue --text <exact fixes>` or `ask` with options. PM relays the verdict verbatim, links intact.

`close` publication goes through the board API only:
- `direct`: branch `taskq-<N>` equals the result SHA, `main` is its ancestor, CI green on that SHA; move `main` to it
  without force, read back, close. GitLab has no fast-forward ref API: `direct` there merges a fast-forward MR.
- `pr`: exactly one open PR/MR of `taskq-<N>` at the result SHA, current `main` its ancestor (else `requeue`: rebase), CI green on its head; `main` refuses a stale head at merge time (GitHub: a ruleset requiring branches up to date that the token can never bypass, or readable protection requiring it with admins enforced; GitLab: fast-forward or semi-linear merge method), else refuse; mark a draft GitHub PR ready; squash-merge with the title and
  all `Task:` lines; read the merge back; close. Incident ancestry checks in this same close use the returned merge SHA for squash publication, the result SHA for direct publication; later human moves are never read.
- No commit (research, or SHA already on `main`): verify ancestry, close.
- Pending or missing CI: refuse, state unchanged. Failed CI or conflict: `requeue` with the message.
- On the attempt host: remove a clean `.worktrees/taskq-<N>` and its local branch; dirty ones stay.
- Merged, not closed (a partial publication, or a PR/MR into a release branch, which never closes its issue on merge): with no open PR/MR of `taskq-<N>` into `main`, `close` finds the merged one of `taskq-<N>` into any base whose head is the result SHA and closes with that one receipt (`merged #P [into <base>] as SHA`): no second merge, no requeue. From a reviewer's `ask` (result kept) an owner `close` option runs it (§ 2); `doing` or a worker's `ask` has no result to verify: `later`, then `close`.

**Delivery presets** are § 9 `delivery` `{preset, revision}`, the owner's (R9; revision +1 per owner edit): `auto-merge` (the `pr` route), `direct`, `review-pr` (`pr` after the owner gate). `local` and `push-branch` are refused. Without `delivery`, `publish` names the preset at revision 0. `close` ends its verdict with `delivery <preset> r<revision>: <receipt>`. Detail: [agent behavior](docs/design/agent-behavior.md#contract-detail).

### Recipes and owner gates
A recipe (P5) is a task list in § 9 `recipes`; `taskq recipe NAME --run ID` adds its tasks held through the § 1 create claim with stable op ids, so a rerun returns the first receipts; nothing starts before every task reads back and `--start` or `taskq start N`. A `gate: true` task or a `review-pr` project needs an owner `approve` of the exact current result before `close` publishes; dependents wait for its close. Detail: [plans and decisions](docs/design/plans-and-decisions.md#contract-detail).

1. A merged version PR is the release ([specq#59](https://github.com/taskqorg/specq/issues/59)): a main push that changes the `Cargo.toml` version tags `v<version>` if absent (an unreadable prior version fails, untagged) and publishes in that `release.yml` run, as a manual tag push does; tags never move; rollout reads heartbeats. 2. CLI/service updates serialize under `<install>/update.lock`, then run coreq; new `current` gets the `<install>` allowlist sweep.
3. An installed service older than `current` re-execs through the launcher. Windows CLI descendants share a native Job Object. CLI children use protected [native handover](docs/runtime-qualification.md#adapter-recovery-matrix); active Claude, codex-app or operator turns defer it.
4. The service marks its version `healthy` after `rollback_after`. Children keep running from their own release folder: no drain, no manual resume, no blocked user command.
5. `service install` registers the exact root and [hands over to the host unit](docs/design/host-service.md#migration): immutable binary replacement, preserved work, verified legacy exit and host ownership before rollback-floor recording. Unknown liveness forbids removal/reload; current work follows protected handover above. Windows setup runs outside MSIX; host rollback counts starts. macOS signing: [worker permissions](docs/design/worker-permissions.md#contract-detail).
**Compatibility N/N-1.** v4 releases differ only by additive log kinds that N-1 can ignore without a different fold. A change that N-1 cannot ignore needs a cutover like § 9. N-1 reads op id and revision lines as text (its cards and deliveries show them). N-1 ignores `gate` and `approve`, so it would close a gated task: `needs-gate` keeps its services from spawning workers or reviewers for one, and an N-1 operator's `close` stays the owner's own act. Hosts update independently in any order.
**Contract size (R8).** `taskq.md` stays within 300 lines and 60 KiB, enforced by the § 2 golden-trace test in `src/core.rs`.

## 9. Config and cutover
`taskq.json` beside the project root:
- `board` `github|gitlab`; `repo` `owner/name`; `host` the board's web host (default `github.com`, `gitlab.com`).
- One module per board under `src/board/` (`github.rs`, `gitlab.rs`): its API, token lookup, login probe, CLI, env and default host. The `Board` trait and `src/board/mod.rs` (shared HTTP, registry by name) are the only contract; core, service and operator never branch on the board kind, and editing one board never touches another's module.
- `label_schema` `canonical|legacy` (absent: legacy if the board has `priority-1|2` or `q-waiting` objects, else canonical). Both names work in priority and focus/status filters; `p0` has no legacy name; logs keep `waiting`. Canonical writes on existing boards need all-host compatible release/idle approval; legacy objects and closed issues stay, only open issues are reassigned.
- `publish` `direct|pr`, `delivery` (§ 7); `workspace` `external` keeps host-owned worktrees.
- Host-owned `<install>/host.json`: `hosts` (hostname → name; TASKQ_HOST override), `has` (name → capabilities), runtime `limits`, `admission` {"max": n}, `load_gate`, `codex` args, `permission_mode` (R9). Local policy only; no capacity_hosts/mode. Keep Auto/D03 defaults; migration never silently enables a gate or changes runtime permissions.
- `add --prefer codex|claude` writes one soft `prefer-<rt>` label ([specq runtime preference](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#runtime-preference)); two values or another runtime are refused; workers take it only while that runtime has a free slot here (§ 4 Filter). Opt-in `codex-app` (macOS, Windows): only on hosts whose `has` lists it, only for `run-codex-app` tasks (`add --runtime codex-app`); reviewer chain checks keep app-worker cases on macOS and Windows and none elsewhere. A screen task adds `needs-screen` (`has` `screen`). macOS evidence tasks: [runtime qualification](docs/runtime-qualification.md#macos-evidence-tasks). Answering a real ask stays the owner's act.
- Project taskq.json keeps board/repo/board host, publish/delivery, workspace, labels, recipes, incident_reports, pages, assignee and other project keys; optional `limits` only lowers host limits. No host identity, capability, model/permission or admission copies. Token lookup and worker-policy grants (§ 8 Access) stay unchanged; host flags never grant access.
- `recipes` `{name: {"version": V, "tasks": [{"title", "goal", "acceptance": [..], "scope", "deps": [earlier 1-based index..], "gate", "type", "runtime", "priority", "host"}]}}` (§ 7).
- `<install>/projects` is the explicit owner-approved list of exact roots (R10). Drain a removed root before retiring its thread; keep status until verified exit. [Six-copy migration](docs/design/host-service.md#six-copy-configuration-migration) compares inputs before writes; conflicts/unknowns hold launches. Keep originals, unknown keys and ownership; replacement resumes idempotently.
- `ttl` and `poll` stay per project (300 and 60 s); `update_every` and `rollback_after` move to host.json (60 and 600 s). Missing/invalid host policy reads unknown and holds launches; it never falls back to per-project copies.
- GitHub token: one owner-installed credential per host in `<install>/token` (owner-only access), shared by service and workers; a fine-grained PAT preferred, an OAuth token accepted. No env or CLI-login fallback; TaskQ, workers and setup never run `gh auth login`; a missing, empty or unreadable token is an owner item, same error in service and worker. Never in config. GitLab keeps coreq token lookup and `Authorization: Bearer`.

A cutover is one step per project, not per host: two board formats do not mix. No migration code: `CHANGELOG.md` says per release what changed on the board and what an open issue needs. An agent reads the entries from the board's version to the new one, prints a plan per open issue and asks the owner about issues the new format cannot hold. After the owner's OK, with old services and children stopped, it applies the plan with `taskq` commands and issue edits. Closed issues are never touched. New services start: Mac, then Windows. Repair is the same agent procedure for one project; it warns when `status` shows another host's fresh heartbeat.
