# taskq contract
taskq runs a queue of agent tasks on a GitHub or GitLab issue board. This file is the whole contract: states, log, roles, lease and fencing, compatibility and deployment. History of decisions lives in git and issues; operational state on the board (R1).
This file specifies **v4**, the Rust binary from `src/`.
## Principles (R1–R13)
### Change rule
A task that changes a rule names its R-number, edits this file in the same deliverable as the code and lists the amended R-numbers in its result. A changed rule keeps its number. A new rule gets the next one. A rule elsewhere that disagrees with this file is a defect. No history here: no dates, no decision logs; at most 300 lines.
### R1. The board's own objects are the only state
No machine block in issues. State is what a person sees: labels, the issue text, `taskq:` comments (§ 2) and host heartbeat issues (§ 4). The comment log is the truth; labels are its projection. Local files are caches that a restart rebuilds: no local DB, receipt store, queue or lock. Exception: accepted [DashQ connection state](docs/design/enrollment.md) (identity/grant/revoke and coalesced projection, never task truth); AI request files, the tray's request history, the request log, local incident/profile records (§ 4) and the host admission file and lock and the emergency hold file (§ 3); the host operator's [resource grants and operation receipts](docs/design/shared-resource-controls.md#host-adapter) (`resources/`); they hold no task state. The `pid` of a fresh `status.json` is the one-service-per-root check (§ 4), not a lock.
### R2. One task, one attempt
A task has at most one live attempt: one worker or one reviewer process. Work bigger than one reviewable diff follows [shared task preparation](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#prepare-the-task), using tasks linked by `Depends on #N`. A live attempt is never moved to another host or session; a new attempt replaces it (§ 4).

### R3. Roles
- **Owner**: decides product questions, answers `ask`, accepts or rejects results through the PM.
- **PM** (manager): the agent session the owner talks to. Files tasks, relays questions and outcomes. Does no task work, never answers for the owner. The queue does not depend on a PM being online.
- **Service**: one per host (§ 5). The only process that spawns workers, reviewers and operators.
- **Worker** `T<N>`: a child of the service. Does one attempt, writes `result`, `ask` or `requeue`.
- **Reviewer** `R<N>`: a child of the service, spawned on demand for a result. Checks the exact candidate, then `close`, `requeue` with fixes, or `ask`. No resident supervisor session.
- **Operator**: the owner-facing agent for project research, edits, checks and TaskQ operations (§ 4), with normal runtime tools and project permissions (R9); authority per [shared approval boundaries](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#approval-boundaries), unresolved authority uses clarify/proposal. Task-state writes use TaskQ commands, never hand-edited logs. Its failure does not fail a worker task and does not prove absence of side effects.

Session names: `T<N> <title[:40]> (<host>)` and `R<N> <title[:40]> (<host>)`.

### R4. Comments move the queue
Each command that changes a task appends one `taskq:` comment, sets the projected labels and pokes the local service. Services also poll the board every `poll` seconds. No sender session, timer or PM chat is on the critical path.

### R5. Completion is written to the task
Result SHA, checks, questions and blockers go to the issue as `result`, `ask`, `requeue` comments; completion evidence follows [specq verification](https://github.com/taskqorg/specq/blob/main/engineering/verification.md).

### R6. Human report
`taskq status` renders the [read-model](docs/design/refactoring-backlog.md) snapshot of one board read (§ 5 `--json`; service status, `status.json` and tray count the same rows), in this order (empty parts omitted). Tray/browser project summaries and task rows (metadata/links first, full wrapped title second under M3) reuse [shared project blocks](docs/design/project-blocks.md), including separate Doing/Review, nonzero K counters and unknown Closed until authoritative totals exist:
1. `<project> · [board](<url>)`, preceded while a local `status.json` under 60 s old reports a board rate-limit pause (§ 4) by `Rate limit: board requests paused until <time> (<host>)`, else a low board budget by its § 4 line, also when this read fails.
2. `In work N · Waiting for answer N · Ready N`. In work: `doing` + `review`. Waiting: `ask`. Ready: `ready`.
3. `| Task | State | Runtime | Session |`, one row per open task except `ask`, `later`, `failed`, by priority then number; task and session cells are links; `waiting` rows say `blocked ([#M](url) open)`: each blocking dependency (§ 1) linked, then `open` or `unknown: <reason>`; `status --json` rows add `blocked` (`ref`, `url`, `reason`).
4. `Questions (answer N.M):` and `| Question | Brief reason | Options |` with `N.1 <option> · N.2 <option> ★` (★ =
   recommended), one row per `ask` and per `review` with options; an owner action (§ 2) reads `waiting for owner: <action>`.
5. `Later: [#N title](url), ...` on one line; then `Failed:` with a reason table.
6. `Hosts: <host> v<version> <age>[ focus off|unknown], ...` from heartbeats (§ 4).
7. `Next: 1 <action> ★ · 2 <action>` from the PM ([shared Next contract](https://github.com/taskqorg/specq/blob/main/design/workflow.md#ai-assisted-controls)).

Display titles at most 60 characters, reasons at most 160 and option text at most 120; show ellipsis with an issue link for the full text. Keep every row and option, counts and answer tokens; no total report cap. Cells pass one formatter: newline becomes space; `|`, `[`, `]`, `\` are escaped. Claude links use only the Remote Control URL registered by that native session; the local UUID is not a remote ID. Codex links: `codex://threads/<id>` when `TASKQ_CLIENT=codex`, else `<pages>/open.html#codex://threads/<id>`.

### R7. Style
Follow [specq Core](https://github.com/taskqorg/specq/blob/main/caveman/rules/core.md) and its applicable profile; project documents follow [Documentation](https://github.com/taskqorg/specq/blob/main/caveman/rules/documentation.md) in English.
Single and batch CLI outcomes use the same success/error renderer; a failed item keeps its task number.
Owner-text templates in sections 1, 2, 4, 5, 7 are the design target; release them with their implementation (R8), not as proof of shipped behavior.
Limits count logical lines and Unicode characters, including labels and numbering; exclude blank separators and the log header.
Link targets and exact commands/SHAs/paths are exempt from character limits, not line limits; link labels stay short.
Commands refuse over-limit new input before writing, naming the excess; historical/hand-written entries fold unchanged; compact displays use ellipsis and a link (stored text verbatim: [Core Write](https://github.com/taskqorg/specq/blob/main/caveman/rules/core.md#write), [source and sink](https://github.com/taskqorg/specq/blob/main/caveman/rules/changes.md#keep-the-source-and-sink-separate)).

### R8. The contract is the SoT and matches code
Apply [shared spec-first rules](https://github.com/taskqorg/specq/blob/main/engineering/spec-first.md) to this contract (code and contract in one deliverable); every §2 table row has a golden trace, and this file stays within 300 lines.

### R9. No silent changes to model, effort or permissions
Name any change to the owner first. `permission_mode`, `codex` and capacity (§ 9) in `taskq.json` are the owner's: agents propose capacity, apply it only on the owner's explicit instruction. Worker access comes only from operator-owned grants (§ 8 Access; [worker permissions](docs/design/worker-permissions.md) P1–P4; [permission authority](https://github.com/taskqorg/specq/blob/main/engineering/permission-authority.md)): project config, task text, labels and board answers may request or narrow access, never grant it. Legacy defaults (requests, not grants): Claude `--permission-mode dontAsk`; Codex `-s danger-full-access`. The operator (R3) uses the same configured CLI permissions, § 8 Access and host board environment as workers; no tool-free override, silent elevation or runtime fallback. Owner requests grant their stated scope; setup external effects still require §6 confirmation.

### R10. Multi-project only by explicit list
A PM manages several projects only from an owner-written list; folders are never discovered. One report per project. An
`N.M` answer that could match several projects needs the project named first.

### R11. Retire sessions only after their attempt ends
A worker or reviewer is stopped only when its task is closed or parked or its attempt is replaced, emergency recovery included (§ 4). Identity is the recorded native session ID, never a name match; a completed Claude background turn is stopped after native completion readback, and a CLI child after its log shows the turn ended (§ 4 step 1), each with its conversation retained for the next turn. Uncommitted work is never lost: only `cleanup --force` removes it, after saving it to `<root>/.taskq/trash/taskq-<N>.patch`.

### R12. Unverified means unknown
Follow [shared verification rules](https://github.com/taskqorg/specq/blob/main/engineering/verification.md). TaskQ readback and platform obligations are specified in §§4–8. Chain checks ([test classes](https://github.com/taskqorg/specq/blob/main/engineering/verification.md#test-classes)) are `cargo test --locked` and `taskq selftest`, both in CI. The [runtime qualification matrix](docs/runtime-qualification.md) is the bounded live acceptance, rerun only when its runtime path, permissions or client version changes; it is not a per-commit gate. Design prototype tests under `docs/design/` are development checks: not in CI; they write evidence only on request. Browser instruments (`tests/*.browser.cjs`, prototype tests) launch through `tests/browser.cjs`: Playwright's chromium headless shell by default; `PLAYWRIGHT_CHANNEL` picks an installed browser outside a worker only, and a worker (`TASKQ_TASK` set) ignores it with one log line, because the Google Chrome app aborts at startup under the macOS service and leaves a crash dialog. Tray screenshots run only when a check needs them and capture only the routes the diff changes (`tray --snapshot DIR --route R,..`); the full matrix (every route, both themes, 16/20 px; [native matrix](docs/design/ui-acceptance.md#native-matrix)) runs only for README shots and release qualification.

- Last README line: `If taskq saves you time, [buy me a coffee](…).`## 1. Tasks
A task is an open issue by a trusted author (GitHub `OWNER|MEMBER|COLLABORATOR`, GitLab Reporter+) labelled `taskq` (`taskq add` sets it; on the board a person adds it). Any other issue never starts: a PM makes a task from it with `taskq add` and comments on it when the task closes. A closed issue is done, unless the board records that it closed without completing (GitHub `state_reason` other than `completed`, e.g. `not_planned`): such a dependency reads unknown, never done (R12; GitLab records no reason). The issue text is for people and may be
edited by hand: `## Goal`, `## Acceptance`, optional `## Scope`, one line `Depends on #N` per dependency; `Depends on <repo>#N` names an issue of another repository on the board's host, read with the board's token (`<repo>`: `name` under the board's owner, or `owner/name`). An unreadable dependency reads unknown. Acceptance items are `A1.`, `A2.`, never renumbered; each an observable result a reviewer checks without reading the code.
`add` writes these sections in that order, then dependencies: Goal 1-2 lines; Acceptance 1-8 items, one line each;
Scope optional, 1-4 bullet lines; dependencies one `Depends on #N` line each; with `--op-id`, a last line `op-id: <id>` identifies the create for read-only recovery below. Title at most 80 characters; each body line at most 240. Use short imperative sentences: Goal names the user outcome; each Acceptance names a visible check; Scope names a boundary. Keep headings on their own lines and one blank line between sections. More than eight checks: split before filing (R2).
**Create claim (R1, R12, R13).** `add --op-id` requires the owner's `create_claim_issue` (positive issue number on this board, trusted author, not a task/held/host issue). The first trusted, unedited `taskq: create-claim <id>` comment by comment-id order owns the request permanently; its second line `request-sha256: <hex>` binds actor, title, complete body (including source reference), labels and later text. Changed input is rejected. Only the invocation whose claim POST returns that winning comment id and whose full comment readback matches may issue one create POST. This uses the §3 board read-after-write ordering qualification; unqualified boards must not enable it. Never edit/delete claims or change the configured issue while operations exist; older clients cannot participate safely and must not submit these creates.
Claims never expire or transfer, including a crash before create. Any other invocation reconciles read-only against all open and closed issues carrying the same op id; exactly one trusted issue with matching title/body returns its readback receipt. Missing, conflicting, duplicate or unreadable evidence remains unknown; legacy issues without a claim are refused for owner reconciliation. An unknown claim POST cannot authorize create; an unknown create POST never permits another create POST, even after restart or an empty list. Drafts stay with the consumer; incomplete hold/start application is separate from discovery and receives no recovery write here. Creates without an op id retain their existing non-idempotent behavior.
**Finding CLI (R1, R12, R13).** `taskq finding <title> --board URL --source installation/rule/episode --goal G --acceptance A.. [--evidence E..] [--start]` uses the owner-authenticated local CLI and configured board only; URL must equal the snapshot's board URL. Observation/answer grants authorize neither this CLI nor a remote consumer; remote action grants remain a prerequisite. No board/config override is accepted. Each source part is an opaque 1-64 character ASCII identifier, excluding dot-only parts (`A-Z a-z 0-9 . _ -`), not a path or URL. Evidence is owner-reviewed text (at most four bullet lines of 240 characters), never automatically collected; consumers sanitize it and retain drafts on cancellation, rejection and unknown outcomes.
The operation id is `finding.<sha256>` of board identity and source, independent of actor/content, so the same episode on this board always takes the same permanent claim. The claim binds actor, board, reviewed body, labels and the explicit start choice; changed input is rejected. Finding creates always use `q-held`, with no execution eligibility; successful create readback is reported independently of optional `start`. A create retry is read-only; an explicit `--start` or standalone `start` may initialize the held log and dispatch the separate idempotent `<op-id>.start` operation on the discovered issue. A failed/unknown start retains its issue and never repeats create. `start` acceptance proves eligibility under focus/permissions/limits, not worker launch or source recovery. JSON is `{create: receipt, start: receipt|null}`; text prefixes each outcome with `Create:`/`Start:`. No new lifecycle states or local draft store.
Held: `add --hold` labels the issue `q-held` instead of `taskq`, then writes `hold`; it is listed as `held` (whatever its log) and no version admits it. `taskq start N` writes `start`, then adds `taskq`.
Labels: `q-<state>` (projection; `waiting` maps to `q-blocked`); type `code|docs|research|asset`; `p0|p1|p2` (lower first, absent = 2; `p0` passes focus, § 4); `run-<runtime>` (none: any); `prefer-codex|prefer-claude` (soft, § 4 Filter); `host-<name>` (none: any host); `needs-<x>` (only a host whose `has` lists x, § 9);
`assignee-only` (start only when the board's user is an assignee); any other, e.g. `area-maps`. Reserved: `taskq-host`.
## 2. Log and states
A log entry is a comment by a trusted author whose first line is `taskq: <kind> [<arg>] [attempt <id>]`; the rest of the comment is its text. Entries are read in comment-id order. An edited comment (`updated_at` after `created_at`) or an unknown kind is ignored. A person can type an entry by hand; it counts like a command. The CLI form `taskq answer K` or `taskq answer N.K` (no colon, N = this task) also counts as `answer K`. In `ask` a comment whose whole body is K or option K's text (trimmed, any case, `K. ` optional) of the open card counts as `answer K` if one option matches; `fold` ignores other comments (an owner comment, § 4).

`core.rs` is one pure function `fold(n, entries, deps_open) -> Task {state, attempt, role, session, retries, card, result, inbox}`; `inbox` lists the accepted `answer`/`steer` ids of the current attempt. The attempt id is the id of the accepted `spawn` comment; it is the fencing token. An entry that names `attempt <id>` is accepted only when `<id>` is the current attempt. An entry not accepted in the current state is ignored and changes nothing.
Optional last lines `op-id: <id>`, then `revision: <R>`, of an entry are fields, not text; without the op id line a `revision:` line is text. The task's revision is the id of the entry that set its open card, else its attempt, else its last accepted entry (0: none). `fold` ignores an entry whose op id an earlier entry carried; a writer whose entry read back at another revision or ignored edits it (§ 5).

| State | Entry | Next | Notes |
|---|---|---|---|
| (none) | — | `ready`, `waiting` if `Depends on` names an open issue | start of every task |
| (none) | `hold` | `held` | only as the first accepted entry; N-1 ignores the kind |
| `held` | `start` | `ready`, `waiting` if `Depends on` names an open issue | then the writer adds `taskq` (§ 1) |
| `held`, `ready` | `gate` | same | owner gate `required` (§ 7); N-1 ignores the kind |
| `review`, `ask` | `approve <sha>` | same | gate `approved`; owner only (no `attempt`); `<sha>` is the current result |
| `ready` | `spawn worker <rt>:<session> <host>` | `doing` | attempt = this id, role worker |
| `doing` | `result <sha> attempt` | `review` | text: verdict (section 7); option lines make a card (section 2) |
| `doing` | `ask attempt` | `ask` | text: ask card below |
| `doing`, `review` | `requeue attempt` | `ready` | text: reason or fixes; `retries += 1`; 3rd: `ask` with the limit card |
| `doing`, `review` | `gone attempt` | `ready` / `review` | service: child exited or lease expired; emergency recovery (§ 4); `retries += 1`; 2nd: `ask` with the limit card |
| `doing` | `steer` | `doing` | text for the worker |
| `review` | `spawn reviewer <rt>:<session> <host>` | `review` | only without a live reviewer; attempt = this id |
| `review` | `ask attempt` | `ask` | reviewer's card; result kept |
| `review` | `close attempt` or `close` | closed | verdict text; written after publication (§ 7); ignored while a gate is not `approved` |
| `ask` | `answer [K]` | state before `ask`, else `ready` | `retries = 0`; delivered: text, else option K, else first line |
| any open | `requeue` | `ready` | by PM/owner: result, card and attempt cleared; `retries = 0` |
| any open | `later` / `failed` | `later` / `failed` | text: reason; attempt ended |
| `later`, `failed` | `requeue` / `close` | `ready` / closed | the only exits |

- `waiting` becomes `ready` when every `Depends on` issue is done (§ 1); an open or unknown one keeps it waiting.
- `gone` in `review` ends only the reviewer; the result stays and a new reviewer is spawned. Emergency interlock ([E1–E5](docs/design/emergency-recovery.md)): under the § 3 emergency hold no `spawn` is written on that host until `service release`; a child whose liveness reads unknown gets no `gone`; `service recover --apply` writes each `gone attempt` with `--op-id` and `--revision` (§ 4).
- `retries` is one counter: an attempt `requeue` that makes it 3, or a `gone` that makes it 2, moves to `ask` with the attempt ended; its `answer` then goes to `ready`. Limit card: a writer whose entry hits the limit appends, unless its text is a card, `Problem:` naming the limit, `1. requeue: …` ★, `2. later: …` and `To answer:` naming only `taskq answer N.K`; the reason's `K. ` lines become `K) ` (N-1 folds the same text). Every move to `ready` clears attempt, card and result.
- `answer K` whose option starts with `close` or `later` runs `close` (§ 7) or `later` instead, only through `taskq answer N.K`: a bare board comment `K` folds as a plain answer; an owner pick of `approve <sha7|sha> ...` approves a gated task only when that SHA matches its current result, including a bare board comment in `ask`. An attempt-bound answer cannot approve.
- Gate states: none, `required`, `approved`, `stale`. An approval binds to the result it names: the next `result` or a move to `ready` makes it `stale`, which blocks like `required` until an `approve` of the new result. The gate blocks only `close` in `review` (its publication and the closed issue that frees `Depends on` tasks); a fold from the board after any restart keeps it (R1). Closing a `later`/`failed` task stays the owner's own act.
- After an entry is accepted, the writer sets the `q-<state>` label; every service pass fixes labels that differ from the fold. A hand-moved label is overwritten: people change state with an entry.

### Ask card
`ask` writes, in order, without headings or blank lines inside the card:
1. `Done: <what was checked or attempted>` -- one line, at most 160 characters; say `not started` when true.
2. `Problem: <decision needed and user effect>` -- one or two lines, at most 240 characters per line.
3. Optional `Evidence: [<label>](<url>)` -- one line, at most two screenshot/video/issue/PR links, labels at most 40 characters each.
4. Two to four options, `1. <action and trade-off>` etc.; one line each, at most 160 characters, exactly one ends in `★`. None: an owner action, its Problem the action; no attempt starts while it waits, its `answer` resumes the same session.
5. To answer: `taskq answer N.K` or comment `K` or the option text; an owner action: `taskq answer N --text <done>`. Last line; substitute this task's number for N.
Accepted shared UI target: [answer card](docs/design/answer-card.md) owns the reusable TaskQ/DashQ presentation; § 2 and § 5 remain behavioral authority. Tray exception (R6): mount cards only in `ask`; without parsed choices, show text and owner requeue (reason), later and confirmed Close controls. Close cancels without publication through `later` then `close`, each with CLI readback; partial/unknown delivery stays explicit. An answer op is resent only with its own id: once when a refresh reads the task past its revision, once per Check delivery after an unknown receipt. Other consumers remain read-only for unparsed cards. A card has at most nine nonblank lines. K is an option number; a bare K or option text counts only in `ask` (section 2).
`--text` supplies literal Done and Problem lines; `--link` supplies Evidence; `--option` and `--recommend` supply the options/star.
Result decision cards use the same format after the verdict (section 7): append Done/Problem to `--text`, use `--option`, `--recommend`, `--link`; omit all card fields for no decision.

## 3. Attempts, lease, capacity
- **Claim.** A service that admits a `ready` task posts `spawn worker`, re-reads the comments and starts the child only if `fold` accepted its own `spawn`. A loser posts nothing more. Same for `spawn reviewer`. `ponytail:` this needs read-after-write order of comment lists; it is verified on each board by a two-host test before use (R12). If a board fails it, a guard label around `spawn` is the upgrade path.
- **Fencing.** The child gets `TASKQ_TASK=<N>` and `TASKQ_ATTEMPT=<id>`; its commands add `attempt <id>`. A late writer of a replaced attempt is ignored by `fold`. A `result`, `ask`, `requeue` or `gone` from a process with `TASKQ_ATTEMPT` set is refused before any write when `TASKQ_TASK` is not `<N>` or the attempt is not the live one, naming both (a reused session's stale environment); a retry of a seen op id still returns its first receipt.
- **Lease** = the attempt's host heartbeat (§ 4) is fresh and lists `#<N> <id>`. No timestamps in the task.
- **App lease.** Runtime `codex-app` (§ 8) has no child for its turn: the turn counts as the child while the Codex app runs in this host's logged-in session and the thread has no `task_complete` after the queued brief or text. A finished turn without `result`, `ask` or `requeue`, a closed app or a logout counts as a child exit (`gone`). Stopping it only drops it from the heartbeat: the app turn runs on and its late writes are fenced. An update or requested re-exec waits for active app turns to finish; it must not retire their attempts (§ 8 step 3).
- **Expiry.** Any service that sees `doing` or `review` whose host heartbeat is older than `ttl`, or does not list the attempt, posts `gone attempt <id>`; an attempt younger than `ttl` (by its `spawn` comment or newest accepted inbox entry, `answer` or `steer`) is judged only by the heartbeat age. That is the only recovery. The owning service instead resumes an attempt without a child when its `inbox` has an entry it has not delivered, else posts `gone` with the last worker message of the attempt log.
- **Capacity** is per project and host: the effective `limits.<runtime>` (§ 9) minus the service's live children of that runtime, reviewers and resumes included; Fixed (default): 0 or no limit admits none; Auto (§ 9): a runtime without a limit has no count ceiling, 0 disables it. No project cap: the sum of host limits bounds the project. Each pass reloads capacity config; invalid config holds every launch and reports, never raises capacity. Lowering a limit never stops a child (R11).
- **Load gate** (opt-in, § 9) holds every new child (claim, reviewer, resume) while CPU busy >= `cpu_max` % or available physical memory <= `memory_min` %; running children continue. Reads: Windows GetSystemTimes/GlobalMemoryStatusEx; macOS host CPU load ticks, VM free + inactive pages/hw.memsize; Linux /proc/stat (idle includes iowait)/meminfo MemAvailable. Sample every 30 s on a monotonic clock, independent of `poll`; the first CPU reading is a baseline. A missing, invalid or over 60 s old reading holds. Auto also holds below 2.5 GiB available and at macOS `kern.memorystatus_vm_pressure_level` >= 4; an unread floor holds. Start, enable and threshold changes start held; reopen after three consecutive valid samples at CPU <= `cpu_max` − 10 and memory >= `memory_min` + 5 (90 s); a failed, late or mid-band sample resets that count. At most one launch per 30 s, the next after a post-launch sample; check before claim and before launch.
- A held resume keeps its inbox undelivered; a won claim held before launch stays leased in the heartbeat (§ 4), not counted used, without another claim, retry or `gone`. No battery or thermal gating, no forced retirement. **Host admission.** One host authority admits every Auto launch (claim, reviewer, resume) after the load gate: `<install>/admission.json` under the lock `<install>/admission.lock`. Each service keeps its entry there (version, reservations), rewritten every pass and 30 s; an entry over 120 s old is dropped. A reservation is `requested` (refused, with its reason), `held` (granted; counted until its child exits) or `released` (child exited, start failed, claim lost, entry dropped). A grant needs every fresh service of `<install>/projects` at the minimum service version `4.2.0-dev` or newer (`status.json` `version`), the host's held reservations under `admission.max`, the last host launch at least 30 s ago and a gate sample after it. An unreadable file refuses and is rebuilt from the writer's entry. Fixed services write their entry and are never refused by it. **Emergency hold.** `<install>/hold` (one reason line) refuses every launch (claim, reviewer, resume) of every service on the host before the load gate, until `service release` removes it; pause and resume never touch it; an unreadable file holds; live children run on; a held resume keeps its inbox and lease. Services older than the minimum service version ignore it: `service hold` names them.
- **Cancellation** of an attempt = `requeue`, `later`, `failed` or `gone`; the owning service stops the child (R11).
## 4. Service
`taskq service run` is the host's single long-lived process; `taskq service install` makes the OS keep it running (§ 8).
One loop:

1. Reap exited children; a CLI child whose attempt log shows its turn ended (`turn.completed`, `turn.failed`, `result`) counts as exited and its lingering process tree is stopped (#1034). A child whose attempt is still current posts `gone attempt <id>` with the exit code and the last worker message of its log (one line, absolute paths root-relative or `<path>`, at most 240 characters with the label; § 7 rule 6), unless the attempt wrote `ask`, `result` or `requeue` after the child started: a clean exit; step 6 resumes it from its inbox.
2. Stop children whose attempt is no longer current (R11). Remove worktrees of closed tasks (§ 7).
3. Write the heartbeat issue `taskq host <name>` (label `taskq-host`) when older than `ttl / 3` or its body changes: lines `version <v>`, `service <id>`
   (12 hex of SHA-256 of `<install>/installation-id`), `machine <hostname>[ wsl]` (the `hostname` output, as agentq `host.name`; `wsl` under WSL; DashQ joins Hosts rows by it, [dashq hosts](https://github.com/taskqorg/dashq/blob/main/docs/design/hosts.md) H2), `#<N> <id>` per live child or launch held by the load gate, `focus off|unknown` when the focus admits nothing, plus `at <board time>` (a same-body edit keeps `updated_at`). Freshness uses the board's `updated_at` and the response `Date`, never local clocks.
4. Post `gone` for attempts of dead hosts (§ 3).
5. Fix projected labels; `waiting` with closed deps becomes `ready`.
6. Resume the session of a live attempt for a new `answer` or `steer` (text on stdin); spawn a reviewer for `review` without a live one; admit `ready` tasks matching this host by priority then number within capacity.
7. Every `update_every`, or at once when a local command wrote `<root>/.taskq/update`: the self-update check (§ 8); an installed service applies a newer version, others only report it. The outcome goes to the log.
8. Sleep until a poke or `poll` seconds.

- Filter: `host-*` absent or this host; workers use `run-*` when present, else a `prefer-*` runtime with a free slot, else the runtime with the most free slots (first listed on a tie), so any-runtime tasks alternate; `run-*` wins over `prefer-*`, and both `prefer-*` labels are ignored with one log line per pass; reviewers prefer the other runtime than the accepted worker (`claude` ↔ `codex`, `codex-app` → `claude`) with free capacity, falling back to the worker's runtime. Other filters remain: `assignee-only` passes; each `needs-*` in `has` (`needs-gate`: every host of a version with gates, § 7); `codex-app` keeps its §9 opt-in.
- Focus: `taskq service focus all|off|<label..> [--request TEXT]` writes `<root>/.taskq/focus`: `all`, one of the labels or `p0` passes; none or `off` (default) admits nothing, heartbeats and updates go on; capacity reason `focus` and the heartbeat say so. `service install` writes `off` when the file is missing, else keeps it. `--request` keeps the owner's words in `focus.request`; a focus without it removes the file. No arguments: print focus, `has`, labels of open tasks; an agent maps the owner's words to these, asks when unsure, says so when none fits.
- Pause: `service pause` (and the tray's) saves the focus to `focus.paused` and writes `off`; resume restores it. Without a saved focus resume fails and names the labels of open tasks: never `all` by default. Emergency ([E1–E5](docs/design/emergency-recovery.md)): under the § 3 hold the loop still reaps, stops replaced children and beats. A failed liveness read in step 1 keeps the child: `status.json` `kids` `live` `unknown` with its `reason` (else `running`), never `gone`; `hold` names the reason. `service recover` (only under a hold) lists each `doing`/`review` attempt of this host with its liveness from a `status.json` at most 60 s old (else all unknown); a child read running or absent gets the op `gone attempt <id>` with `--revision` (the task's) and `--op-id recover.<N>.<id>`; unknown gets none and blocks relaunch. `--apply` writes the ops through the § 5 dispatcher, one receipt each; step 2 stops fenced children; release admits by focus. Targets: tray control, graceful/force stop, per-project entries, selective resume (E1–E3).
- Poke: a local command touches `<root>/.taskq/poke`; the sleeping service checks its mtime every second. Each pass
  writes `<root>/.taskq/status.json` (coreq.md common keys, `update` included; plus state, the snapshot keys `schema`, `source` host, `observed`, `complete`, `reason`, `totals` and `tasks` (§ 5 `--json`, each with its § 2 `revision`; a failed pass keeps the last rows with `complete` false), `request`, `restart_waits`, `events_since`, `capacity`: effective `limits`, live-child `used`, effective `load_gate`, `admission` (`mode`, `max`), `host_used`, `min_service_version`, own `reservations` (task, attempt, runtime, state), `gate` off/open/held/unknown, all `reasons` (host and access refusals and an empty focus included), `cpu_percent` and `memory_available_percent` (null when unknown), `sample_at`, monotonic `sample_age_seconds`, `agents`: the § 5 `agents` rows and their `at`, probed at most every 5 minutes, `access`: § 8 Access rows) for `service status` and the tray; capacity is also published on each sample. Missing or over 60 s old capacity reads unknown ([specq](https://github.com/taskqorg/specq/blob/main/engineering/verification.md#unknown-is-never-healthy)).
- Events: a pass appends to `<root>/.taskq/events` a line `<board time> #<N> close|failed|ask|blocked|gone <id>` per task it saw move to closed, `failed`, `ask` or `waiting` since its previous pass (a new task counts from its first state); the id is the attempt current at the move, else the task's last spawn; for `ask` and `blocked` else its last comment, else the issue number; a closed or `failed` task never spawned adds none. `gone`: per trusted `gone attempt <id>` log entry newer than the previous pass (the first pass adds none). One line per attempt and kind; lines older than 30 days drop. The first line `since <time>` is the first time covered (`events_since`); a restart keeps the file, moves while no service ran are missing. `ponytail:` no board replay. `ponytail:` files, no socket or pipe, on every OS.
- One service per root and host name: `service run` waits while a `status.json` under 60 s old names another live pid; a pass that finds this host's heartbeat under `ttl` naming another `service <id>` writes nothing and fails with `another service <id> runs as host <name>`. Restart: rebuild from the board; former children are not adopted (except the § 8 re-exec), their attempts are `gone`. `service restart` writes `<root>/.taskq/restart`: the next pass re-execs (§ 8 step 3).
- Tray (macOS, Windows; layout, routes and platform packaging: [menu specification](docs/design/menu.md) M1–M14): one per host. Any installed service starts `releases/<current>/taskq tray` when the heartbeat `<install>/tray` (the tray's pid) is older than 30 s; a tray that finds another fresh pid there exits, as does a tray on another version than `<install>/current`. It lists the projects of `<install>/projects` and reads each `<root>/.taskq/status.json` and `events`: no board, no token. Writes name their target first: pause/resume per project and over all after a confirm naming each project and its effect; resume without a saved focus offers the project's labels and writes the pick; per project log, folder, restart, stop until the next logon, and uninstall after a confirm naming it. `Edit limits` writes only after a confirm naming project, host, old → new and `Running tasks continue`, and shows `Applied` only when `status.json` reads the values back. `Update now` shows when a `status.json` names an `update`: it writes that project's `<root>/.taskq/update` and reports success only when a `status.json` reads back that version. History (M6) is built from `events` only. Agents (M3) shows the § 5 `agents` probe, read-only. Resources opens btop in its own OS terminal window, never inside the menu; missing btop is installed first with the OS package manager, unelevated (M9). Notifications (M14): native OS notifications of new `events` lines, per kind and project as M14 sets, at most once per event. - AI requests ([menu specification](docs/design/menu.md) M7, M10; [AI workspace](docs/design/ai-workspace.md)): the tray writes `<root>/.taskq/requests/<id>.json` (`text`; `after`: the request it clarifies) into the first registered project with a fresh `status.json` and pokes it. ### Profiling (#988)
Follow [shared profiling](https://github.com/taskqorg/specq/blob/main/engineering/profiling.md). Always measure `service.pass` (board reconciliation, excluding sleep), `dispatch` (claim/readback up to runtime handoff; start failures belong to `spawn`), `spawn` (runtime start/resume, not child lifetime), `forge.call` (one HTTP request), `update` (check/download/verification), and `tray.render` (icon rasterization and native application, not webview paint). Budgets for all six are **unknown** until owner-approved ([shared budgets](https://github.com/taskqorg/specq/blob/main/engineering/profiling.md#budgets-and-unknowns)); profiling never changes admission or task state.
Counters use fixed operation/outcome/error codes and numeric duration/start time only; `TASKQ_PROFILE_TRACE=1` adds numeric run/process/span/parent ids for the process run (off by default). Store ([shared store](https://github.com/taskqorg/specq/blob/main/engineering/profiling.md#store)): `<install>/taskq.log` with its §4 Data pruner, and `incidents/`; records hold no URLs. Profile appends and the service pruner use nonblocking coordination through the empty `taskq-profile.lock` (no task state); collection stops as unknown at the bound until the service prunes, rather than introducing another pruner; instrumentation failure cannot fail the operation and is reported as unknown locally. Its chain check (R12) races appends against a prune that must win the lock: every retained record is a counted successful append.
`taskq profile` reads the retained log without board access and ranks the six operations separately by p95 time, failure rate and duration variance, with count, p50/p95/max, outcome/error counts and unknown budgets. Empty, unreadable or corrupt records read unknown; unrelated log lines are ignored. Collection completeness is unknown (best-effort writes); counts and the timestamp window describe retained observations, not lifetime totals; earlier/pruned history and adapter retry/cancellation counts stay unknown. Incident and optimization links follow [shared report](https://github.com/taskqorg/specq/blob/main/engineering/profiling.md#report); local incident outcomes carry their numeric occurrence time. It then lists this host's board requests of the hour before now by source (records, requests, top 3 operations; § 4 Sources); none or a corrupt record reads unknown, records that start inside the hour say partial; agent `gh`, PM chat tools and DashQ are not counted.

- Success: `#N <state>` for task writes; close adds one publication link/SHA line. `wait`: `<state> #N` or `tick`.
- Errors/refusals: `Error: <problem>` then `Next: <action>`; at most 2 lines, at most 160 characters each. A compact error links its complete diagnostic in `.taskq/cli-errors.log`; if saving fails, preserve the diagnostic as raw output (R12).
- Other command acknowledgements: one line naming action and project/version; at most 160 characters. Batch operations: one outcome per item.
- `requeue`, `later`, `failed`: `Reason: <blocker>` then optional `Next: <fix>`; at most 2 lines, at most 240 characters each.
- `answer --text` and `steer`: at most 4 lines, at most 240 characters each; one decision/instruction per line, no invented context.
- `service focus/list/status`: named project, focus, counts, freshness and unknown reason; one field/item per line, at most 160 characters.
- `update`, `cleanup`, setup and `selftest`: one outcome per version/path/check ([Core Write](https://github.com/taskqorg/specq/blob/main/caveman/rules/core.md#write)).
- Help keeps full command syntax; `inbox`, raw service logs/status JSON and original issue/log text are exempt from display caps ([verbatim diagnostics](https://github.com/taskqorg/specq/blob/main/caveman/rules/changes.md#keep-the-source-and-sink-separate)).
- Unused positional arguments are refused before any action: `unused positional arguments: <arguments>`; repeat value flags for multiple items.
- Commands add `attempt $TASKQ_ATTEMPT` when it is set. A command refused by `fold` prints the current state. `TASKQ_ROOT` must contain the current directory when that directory lies in a taskq project (a folder with `taskq.json` here or above), else every command is refused `TASKQ_ROOT <root> is not the project of the current directory <dir>`: a reused session's stale environment never writes into another project.
- `--op-id ID`, `--revision R` (answer, requeue, later, failed, steer, result, ask, close, start, approve; `add`: op id, § 1) write the § 2 fields: a seen op id returns the first receipt, writes nothing; another revision is refused `stale` naming the current one, board unchanged. An entry that a concurrent write beat on readback (other revision, raced op id, ignored) is edited by its writer: `stale`.
- Receipt: `--json` prints one object `{task, op_id, outcome, state, revision, reason, next}`; outcome `accepted` (readback state), `rejected`, `stale` or `unknown` (written, no readback: `Next:` reads `inbox N`, retries the same op id); else the lines above.
- `wait` reads issues updated since the local cursor `<root>/.taskq/pm-cursor` (a cache, R1) and folds those that changed.

## 7. Worker, reviewer, publication
Worker brief: task text, attempt, branch, delivery commands, this file's path (this release's URL when the root has none), the folder rule (§ 8), the CI-wait rule (§ 4). The task is the owner's grant for this section's commit and publication steps ([shared approval boundaries](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#approval-boundaries)); nothing outside them is approved. Rules:
1. Read this file and the whole issue first, then [prepare the task](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#prepare-the-task): a decision conflict (R13), an untestable or ambiguous Acceptance item or a split (R2) is an `ask` with options before any code.
2. Workspace: `git worktree add -b taskq-<N> .worktrees/taskq-<N> origin/main` (existing branch: continue it). `workspace: external`: the path the project's `AGENTS.md` gives.
3. Owner-only question: `ask` with options, then stop. Cannot be done: `requeue --text`, then stop.
4. Before `result`: commit on `taskq-<N>` with `Task: <issue url>` in the message, rebase on `origin/main`, run the project checks, name each command and outcome in `--checks`. `result` refuses, naming the files, when the diff from `origin/main` changes a `uiSources` file whose blob `docs/shots/manifest.json` at the SHA does not record (fix: `docs/shots/update.sh`); a readable SHA without the manifest: no check; any other Git or manifest failure reads unknown and refuses. Never weaken a check to pass: a changed or deleted existing test or golden trace needs a changed rule in the same diff and is named in `--text`. For fixes, `--checks` records the [shared before/after evidence](https://github.com/taskqorg/specq/blob/main/engineering/verification.md#run-policy-by-stage) or its limitation.
5. Delivery `direct`: push `taskq-<N>`. `auto-merge`, `review-pr`: push and open one PR/MR into `main`. Then `result --sha <sha>`; do not wait for CI, `close` checks it (§ 4 board budget). Research: `--sha` = current `origin/main`, the answer in `--text`.
6. Everything written through taskq is public: no secrets, tokens or local paths.

### Result and close verdicts
`result` body: `Changed: <user effect>` (1-2 lines), `Checks: <command -- outcome>` (one line per check, 1-8 lines),
then `Open: <remaining item|none>` (1-2 lines); at most 12 lines, at most 240 characters per line. Keep exact commands and platform qualifications (R12).
`--text` supplies literal Changed and Open lines; `--checks` supplies unprefixed command/outcome lines, each rendered with `Checks:`. SHA stays in the log header; one PR/evidence link may share Changed and carry the [shared risk description](https://github.com/taskqorg/specq/blob/main/caveman/rules/changes.md#merge-request-description-markdown) for either publication route.
`close --text` supplies all three labelled fields in the same order and limits; Checks names each `A<k> ok|gap|unknown` plus exact-SHA CI outcome, not a vague PASS.
Reviewer checks every Acceptance and contract against the candidate and CI on that SHA, waiting at most one poll a minute (`gh pr checks <PR> --watch --interval 60`; never `gh run watch`, which polls every 3 s, or `gh run view` without `--json`); `Checks:` follows [shared review](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#review), within the same verdict limits. Requeue only for Acceptance/contract gaps; advisory findings go in `Open:`. Then `close --text <verdict>`, `requeue --text <exact fixes>` or `ask` with options. PM relays the verdict verbatim, links intact.

`close` publication goes through the board API only:
- `direct`: branch `taskq-<N>` equals the result SHA, `main` is its ancestor, CI green on that SHA; move `main` to it
  without force, read back, close. GitLab has no fast-forward ref API: `direct` there merges a fast-forward MR.
- `pr`: exactly one open PR/MR of `taskq-<N>` at the result SHA, current `main` its ancestor (else `requeue`: rebase), CI green on its head; `main` refuses a stale head at merge time (GitHub: a ruleset requiring branches up to date that the token can never bypass, or readable protection requiring it with admins enforced; GitLab: fast-forward or semi-linear merge method), else refuse; mark a draft GitHub PR ready; squash-merge with the title and
  all `Task:` lines; read the merge back; close. Incident ancestry checks in this same close use the returned merge SHA for squash publication, the result SHA for direct publication; later human moves are never read.
- No commit (research, or SHA already on `main`): verify ancestry, close.
- Pending or missing CI: refuse, state unchanged. Failed CI or conflict: `requeue` with the message.
- On the attempt host: remove a clean `.worktrees/taskq-<N>` and its local branch; dirty ones stay.
- Merged, not closed (a partial publication, or a PR/MR into a release branch, which never closes its issue on merge): with no open PR/MR of `taskq-<N>` into `main`, `close` finds the merged one of `taskq-<N>` into any base whose head is the result SHA and closes with that one receipt (`merged #P [into <base>] as SHA`): no second merge, no requeue. From a reviewer's `ask` (result kept) an owner `close` option runs it (§ 2); `doing` or a worker's `ask` has no result to verify: `later`, then `close`.

**Delivery presets** ([agent behavior](docs/design/agent-behavior.md) B1–B5; commit, push, PR and merge, apart from § 8 Access) are § 9 `delivery` `{preset, revision}`, the owner's (R9; the revision +1 per owner edit): `auto-merge` (the `pr` route), `direct`, `review-pr` (the `pr` route after the owner gate below). `local` and `push-branch` are refused until B3 pending-handoff states exist. Without `delivery`, `publish` names the preset at revision 0 (`pr` is `auto-merge`); nothing converts it to `review-pr`, a migration is an owner-reviewed edit. `close` reads the policy then. Its publication receipt is the last verdict line `delivery <preset> r<revision>: <main fast-forwarded to SHA|merged #P as SHA|SHA already on main>`. `review-pr` needs every host at `4.2.0-dev` or newer: 4.1.11 ignores `approve` and publishes it as `auto-merge`.

### Recipes and owner gates
A recipe ([plans and decisions](docs/design/plans-and-decisions.md) P5) is a reusable task list in § 9 `recipes`; its identity is the name and its `version`. `taskq recipe NAME --run ID` adds each task held through the configured create claim (§ 1) in order with op id `recipe.<name>.<version>.<ID>.<k>`, so a rerun returns the first receipts; `deps` become `Depends on #N`, `{goal}` is replaced by `--goal`. A task with `gate: true` also gets label `needs-gate` and a `gate` entry. Nothing starts until every task reads back; then only `--start` or `taskq start N` starts them: the queue runs them like any task, no separate scheduler.
A gated task's or `review-pr` project's reviewer that finds the result otherwise done asks with options, Done naming task fit and CI on that SHA, the first `approve <sha7> and close ★`; an owner pick (§ 2) or `taskq approve N` binds the gate to that result, the reviewer then closes. A new result needs a new approval; a stale or missing one makes `close` refuse before publication. Tasks that `Depends on` the gated one wait for its close.

## 8. Runtimes and deployment
**Access (R9).** `<install>/worker-policy.json` is operator-owned: `revision` (+1 per write) and `grants`, each `runtime`, preset `mode`, scope (`project` root, else host default; a project grant replaces the default there) and provenance (`by` OS account, `at`). Presets: `restricted` writes runtime homes, user caches, OS temp and `<root>/.taskq`; `workspace` also `<root>`; `full` turns the runtime sandbox off on start and resume (Claude `--permission-mode bypassPermissions`; Codex `-s danger-full-access` without other sandbox options, model and effort kept). Each start and resume resolves requested (`taskq.json` flags) and effective access; `service permissions` and `status.json` `access` show both. No grant: legacy flags run unchanged, never recorded as a grant. Every mode but Full keeps `<install>` (policy, token, releases), `PATH` directories, the runtimes' package directories and `.codex/*.toml` out of worker writes. Enforcement: macOS a taskq Seatbelt profile; Linux Codex Restricted/Workspace the `taskq-sandbox` launcher ([setup and boundary](docs/design/linux-sandbox.md)) and an explicit project grant; Windows Codex Workspace an explicit project grant and the pinned native candidate ([qualification matrix](docs/runtime-qualification.md)); per-platform boundaries in [shipped enforcement](docs/design/worker-permissions.md#shipped-enforcement). Windows Restricted, read-only narrowing and network-denied requests refuse until qualified; no Full retry or working-installation migration. Unknown enforcement refuses before claim or resume, with the reason in `capacity` `reasons`: unreadable policy, missing launcher prerequisites, no Linux grant, or other OS/runtime without enforcement. Full on the same host and user is uncontained: its worker can edit the policy. Other modes close direct writes only: user autostart, shell or runtime settings and repository Git config or hooks a worker plants and that later run outside a sandbox (the service's own `git` included) stay a same-user path. `service permissions` writes outside a worker only (refused under `TASKQ_ATTEMPT`); a board answer never grants. Changes apply to new starts and resumes. Rollback floor `4.2.0-dev`: with any grant or an unreadable store the service and a grant write set an older `previous` to the running version; a release that fails health then stays down, nothing admitted, for the operator. ## 9. Config and cutover
`taskq.json` beside the project root:
- `board` `github|gitlab`; `repo` `owner/name`; `host` the board's web host (default `github.com`, `gitlab.com`).
- One module per board under `src/board/` (`github.rs`, `gitlab.rs`): its API, token lookup, login probe, CLI, env and default host. The `Board` trait and `src/board/mod.rs` (shared HTTP, registry by name) are the only contract; core, service and operator never branch on the board kind, and editing one board never touches another's module.
- `label_schema` `canonical|legacy` (absent: legacy if the board has `priority-1|2` or `q-waiting` objects, else canonical). Both names work in priority and focus/status filters; `p0` has no legacy name; logs keep `waiting`. Canonical writes require all-host compatible release/idle approval on existing boards. Keep legacy objects and closed issues; reassign only open issues (#769 owner answer). This board is canonical since #776.
- `publish` `direct|pr`, `delivery` (§ 7); `workspace` `external` keeps host-owned worktrees.
- `hosts` `{hostname: name}` (env `TASKQ_HOST` overrides); `has` `{name: [x..]}`; `limits` `{"claude": n, "codex": n, "codex-app": n}`.
- `add --prefer codex|claude` writes one soft `prefer-<rt>` label ([specq runtime preference](https://github.com/taskqorg/specq/blob/main/engineering/agent-workflow.md#runtime-preference)); `add` refuses two values or another runtime. The worker filter takes it only while that runtime has a free slot on this host (§ 4 Filter); reviewers keep their rule. `add --runtime codex-app` creates the explicit runtime label on any manager host. Opt-in `codex-app` (macOS, Windows): a host runs it only when its `has` lists `codex-app`, and only for tasks labelled `run-codex-app`; other hosts are unchanged. Reviewer chain checks retain app-worker cases on macOS and Windows and assert no app worker on other OSes. A screen task adds `needs-screen`, admitted where `has` lists `screen`. A macOS evidence task (`tray --snapshot` PNGs, macOS-only host tests) is added with `--host mac --runtime claude`: the Claude worker produces them under unchanged access (#1028); Codex workspace-write does not (#960, #1021). Answering a real ask stays the owner's act.
- `capacity_hosts` `{name: {"limits": {..}, "load_gate": {..}}}`: partial `limits` override the top-level ones for that host; a host `load_gate` replaces the top-level `load_gate` object; omitted gate fields are `enabled` false, `cpu_max` 85, `memory_min` 15. Valid: limits 0..u32::MAX, `cpu_max` 10..100, `memory_min` 1..95, integer percent. `admission` `{"mode": "auto"|"fixed", "max": n}` (a host's replaces the top-level one; absent: fixed; setup (§ 4 Add project) writes auto): auto turns the gate on with the [D03](docs/design/admission-calibration.md) defaults `cpu_max` 90, `memory_min` 10 and CPU as the 60 s mean, a 100 % latest interval vetoing, memory floor max(`memory_min` %, 2.5 GiB) and macOS pressure level >= 4 holding; given gate fields override them; `enabled` false is invalid. Absent keys keep today's behavior; nothing migrates or enables itself; old binaries ignore these keys, so use them only on hosts with a compatible version.
- `recipes` `{name: {"version": V, "tasks": [{"title", "goal", "acceptance": [..], "scope", "deps": [earlier 1-based index..], "gate", "type", "runtime", "priority", "host"}]}}` (§ 7).
- `permission_mode`, `codex` (R9); `incident_reports` `true|false` (§ 4); `pages` link wrapper base; `assignee` (login or `me`) report filter.
- `ttl`, `poll`, `update_every`, `rollback_after`: seconds, defaults 300, 60, 900, 600.
- GitHub token: one owner-installed credential per host in `<install>/token` (0600 on Unix; owner-only access on Windows), shared by service and workers; existing OAuth tokens are accepted, a fine-grained PAT is preferred. No env or CLI-login fallback. TaskQ, workers and setup never run `gh auth login`; missing/empty/unreadable token is an owner item with the same error in service and worker. Never in config. [OAuth token limit](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/token-expiration-and-revocation#token-revoked-due-to-excess-of-tokens-for-an-oauth-app-with-the-same-scope). GitLab retains coreq token lookup and `Authorization: Bearer`.

A cutover is one step per project, not per host: two board formats do not mix. No migration code: `CHANGELOG.md` says per release what changed on the board and what an open issue needs. After the owner's OK, with every old service stopped and no old children, it applies the plan with `taskq` commands and issue edits. Closed issues are never touched. New services start: Mac, then Windows. Repair is the same agent procedure for one project; it warns when `status` shows another host's fresh heartbeat.
