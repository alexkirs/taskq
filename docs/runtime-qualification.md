# Runtime qualification matrix

Verify supported TaskQ capabilities through observable outcomes. [R9, R12 and runtime contract](../taskq.md) own policy; [specq verification](https://github.com/taskqorg/specq/blob/main/engineering/verification.md) owns test method. This matrix does not grant access or turn pending permission designs into shipped behavior.

## Short dependency commands

Operator inspection commands and tray status/selftest/setup exchanges use the shared CoreQ executor through `platform::output`. Complete nonzero output remains available for receipt parsing; spawn, timeout, capacity and incomplete output return an explicit unknown with the original native error. Inspection/status/selftest use30s; board mutation/setup use60s. The process trace keeps the failure even when a caller handles it. An OS opener records submission only; it does not claim that the target window appeared. Interactive pickers and resource terminals have their own human-driven lifetime and are not short exchanges.

## Execution policy

One bounded live scenario covers each applicable runtime, role and continuation. Run it when that integration, permission configuration or client version changes, not on every commit or documentation edit. Record exact versions, effective permissions, initial state, actions, observed output and remaining gaps. A prior pass qualifies only its recorded configuration.

Deterministic checks follow [specq test classes](https://github.com/taskqorg/specq/blob/main/engineering/verification.md#test-classes). TaskQ chains: state transitions, duplicate/stale writes, admission, publication and preservation of active work. A constructor/argument-string check is not live permission or behavior proof.

## Bounded live scenario

1. Record candidate/client/OS and effective configuration. Use only an isolated fixture and an explicitly owned test task; leave existing jobs, grants and global configuration untouched.
2. Start worker with an ambiguous in-memory pause fixture. It must ask before editing. Answer keep-active, resume the same session, verify exact canonical rule bodies in both actual inputs, and inspect tool output for expected baseline failure and corrected active/repeat/empty success.
3. Start independent reviewer, execute the published fixture, inspect its actual rule input, ask before acceptance, resume the same reviewer and inspect the continuation before closing. A self-report or handshake is insufficient.
4. For each changed permission boundary, controller creates disposable canaries with unknown content, agent attempts the approved positive/negative operations, controller checks actual results and unchanged forbidden targets. Use native denied operations, not a request to obey prose. Never inspect real private files or credentials. Report allowed reads separately from denied writes.
5. For operator, inspect actual tools and execute only authorized fixture read/write/check. Require actual read/write/check results and same native session on continuation; disabling that runtime must prevent continuation without fallback. Proposed JSON still passes the existing validation/confirmation/readback chain.
6. For lifecycle changes, preserve an owned long-running fixture across pause/update; distinguish process exit, app-turn exit, lease and board state. Do not cancel unrelated work to manufacture an idle host.

## Current limitations

The shipped access presets in taskq.md § 8 supersede the earlier permission proposal: macOS enforces a TaskQ Seatbelt profile, while Windows/Linux currently require an explicit Full grant; missing grants or unknown restricted enforcement refuse launch. Full has no OS containment. Earlier passes below qualify their recorded candidate and permission configuration, not a later policy revision. No prompt, project configuration or 0600 file is claimed as an immutable host ceiling. No new grant broker, background monitor or duplicate test framework is introduced by this matrix.

## Operator qualification command

Run once per changed native integration, from the candidate checkout:

```sh
TASKQ_QUALIFY_RUNTIME=claude TASKQ_INCIDENT_REPORTS=off cargo test --locked live_operator_matrix -- --ignored --nocapture
TASKQ_QUALIFY_RUNTIME=codex TASKQ_INCIDENT_REPORTS=off cargo test --locked live_operator_matrix -- --ignored --nocapture
```

For an owned fixture selected by `TASKQ_QUALIFY_ROOT`, set `TASKQ_INSTALL` to its `fixture-install` directory and provision the required board credential privately there. Provision any required TaskQ grant explicitly in that disposable `worker-policy.json` first; the test never grants Full itself. The chain keeps its fixture and native logs in `.taskq/qualification/`; no global settings, existing jobs, board writes or commits change. With the explicit qualification grant, the Claude fixture uses Bash/PowerShell on Windows and Bash/Write on macOS in its own `.claude/settings.local.json`; this grants no OS containment. It checks random file contents independently, verifies the session ID on continuation, then disables only its fixture runtime and requires failure before launch. It does not prove every permission boundary or MCP tool. Normal `cargo test --locked` skips these paid calls.

Claude worker/reviewer #969 includes a rejected first result (missing reproducible fixture), a repaired worker result, independent reviewer execution and resumed reviewer input. Controller compared all four pinned bodies against actual worker/reviewer start and continuation messages. The rejection is evidence that review applied the rules; closing the issue alone is not that evidence.

## Rule delivery: contract detail

Continuation bodies supersede earlier versions; an index alone is insufficient after a change or compaction. ### Execution ownership

R1/R2/R8/R11/R12/R13: execution safety is separate from task state. This accepted recovery contract replaces timeout-only failover. Its implementation and cutover are incomplete in this draft; do not release the queue from specification or local-test evidence alone.

- One task can have many turns within an attempt. Identify each external submission separately by task, accepted attempt and requested inbox cursor. A result, answer, requeue, cancellation request or expired heartbeat never proves that submission stopped.
- Commit attributable board intent before external submission; read it back before proceeding. An accepted initial spawn can be that intent. Continuations need their own intent, tied to the requested inbox boundary; coalesced inbox entries do not create several executions. An uncertain intent write is discovered by its stable operation identity, never blindly reposted or executed.
- Record release only after observed native completion/termination or proven no-start. The release identifies its exact execution and accepted attempt, including an attempt replaced meanwhile. Duplicate release is idempotent; stale, malformed, foreign or unmatched release changes nothing. Release is an execution observation, not a new task result or authorization.
- Every host checks unresolved execution intents before a new worker, reviewer or continuation. This includes prior attempts after result/requeue and user cancellation. Board fencing rejects late task writes but cannot cancel arbitrary external effects. Missing heartbeat means unavailable owner, not permission to duplicate work.
- Reuse board intent and native identity/state/logs first. Extend an existing bounded record only for recovery data shown missing in the [adapter matrix](#adapter-recovery-matrix). Identity enables readback; it proves neither acceptance nor termination. A marker found after a crash never proves no-start. Preserve required unresolved identities across update/pruning and refuse admission if their protected preparation fails. No independent ownership journal, task database, prompt copy or permission grant.
- Reconcile interrupted submission by the recorded native identity and original input boundary. Never infer ownership from process name, a reused PID, another conversation's completion or launcher exit. An uncertain external side effect needs its own reconciliation even after process exit.
- A fresh owner can resume supervision of a proven identity. Missing/corrupt identity, unreachable runtime and ambiguous acknowledgment stay unknown, retaining occupied capacity and blocking replacement. Resume does not clear this fence. Expose task/attempt, last observation, unresolved boundary and required recovery action.
- New safe retries remain automatic after confirmed no-start/exit and ordinary task policy. A persistently unavailable host leaves its affected tasks waiting until verified recovery; elapsed time is not proof. Preserve worktrees, sessions and logs.
- Cutover requires every service on the board to support the execution-release protocol. Old services may expire an attempt even under admission hold, so a local capability label or hold does not make mixed-version recovery safe. Drain/stop incompatible services before release, reconcile historical unresolved attempts and preserve rollback evidence. Never invent historical release records from age, task closure or owner acceptance. Cutover records attributable native/operator verification evidence and refuses rollback below a compatible execution-protocol version.

Status exposes unresolved execution id, host and termination reason in `execution_wait` per snapshot row, plus host `execution_waits`. Task state and counts remain board-derived. Native launcher I/O is bounded: Claude background exchange30s; Codex open/queue10s each. Pre-submission failures may release no-start; timeout, nonzero launcher exit and post-submission read errors remain uncertain.

Acceptance chains: disconnected owner with a running child; crash before/after intent and native submission; lost acknowledgment; same-attempt inbox continuation; worker result before process exit; cross-host requeue; cancellation refusal; corrupt ownership metadata; duplicate/stale release; confirmed no-start/exit permitting progress; incompatible service cutover refusal. Model, process and installed-host evidence remain separate.

Execution observations share the trusted immutable comment log but do not change task state or its revision. An accepted `spawn` is its first intent: execution id and initial intent cursor equal the spawn id. `taskq: executing <inbox cursor> attempt <A>` records a continuation only for the current doing/review attempt, after all earlier executions released, at its newest accepted inbox entry. That comment id is the new execution id.

`taskq: accepted <execution id> attempt <A>` records attributable native acceptance of that execution's exact input. It advances delivery through that execution's cursor; intent, process creation, task result and native exit do not. An observation can arrive after exit or task replacement, but cannot affect another execution. A prior `no-start` contradicts acceptance and cannot be overwritten. A released execution with unknown acceptance requires reconciliation before replaying its input, including inside a later cumulative input.

`taskq: released <execution id> exit|no-start attempt <A>` releases that exact accepted intent, including after its attempt is replaced. The first release proof is immutable; no-start is rejected once native acceptance is known. Release cannot target a future intent. A continuation cursor may repeat only when the prior intent for it has confirmed no-start; all earlier inputs must be accepted or confirmed no-start. Retry uses a new execution id and operation id `execute-<attempt>-<cursor>-<previous execution id>`; no-start does not consume the cursor. A new cursor must equal the newest accepted inbox entry. Two no-start failures for a continuation cursor ask the owner while retaining the inbox and session. An answer permits another bounded cycle; a native-identity lookup failure preserves the input and exposes a recovery action.

Edited, duplicate-op and malformed observations are ignored; absence of release preserves the fence. Services use deterministic operation ids (`accept-<execution>` and `release-<execution>`) and read back observations before updating caches. Retry an observation after a lost response, never the underlying native call. Historical accepted spawns without release remain unresolved until native proof; age, task closure and legacy `gone` never synthesize release. Legacy exit without acceptance stays explicitly unknown for input delivery.
